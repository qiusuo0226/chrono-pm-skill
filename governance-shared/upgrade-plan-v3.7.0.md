## 2. 原始需求照抄

> skill里面现在已经有一个文档拆分的能力了我现在要优化功能需求
> （1）skill拆分的文档要支持自动重复性校验和自动更新，比如我把项目的ai目录完整打包给项目集经理，项目集经理拿到我打包后的ai目录放到projects下面，然后项目集经理那儿原本就有一个项目b，a的合同和b的合同是同一个，那么拆出来的东西可能因为用的ai不同，ai版本不同，拆出来的需求范围和颗粒度可能不同，但是ai要能知道这是同一个文件拆出来的东西。
> （2）我二次拆这个文件，ai要能自动识别，更新对应的文件目录，比如我一个大项目，光需求文档一百多份，中途肯定不断更新，要不断进行拆解覆盖调整。
> （3）覆盖调整的这个事情要留痕留记录
> （4）拆解的文件可能需要一个文件去记录文件的基本信息，比如说大小、文件名、文件类型、文件md5值、文件创建时间、文件版本号、文件基础描述、文件修改拆解历史记录，等等，你还可以扩充需求
> （5）在之前升级的版本中我有提到，文件拆解了之后，对应放在同一个文件夹内，文件夹名应该是对应的文件编号，上层也会有索引。
> （6）拆好的文件夹内部，你根据我和另外agent对话的设计思路，你想想如何设计，需要多少文件。文件过多要考虑拆分，保证ai的可读性
> （7）还有专业术语，因为如果都合并到术语库里面，更新的时候会不会很麻烦，这块是不是要考虑一起优化处理。
> （8）比如拆出来的需求这种，需要自己给需求设置编号，这样方便WP工作包绑定。
> （9）我之前想过把这个能力单独拆成一个skill，但是考虑到功能性以及便利性，暂时就不拆了，但是我希望，在设计的时候，把这个能力直接集成到ChronoPM-Project下面的一个文件夹里面，可以也叫 xxxx-skill，这样后面想把这个技能独立出去会很简单。
>
> 前置对话背景（用户提供）：Skill 管理方法论（像管 Java 项目一样管 Skill：契约层/规范层/示例层三层、变更工单、回归测试、版本快照）、网关+专项 Skill 架构（薄网关常驻 ≤600 token、专项按需加载 800-1400 token、1800 红线）、token 消耗结论（封装不费 token，每轮全文注入才费）。

- **不纳入本次范围**：业务工作区零清的**代为执行**（清零是业务工作区动作，Skill 只提供流程与指引，执行须 PM 逐层确认）；拆解能力真正独立成第二个 Skill 包（用户明确暂不拆）；SRC-NNN 作互认键（延续禁令）。

### 设计要点 1：同源识别与自动对账（需求 1）

**同源判定口径（显式固化）**：同一源文档的判定**只看输入侧，不看产出侧**——`(簇固定号 OR source_doc 指针名+版本) + source_fingerprint` 相同即为同源；不同 AI / 不同 Skill 版本拆出的 ATOM 数量、颗粒度、norm_text 措辞不同**属正常现象，不影响同源判定**，且**不构成重拆理由**（延续"禁止二次拆解"）。

**WF-SD-1 接收侧对账工作流**（触发：联邦挂载/新 ai 目录放入 `projects/` 下后的首次对话，或 PM 说"对账/查重"；Portfolio 侧由 V-8 承接遍历）：

```
Step 1 扫描新纳入项目 requirements/sources/*/ledger.md（+meta.md 指纹）
Step 2 与其余项目逐条比对互认键（簇固定号 + 指纹）
Step 3 ├─ 指纹相同 → 判同源副本：本项目已有拆解则跳过（禁二次拆解），
       │            没有则复制首拆项目 sources/{簇ID}/ 并标 meta.shared_from
       ├─ 簇 ID 相同但指纹不同 → 源文档已变：走 WF-SD-2 增量重拆（先 SUGGEST 待 PM 确认）
       ├─ 文件名相似/指针名相同但指纹不同 → 疑似同源不同版：列证据请 PM 裁决，
       │            裁决前登记 pending-changes（类型=来源同源待裁决），禁止擅自归并
       └─ 无匹配 → 正常新建
Step 4 [AUTO] 更新 sources/_index.md（派生视图）；输出对账报告（同源 N / 版本差异 M / 待裁决 K）
```

原子性：Step 3 各分支写入均走"待确认"标记；失败整体回退，不留半对账状态。

### 设计要点 2：增量重拆工作流（需求 2）

**WF-SD-2**（触发：PM 提供源文档新版本 / 再次说"拆一下这份"）：

```
Step 1 算新指纹：与 meta.指纹相同 → 输出"无变化，跳过"（可强制重拆，需 PM 明示）
Step 2 不同 → 比对 source_version（PM 提供；不给则标"版本未知-指纹{8位}"，不猜测）
Step 3 章节级差异：meta 已记已拆/待拆章节 → 只对变化章节重提取（断点续导机制已有）
Step 4 ATOM 增量三态：
       ├─ 新增章节 → 追加 ATOM（新 ATOM_ID，接续编号）
       ├─ 变化章节 → 旧 ATOM 标 superseded_by=新 ATOM；新 ATOM supersedes=旧（沿用血缘字段）
       └─ 删除章节 → 旧 ATOM 标 stale，evidence 引用保留可查
Step 5 [AUTO] 更新 Canonical evidence + 索引；scope_scope 受影响的 Canonical 标 evidence_stale
Step 6 [SUGGEST] 受影响的 REQ 清单 → PM 确认后走 08 号 requirement 变更；未确认前登记册不动
Step 7 [AUTO] parse-log 记本轮；meta 更新（版本/指纹/拆解状态/已拆章节）；_index.md 更新
```

**覆盖即替换 + 血缘可查**：ATOM 只读不改写原则不变——"覆盖调整"通过 superseded_by 链实现替代而非原地改写（与 Module 32 需求情报 RI-001 长条款拆分血缘同一机制；注：CR-J 回归用例前缀因此改用 RJ-，避免与 Module 32 的 RI- 撞前缀）。

### 设计要点 3：留痕（需求 3）

每目录新增 `parse-log.md`（模板 source-parse-log-template.md），每轮一行 + 摘要段：

| 轮次 | 日期 | 触发 | 源版本 前→后 | 指纹变化 | ATOM 增/替/废 | REQ 影响 | 执行者 |
|---|---|---|---|---|---|---|---|

活跃区上限沿用 06 号归档口径（超限归档到目录内 parse-log-archive.md，同目录不另开子目录）。

### 设计要点 4：文件基本信息卡（需求 4，ledger 扩充）

ledger.md 从 5 列扩为 **9 列**（台账工具表，与 contract-register 同宽度级别；用户授权的扩充）：

| 字段 | 必填 | 说明 |
|---|---|---|
| source_id | 是 | 目录编号 |
| file | 是 | 源文件名 |
| file_type | 是 | pdf/docx/xlsx/md/其他 |
| size_kb | 否 | 文件大小（工具可得时填；不可得默认 `—` 不逼填，与必填最小集口径一致） |
| source_fingerprint | 是 | **升级为 MD5（可得时）**；不可得回退"大小+mtime"（口径写入字段注释） |
| file_created | 否 | 源文件创建时间（不可得填 —，不猜测） |
| source_version | 是 | 源文档版本（PM 登记；未知按 §设计要点2 Step2） |
| description | 否 | 一句话基础描述（≤30 字） |
| parse_history | 是 | 轮次计数 + 最近日期，明细指向 parse-log.md |

原 parsed_by/parsed_at 并入 parse-log（ledger 不再重复存，避免双写漂移）。**历史拆解产物不回填猜测值**（延续用户习惯约束：欠账数据保留"—"）。

**必填最小集标注（V0.2 采纳 B 问题 4）**：模板中显式区分两档——必填最小集（source_id/file/file_type/source_fingerprint/source_version/parse_history，6 列）与选填档（size_kb 工具可得时应填，file_created/description 不可得默认 `—` 不逼填），降低宽表 AI 填表错误率。

### 设计要点 5：目录=编号+上层索引（需求 5）

✅ 3.6.0 已实现：`sources/{编号}/`（编号=目录名）+ `sources/_index.md` 台账 + contract-register「拆解文件夹指针」列。本次仅在回归用例中固化，不改结构。

### 设计要点 6：文件夹内部设计与可读性拆分（需求 6）

**结论：6 件套 + 条件分片**。结合用户方法论的 token/可读性约束（单文件加载预算、_digest ≤400 行）：

| 文件 | 角色 | 膨胀控制 |
|---|---|---|
| meta.md | 基本信息卡 + 拆解状态 | 固定结构，不膨胀 |
| _digest.md | AI 专用 L2 摘要 | ≤400 行硬预算（已有） |
| atoms.md / atoms/ | 需求类 ATOM | **>300 条或 >1500 行** → 转 `atoms/`：按章节分片 `part-NN-{章节}.md` + `atoms/_index.md`（每分片一行：编号区间/章节/条数/摘要≤50字） |
| facts.md / facts/ | 非需求类事实 | 同上阈值 |
| ledger.md | 台账 9 列 | 单文档单目录，行数有限 |
| parse-log.md | 拆解历史 | 活跃区超限归档（要点 3） |

- 分片是**目录内二级**，不突破"索引 ≤3 层"红线（_index.md 台账 → atoms/_index.md → part 文件，共 3 层）。
- 分片只按章节语义切，禁止按行数硬切条款（一条 ATOM 不跨片）。
- 查询路由不变：_digest 先行；取证才进 atoms（分片时先读 atoms/_index.md 选片，单次只载 1 片）。

### 设计要点 7：术语节流（需求 7）

**不另建词库、不逐条打扰**，在既有入流链上加三档节流：

1. **证据先行**：拆解发现的术语一律先落 `facts.md`（kind=term，带出处），词库只收"候选指针"，不收原文——词库条目瘦，更新轻。
2. **批量确认**：术语候选默认攒批（每次拆解结束汇总输出"N 条术语候选"一次确认），禁止逐条弹确认；PM 也可说"术语全部 pending 先放着"。
3. **去重与升级门槛**：入 pending 前先对词库已有（原词/标准词）查重，命中则只更新"命中次数/最近命中"，不新增行；confirmed 仅对跨文档复用 ≥2 次或 PM 点名的术语建议升级（SUGGEST）。

### 设计要点 8：REQ 自动编号与 WP 绑定（需求 8）

- 拆解产出 REQ 时**自动取号**：`REQ-[模块代号]-NNN`，模块代号由来源派生——簇前缀映射表（CON→CONTRACT、BID→BID、INIT→INIT、COMP→COMP、SUP→SUPPLEMENT、TRN→TRANSFER、SRC→登记册既有模块代号或文档缩写，PM 可在登记册首次使用时改写一次）；NNN 在登记册内该代号下接续递增。
- 编号同时回填 ATOM/Canonical 的 REQ 指针，保证"条款→REQ"可取证。
- WP 绑定复用 §8.11.3 双向绑定（新产 REQ 提示归属 WP；未分配合法但登记 pending），不新造机制。

### 5.1 六件套对全生命周期文档种类的覆盖论证（V0.3 新增，回应用户追问）

用户提供的全生命周期文档清单（售前立项→招投标→签约→规划启动→需求设计→开发实施→测试→上线→验收→售后结项→贯穿类 + 监理专属，共 11 段约 60+ 种）与六件套的关系是**三个正交维度，六件套只是其中一维**：

| 维度 | 承载者 | 说明 |
|---|---|---|
| 文档是什么种类 | `source-type-registry.md` | 每类文档一行（source_type→category→authority），项目级可扩展 |
| 拆解产物放哪 | 六件套（本次升级） | 任意种类文档拆出来都是同一套容器，结构不随种类变 |
| 条款是什么语义 | ATOM `kind` | 要求/条件/约束/描述四语义类映射到 kind |

**覆盖实测**：用户清单对照 3.6.0 基线包（source-type-registry-template 实有 45+ 行）——合同/补充/NDA/廉政/保函、招标/投标/中标/澄清/补遗、立项/可研/建议书/报价/章程/管理计划、SRS/设计/API/原型/UI、WBS/部署/开源合规、测试报告/缺陷清单、割接/试运行/培训/手册、验收申请/初验/终验/资产移交、运维/结算/复盘/归档、变更单/函件/签字单、监理规划/月报/旁站/评估**均已有对应行**；缺口仅少量（如监理日志 supervision_log、监理实施细则 supervision_rule、会议纪要类 meeting_minutes、知识产权协议 ip_agreement 等，预计 ≤6 行），施工时在基线包模板追加即可（延续 Q11"清单外追加一行"机制，不预灌）。

**四语义类 ↔ kind 映射（拆解时逐条定性）**：

| 用户语义类 | ATOM kind（既有 10 类内） | 去向 |
|---|---|---|
| 要求类（必须做到） | requirement / requirement_directive | atoms.md → Canonical → REQ |
| 条件类（前提/触发/交付条件） | agreement（约定条件）；工期条件→milestone_fact | atoms.md / facts.md 按性质分流 |
| 约束类（强制限制） | constraint | atoms.md → Canonical → REQ |
| 描述类（背景/基线/参数） | background / baseline / hardware / spec / term | facts.md，不进 scope_scope |

**结论：六件套够用**。文档种类再多，变的只是 registry 行数与 kind 定性，容器结构不变——这正是"一源文档=一目录+统一六件套"设计的扩展性所在；种类膨胀被 registry（一行一类）吸收，不会冲击目录结构。

### 5.2 词库全生命周期设计（V0.3 新增，回应用户追问）

| 问题 | 设计 | 既有机制落点 |
|---|---|---|
| 词库怎么设计 | 项目级单库 `context/domain-glossary.md`，术语映射/纠错/待确认三表 + pending→confirmed 状态机；拆解不另建词库 | 17 号 §2/§3/§4 |
| 拆完了会合到总词库吗 | 会，但**瘦入流**：原文证据留在 facts（kind=term），词库只收候选指针；攒批一次确认，查重命中只计次不加行 | 设计要点 7 三档节流 |

**结论：词库机制 17 号已完备**（懒加载+分类拆分+阈值均为既有能力），本次只在拆解入流端加节流（设计要点 7），不动词库本体。参考"大型拆解"思路的核心 = **证据下沉（facts）、摘要上浮（词库只收指针）、按需加载（懒加载+预筛）**，与 17 号现行设计同源。

## 7. 数据、索引与扩展性设计

- **不新增索引层**：仍是 `sources/_index.md`（台账）→ 目录 → `atoms/_index.md`（分片，条件出现）三级封顶。
- **单文件膨胀控制**：atoms/facts 300 条/1500 行阈值分片；parse-log 活跃区归档；_digest ≤400 行不变。
- **增量更新**：WF-SD-2 天然增量（章节级断点）；台账/索引与数据写入同一操作内完成（AUTO 派生视图），失败整体回退。
- **stale 检测**：Canonical.evidence_stale + meta.source_version 双标记，AI 读取时可判过期（满足联动可检测性）。
- **去重策略**：互认键（簇固定号+指纹）即去重键；对账工作流是去重的执行体。

### 联动更新设计（摘要）

| 更新场景 | 触发 | 同步顺序（底层→上层） | 原子性 | 失败回退 |
|---|---|---|---|---|
| 首次拆解 | PM 提供文档 | atoms/facts → ledger/parse-log → meta → _index.md → Canonical → REQ(SUGGEST) | 同操作 | 整体回退 + stale |

| 接收对账 | WF-SD-1 | 副本复制(shared_from) → _index.md → 对账报告 | 逐分支独立事务 | 分支回退，不影响他分支 |

## 19. CR-J：风险问题体系重构 ★ §19.2 为 B 严格全方面审查区 ★

> 源自用户 2026-08-21 新需求：AI 不能很好识别风险与问题（如日报出现"有…风险"字样就直接登记为风险），需综合 PRINCE2/PMP/CSPM 多知识体系概念约束 AI 描述方式、强化识别；风险登记册与问题清单模板重新设计（现状不够结构化，不如个人待办任务 md 清晰可追溯历史）；风险与对应待办任务的绑定联动触发 AI 保证执行；升级执行文件里考虑历史数据迁移，旧格式废弃。

**现状实测痛点**：① AI 见"风险"字样直接登记，无判定过程；② 登记册主表 **15 列**宽表超 AI 稳定生成上限（用户 ≤7-8 列约束）；③ 模板状态枚举与 04 号规则**两套并存且互不一致**（risk 模板"识别中/监控中/已关闭/已发生" vs 04 号 §6.1"开放/监控中/已缓解/已关闭/转为问题"；issue 模板"待处理/处理中/已关闭" vs 04 号 §7.1"开放/处理中/已阻塞/已解决/已关闭"）；④ 历史不可追溯（状态变更记录=自由文本）；⑤ 风险应对与待办绑定无强制闭环。

### 19.1 识别强化：三体系概念锚定 + AI 判定硬约束（04 号新增 §1.2）

**概念锚定（综合 PRINCE2 / PMP / CSPM）**：

| 体系 | 风险定义要点 | 问题定义要点 | 本方案吸收 |
|---|---|---|---|
| PMP（PMBOK） | 不确定事件/条件，发生则对目标产生正向或负向影响 | 已发生、需处置的事项 | "不确定性"为风险第一判据 |
| PRINCE2 | 不确定事件（威胁+机会），属性=概率×影响×邻近度 | 已发生/必发生、正在影响交付的事项 | "已发生 vs 未发生"时间判据；问题必须关联影响对象 |
| CSPM（国标项目管理） | 可能影响项目目标实现的不确定性 | 已出现的偏差/障碍 | "对目标的影响"为登记必要条件 |

**AI 判定硬约束（四条，写入 04 号 §1.2）**：
1. **信号词甄别**：风险信号词（可能/担心/恐怕/万一/有苗头/不确定/存在…隐患）vs 问题信号词（已经/正在/导致/卡住/失败/缺员已发生）。日报出现"有…风险"字样**不直接登记**，必须先走三问判定；反之已发生事实用风险句式表述时，AI 必须纠正并建议改归问题。
2. **三问判定法（硬流程）**：① 是否已真实发生？② 描述是"可能性"还是"事实"？③ 是否已造成实际阻塞/影响？→ 风险/问题/待确认；任一问无法回答 → 标"待确认"（既有规则 3 升级为主路径）。
3. **描述句式校验**：登记必须符合句式（风险：`因为[原因]，可能导致[后果]，影响[对象]`；问题：`[已发生事实]+[已造成影响]+[影响范围]`）；用户原始表述不合句式时，AI 改写为合句式并**同屏呈现改写前后对照**，PM 确认未曲解原意后方可登记。
4. **识别判定卡前置**：日报/纪要/需求处理流程中检出风险信号 → 先输出"识别判定卡"（分类判定 + 三问依据 + 合句式描述建议 + Source）→ SUGGEST 登记；**禁止静默直写登记册**（延续底线 #2）。

**体系边界声明（V0.5 按 B 意见写死）**：① 04 号 §1.2 明文写"**本包仅威胁向**"，避免 AI 按 PMP 原文去登机会型风险（待确认 QJ-1）；② **邻近度本版不纳入**：概念对照表保留 PRINCE2 邻近度作为背景知识，但不进模板字段、不进评级矩阵（待 §19.1 对照表加注；B 建议 18）。

**机会型风险（PMP/PRINCE2 含机会）本次不纳入**：现行体系仅威胁向，扩机会型会波及应对策略/评级矩阵全套，超本次范围，入后续版本建议（待确认 QJ-1）。
