# 风险与问题约束规则

本规则适用于风险和问题的识别、评估、应对和升级。风险与问题必须分离管理。

---

## 1. 风险与问题的区分

| | Risk（风险） | Issue（问题） |
|--|--|--|
| 定义 | 可能发生但尚未发生 | 已经发生正在影响项目 |
| 性质 | 潜在威胁 | 实际问题 |
| 管理目标 | 降低概率或影响 | 尽快解决 |
| 文件 | `risks/risk-register.md` | `issues/issue-register.md` |

### 1.1 判定规则

1. 如果某事项已经发生，不得登记为 Risk，应登记为 Issue。
2. 如果某事项尚未发生但存在可能性，不得登记为 Issue，应登记为 Risk。
3. 如果无法判断，标记为"待确认"，不得擅自归类。
4. 风险实际发生时，必须从 Risk 转为 Issue：
   - 风险状态改为 `转为问题`。
   - 在 Issue 登记册中新增对应记录。
   - 两个记录通过 ID 互相关联。

## 2. 风险识别

### 2.1 风险来源维度

| 维度 | 检查方向 |
|------|----------|
| 需求风险 | 需求模糊、频繁变更、范围蔓延 |
| 技术风险 | 技术选型、架构可行性、性能瓶颈 |
| 进度风险 | 依赖未就绪、资源冲突、工期压缩 |
| 资源风险 | 人员变动、能力不足、多项目冲突 |
| 外部风险 | 政策变化、客户组织变动、供应商问题 |
| 质量风险 | 测试不充分、缺陷修复延迟 |
| 成本风险 | 人力成本超支、返工成本 |
| 合规风险 | 安全合规、数据合规、信创要求 |

### 2.2 风险描述规范

```
风险编号：R-YYYYMMDD-NNN
风险描述：因为 [触发条件/原因]，可能导致 [后果]，影响 [受影响对象]。
风险类别：[需求/技术/进度/资源/外部/质量/成本/合规]
```

## 3. 风险评估

### 3.1 概率评级

| 等级 | 概率范围 | 判定参考 |
|------|----------|----------|
| 极低(1) | <10% | 几乎不可能发生 |
| 低(2) | 10%-30% | 偶有可能 |
| 中(3) | 30%-50% | 有一定可能 |
| 高(4) | 50%-70% | 较可能发生，已有迹象 |
| 极高(5) | >70% | 很可能或已在发生 |

### 3.2 影响评级

| 等级 | 进度影响 | 成本影响 | 质量影响 | 范围影响 |
|------|----------|----------|----------|----------|
| 极小(1) | <2天 | <1万 | 轻微缺陷 | 无变化 |
| 较小(2) | 2-5天 | 1-3万 | 少量缺陷 | 局部调整 |
| 中等(3) | 5-10天 | 3-5万 | 需修复后可用 | 模块级调整 |
| 较大(4) | 10-20天 | 5-10万 | 核心功能受影响 | 需求级变更 |
| 极大(5) | >20天或里程碑延期 | >10万 | 系统不可用 | 范围基线变更 |

### 3.3 风险等级矩阵

风险等级 = 概率 x 影响：

- **极高(16-25)**：必须升级至项目发起方，制定专项应对方案。
- **高(12-15)**：必须升级至项目经理，有明确应对计划。
- **中(6-11)**：项目组跟踪管理，有应对措施。
- **低(1-5)**：记录观察，无需专项措施。

## 4. 风险应对策略

| 策略 | 适用场景 | 做法 |
|------|----------|------|
| 规避 | 风险过高，可改变计划避免 | 调整方案或技术路线 |
| 转移 | 自身无法控制 | 外包、保险、合同条款 |
| 减轻 | 可降低概率或影响 | 增加测试、备份方案、POC 验证 |
| 接受 | 风险可控或应对成本过高 | 记录并准备应急计划 |

中等及以上风险必须制定应对计划，包含：预防措施、缓解措施、负责人、触发条件、应急计划、预计成本、关闭条件。

## 5. 风险升级机制

| 触发条件 | 升级目标 | 时限 |
|----------|----------|------|
| 风险等级达到极高 | 项目发起方 | 24小时内 |
| 风险等级升至高 | 项目经理 | 48小时内 |
| 风险已发生（转为问题） | 项目经理 | 立即 |
| 应对措施失效 | 原路径上一级 | 立即 |

升级时必须提供：风险描述及等级、已采取措施及效果、升级原因、至少2个决策选项（含利弊）、不升级的后果。

## 6. 风险登记册

### 6.1 字段定义

| 字段 | 说明 |
|------|------|
| Risk ID | R-YYYYMMDD-NNN |
| 描述 | 风险描述 |
| 类别 | 需求/技术/进度/资源/外部/质量/成本/合规 |
| 概率 | 1-5 |
| 影响 | 1-5 |
| 风险等级 | 低/中/高/极高 |
| 应对策略 | 规避/转移/减轻/接受 |
| 应对措施 | 具体措施 |
| 负责人 | 责任人 |
| 状态 | 开放 / 监控中 / 已缓解 / 已关闭 / 转为问题 |
| 识别日期 | YYYY-MM-DD |
| 关闭日期 | YYYY-MM-DD |
| Source | 来源 |

### 6.2 维护频率

- 项目启动时建立初始版本。
- 每个里程碑评审前全面更新。
- 每周项目例会确认新增和状态变化。
- 风险发生时立即更新。

## 7. 问题登记册

### 7.1 字段定义

| 字段 | 说明 |
|------|------|
| Issue ID | I-YYYYMMDD-NNN |
| 描述 | 问题描述 |
| 类型 | project（项目级）/ defect（产品缺陷，MVP暂存） |
| 影响范围 | 受影响的任务/里程碑/模块 |
| 严重程度 | P0 / P1 / P2 / P3 |
| 负责人 | 责任人 |
| 状态 | 开放 / 处理中 / 已阻塞 / 已解决 / 已关闭 |
| 提出日期 | YYYY-MM-DD |
| 解决日期 | YYYY-MM-DD |
| 解决方案 | 处理方式和结果 |
| Source | 来源 |

### 7.2 问题与任务的关联

- 每个问题应关联到受影响的任务（Issue Ref 字段）。
- 任务因问题阻塞时，任务状态改为 `已阻塞`，并填写 Issue Ref。
- 问题解决后，阻塞任务应恢复为 `进行中`。

## 8. Change Log

风险登记册和问题登记册底部各自维护 Change Log，格式同待办文件变更段。Change Log 活跃区上限 50 行或超过 30 天时触发按月归档到 `change-log/archive/YYYYMM-change-log.md`，并维护 `change-log/index.md` 月份导航（与 06 号归档规则一致）。

### 8.1 Issue 主体拆分规则

issue-register 主体拆分（与 risk-register 对齐）：
- 触发：>30 条记录
- 策略：`已解决`/`已关闭` 状态的 issue 归档到 `issues/archive/YYYY-issue-register.md`
- 主体仅保留 `开放`/`处理中`/`已阻塞` 状态的 issue
- 归档后维护 `issues/index.md`
- 归档操作记录在 Change Log 中

## 9. 级联传播规则

本实体（Risk / Issue）状态变更时，按以下规则触发下游动作。动作分三类：
- [AUTO] 写派生视图（索引/待办），低风险，直接执行
- [CHECK] 只读校验，检查关联是否存在/一致
- [SUGGEST] 写事实源或影响其他实体，加入建议更新清单待 PM 确认

> **AUTO 作用域声明**：AUTO 仅作用于非事实源的派生视图，不触碰任何事实源文件。事实源写入（含 pending 登记）一律受 `skill-contract.md` 第 5 条约束。

执行顺序：先 AUTO → 再 CHECK → 最后 SUGGEST。
同一处理流程内，级联动作只执行一次；多个 SUGGEST 汇总为同一批建议清单，流程末尾统一输出。
执行完毕后，14 号自查清单验证完整性。

> **强制执行要求**（见 `00-pm-main-rules.md` §8a）：以上 AUTO/CHECK/SUGGEST 动作不得静默跳过。SUGGEST 必须呈现给 PM 确认，不得以"用户未要求"为由省略。流程末尾必须输出"级联完整性"结论。

Risk 创建 →
  [AUTO] 更新 risk-register 衍生索引（若已拆分）
  [SUGGEST] 若 risk.owner 存在 → 建议在其待办文件 todos/{date}/{owner}.md 追加跟进待办

Risk 状态 → 已关闭 →
  [AUTO] 更新待办文件中关联待办（Risk Ref 指向本风险）的状态
  [CHECK] 检查是否有 task 的 Risk Ref 指向本风险

Risk 状态 → 转为问题 →
  [SUGGEST] 必须在 issue-register 新增对应 issue，双向 ID 关联（§1 规则 4）
  [AUTO] 更新 risk-register 和 issue-register 的衍生索引
  [SUGGEST] 检查是否有 task 引用本风险 → 建议更新为引用新 issue

Issue 创建 →
  [AUTO] 更新 issue-register 衍生索引（若已拆分）
  [CHECK] 若含 Risk Ref → 验证关联风险存在且状态合理
  [SUGGEST] 若 issue.owner 存在 → 建议在其待办文件 todos/{date}/{owner}.md 追加处理待办
  [SUGGEST] 若关联 task-id → 建议将对应 task 状态设为已阻塞

Issue 状态 → 已解决/已关闭 →
  [AUTO] 更新待办文件中关联待办（问题 Ref 指向本问题）的状态
  [SUGGEST] 检查被阻塞的 task → 建议恢复为进行中
  [CHECK] 若由 Risk 转化而来 → 检查原 Risk 状态是否需要同步

Issue Owner 变更 →
  [AUTO] 更新待办文件中该 issue 关联待办的 Owner 字段

### 9.1 关闭确认佐证强制要求

> 本约束适用于 AI 在 WF-1/WF-2 等流程中建议关闭 Risk 或 Issue 实体时。§9 主体定义关闭后的级联动作，本节定义关闭建议本身的输出质量要求，两者互补。

当级联传播涉及 Risk 或 Issue 的关闭建议（状态 → 已关闭 / 已缓解 / 已解决）时，AI 必须在 SUGGEST 动作中显式列出：

1. **候选关闭项编号**：Risk ID 或 Issue ID
2. **关闭佐证**：具体说明为什么可以关闭（哪个关联 Task 已完成 / 哪个触发条件已消除 / 用户明确确认已解决）
3. **关联影响**：关闭后是否影响其他开放实体
4. **PM 确认门禁（DF-002，v2.1.0 强化）**：候选清单输出后，必须等待 PM 逐条明确确认，方可修改登记册对应状态；未获确认前不得改库，也不得以"默认同意""无异议即关闭"代替确认

**枚举时机**：除级联触发外，日报/周报处理流程（WF-2/WF-5）输出后，AI 应主动批量罗列当期可关闭的风险/问题候选（明确到具体编号 I-XXXX/R-XXXX 并附详细描述与佐证），供 PM 逐条确认。

格式：

```
建议关闭：
1. R-20260810-001（佐证：关联待办 TD-CJJ-20260810-003 已完成，触发条件已消除）
2. I-20260811-002（佐证：用户确认问题已解决，日报 2026-08-14 提及）
```

禁止在未列明佐证的情况下输出关闭建议。此要求与 `00-pm-main-rules.md` §8a 的 SUGGEST 强制呈现互补：§8a 确保 SUGGEST 不被跳过，本节确保关闭类 SUGGEST 必须含可验证证据。

> 本节规则由内置默认偏好 **DF-002**（见 pm-profile §1 与 `21-pm-profile-rules.md` §5.1a）承载：PM 可在偏好中修正或废弃（如允许特定类别自动关闭）；PM 有明确声明时以声明为准，无声明时按本节执行。

> 端到端工作流数据路径见 `00-pm-main-rules.md` §9（WF-1~WF-6）。本文件 §9 定义 Risk/Issue 实体的级联规则，00号 §9 定义跨实体的完整工作流路径，两者互补不替代。
