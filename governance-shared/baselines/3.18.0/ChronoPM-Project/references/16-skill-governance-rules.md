# Skill 变更治理规则

本规则用于约束 AI 对本 Skill 的修改行为，防止随意修改导致已有能力失效。

---

## 1. 核心规则

AI 不得直接修改 Skill 文件。任何 Skill 修改必须先生成变更工单、影响分析和回归测试计划，并等待用户确认。

---

## 2. 强制变更流程

任何 Skill 变更必须按以下流程执行：

```
1. 生成升级方案审查文档（AP）← 设计阶段只改 AP，必须详细输出，供用户审查
2. 用户准许执行后，在开发仓 `governance-shared/change-requests/` 创建变更工单（CR）
3. 生成影响分析（IA）
4. 提出最小修改方案
5. 等待用户确认
6. 执行最小变更
7. 运行回归测试
8. 生成回归报告（RR）
9. 更新 VERSION / skill.json / CHANGELOG.md
10. 清理：清理本次升级过程中产生的临时工作文件（Agent 工作草稿、临时输出目录）、构建缓存（__pycache__/ 等），检查根目录是否符合白名单（§18），删除非标准文件。**AP 升级方案草稿属 Agent 工作草稿，发布验证通过后删除**（实质已固化于 migration 文件 + 基线 + CHANGELOG，见 §19 AP 生命周期）
11. 验证：检查根目录白名单合规性；检查正式文档中是否存在幽灵引用（引用了不存在的文件或非标准产物）；检查文档内版本号一致性（如 SKILL.md 版本控制表）；验证历史污染已清除；**执行 `governance-shared/review-checklists/release-checklist.md` 全部检查项（含 C-1～C-4；C-4 存量 examples 豁免场景/mermaid）**
12. 如发布通过，生成基线快照（此时工作空间已是清洁状态）
```

### 2.1 升级方案审查文档（AP）输出要求

AI 在提出任何 Skill 变更前，**必须先输出完整的升级方案审查文档**，供用户审查决策。文档必须包含以下 7 个章节，缺一不可：

#### AP-1. 变更概述

用一段话说明本次变更的核心内容和目标，让用户 30 秒内理解要改什么、为什么改。

#### AP-2. 影响点详细分析

逐文件、逐能力分析影响，**不得只写"低风险"或"无影响"**，必须具体说明：

| 影响项 | 当前状态 | 变更后状态 | 影响描述 | 影响程度 | 是否可逆 |
|---|---|---|---|---|---|
| [文件路径] | [当前内容/行为] | [变更后内容/行为] | [具体影响什么] | 高/中/低 | 是/否 |

分析维度必须覆盖：
- 哪些规则文件的逻辑会变化
- 哪些已有能力的行为会改变
- 哪些模板结构会调整
- 哪些目录结构会变化
- 哪些脚本行为会改变
- 哪些回归用例可能受影响
- 是否影响已有工作区的兼容性
- 是否影响核心契约层

#### AP-3. 变更策略与设计思路

必须说明：
1. **为什么选择这个方案**（而不是其他替代方案）
2. **设计思路**（新增的能力如何与现有体系融合，不会产生冲突）
3. **关键决策点**（每个关键设计选择的理由）
4. **与现有规则的交互关系**（新增/修改的规则如何与 00-15 的现有规则联动）
5. **替代方案对比**（至少列出 1 个被否决的替代方案及否决原因）

#### AP-4. 修改范围清单

| 文件 | 修改类型 | 修改内容摘要 | 新增/修改行数 | 是否核心契约 |
|---|---|---|---|---|

修改类型取值：`new_file` / `edit_section` / `edit_full` / `delete` / `rename`

#### AP-5. 回归测试计划

| Case ID | 模块 | 输入 | 预期结果 | 类型 | 说明 |
|---|---|---|---|---|---|
| | | | | positive / regression / negative | |

必须明确说明：
- 本次变更影响了哪些已有回归用例
- 是否需要新增回归用例
- 哪些用例是"必须通过"的阻断项

#### AP-6. 风险评估与回滚方案

| 风险项 | 发生概率 | 影响程度 | 预防措施 | 回滚方案 |
|---|---|---|---|---|

回滚方案必须具体：
- 回滚到哪个版本
- 回滚操作步骤
- 回滚后哪些新能力不可用
- 是否需要工作区迁移回退

#### AP-7. 版本影响

| 维度 | 变更前 | 变更后 |
|---|---|---|
| Skill Version | | |
| Workspace Schema | | |
| 是否需要工作区迁移 | | 是/否 |
| 迁移模式 | | structure-only / recent-7-days / N/A |
| 是否影响核心契约 | | 是/否 |
| 是否影响已有工作区 | | 是/否 |

### 2.1a CR 文件创建时机（v3.8.0）

| 规则 | 内容 |
|---|---|
| 设计阶段 | **只改 AP**。方案讨论、审查、修订一律写在 `governance-shared/planning/upgrade-plan-v{目标版本}.md`（每周期限 1 个，禁止附加后缀），**不得**落 CR 文件 |
| CR 创建时机 | **仅当用户准许执行**（如确认 upgrade-to 施工清单）时，才在开发仓 `governance-shared/change-requests/` 创建 CR |
| 创建位置 | CR / IA / 基线等 governance 文件只允许出现在开发仓 `governance-shared/`，不得写入业务工作区 |
| 业务对话 | ChronoPM-Project 业务对话**严禁创建任何 governance 层文件**（含 CR/IA/基线）。需求与待确认走 `pm-decisions.md` 或直接回答。用户说「帮我开 CR」→ 拒绝落文件，引导到开发仓先写 AP |

### 2.2 审查输出格式要求

AI 输出升级方案审查文档时，必须使用以下格式：

```markdown
---
CR ID: CR-YYYYMMDD-NNN
AP Version: 1.0
Status: pending_review
---

# 升级方案审查文档

## AP-1. 变更概述

[一段话概述]

## AP-2. 影响点详细分析

[影响分析表 + 文字说明]

## AP-3. 变更策略与设计思路

[设计思路 + 关键决策 + 替代方案对比]

## AP-4. 修改范围清单

[文件清单表]

## AP-5. 回归测试计划

[测试用例表 + 阻断项说明]

## AP-6. 风险评估与回滚方案

[风险表 + 回滚步骤]

## AP-7. 版本影响

[版本影响表]

---
请审查以上方案。确认后回复"同意执行"，我将按最小修改方案实施。
```

### 2.3 禁止跳过审查

AI 不得跳过升级方案审查文档直接修改文件。即使用户说"直接改吧"，AI 也必须先输出审查文档的核心章节（至少 AP-1 到 AP-4），再执行。

---

## 3. 禁止直接修改规则

当用户提出"优化 Skill""调整规则""加一个能力""改一下提示词"等请求时，AI 必须先输出变更工单草案，不得直接改文件。

例外情况（可直接修改，但需记录 CHANGELOG）：
- 仅修复模板中的错别字或格式问题
- 仅新增测试用例
- 仅新增模板文件（不修改已有文件）

---

## 4. 单一目标规则

一次变更只能服务一个明确、可验证目标。

禁止在同一次变更中混合：新功能、Bug 修复、文案优化、目录结构调整、模板重构、脚本重构。

如用户提出多个目标，必须拆分为多个 CR。

---

## 5. 核心契约保护规则

以下文件属于核心契约层，未经用户明确批准不得修改：

- `SKILL.md`
- `skill.json`
- `governance/contracts/skill-contract.md`
- `references/00-pm-main-rules.md`

修改核心契约层必须标记为 `contract_change`，并执行全量回归。

---

## 6. 最小补丁规则

实施变更时，只允许修改达成本次 CR 目标所必需的最小文件和最小片段。

禁止顺手优化、顺手改名、顺手重构。

---

## 7. 回归必跑规则

每次变更必须至少包含：

1. 正向用例（验证新能力生效）
2. 反向用例（验证不应触发的场景不触发）
3. 旧功能回归用例（验证未破坏已有能力）

如无测试用例，不得发布新版本。

---

## 8. 不可改目标规则

变更执行后，不得修改原始变更目标来适配实际结果。

如果结果不满足目标，必须判定为失败、修复或回滚。

---

## 9. 回滚规则

如果回归测试失败，AI 必须建议回滚到上一版本基线，不得继续叠加临时修复。

---

## 10. 版本号规则

| 变更类型 | 版本提升 |
|---|---|
| 核心契约变化 | Major 或 Minor |
| 新增能力或目录结构 | Minor + workspace schema |
| 规则修复 | Patch |
| 仅新增测试或模板 | Patch |

---

## 11. CHANGELOG 强制格式

任何发布版本必须更新 `CHANGELOG.md`，记录：

- 变更目标
- 修改文件
- 测试用例
- 是否影响 schema
- 是否需要迁移
- 回滚方式

---

## 12. 规则重构审查

每 3 个 Minor 版本做一次规则重构审查，检查：

- 是否有重复规则
- 是否有互相冲突
- 是否有已废弃的目录
- 是否有旧术语没更新
- 是否有模板和规则不一致
- 是否有路由表落后于实际能力

重构本身也必须走 CR。

---

## 13. 安全提问方式

用户要求修改 Skill 时，推荐使用：

```
请不要直接修改 Skill。
我想新增/调整能力：[描述]。
请先按 skill-governance-rules 生成：
1. 变更工单
2. 影响分析
3. 回归测试计划
4. 最小修改方案
等我确认后再实施。
```

或简短版：

```
按 Skill 变更治理流程处理，不要直接改。先出 CR、影响分析和回归用例。
```

## 14. 发布检查清单

发布前必须完成 `governance-shared/review-checklists/release-checklist.md` 中的所有检查项。

## 15. 与其他规则的关系

## 17. Blueprint 更新规则

`SKILL_BLUEPRINT.md` 是 Skill 的架构决策与能力审查蓝图。更新规则如下：

### 17.1 分级触发

| 触发条件 | 更新级别 | 更新内容 |
|---|---|---|
| Major 版本 | 必更 | 全文审查：能力地图、架构决策、Roadmap、Limitations |
| Minor 版本 | 必更 | 能力地图、版本状态、Roadmap、Known Limitations、数据流 |
| 新增/删除能力 | 必更 | Capability Map、Rule Dependency |
| workspace schema 变化 | 必更 | Schema Evolution |
| 新增治理机制 | 必更 | Governance Model |
| 新增核心数据流 | 必更 | Data Flow |
| 新增迁移/升级机制 | 必更 | Workspace Upgrade |
| Patch 版本 | 应更 | 版本元数据（版本号、日期） |
| 仅新增模板/测试/措辞 | 免更 | CHANGELOG 标注 "Blueprint Impact: none" |

### 17.2 结构性变更走 CR

以下 Blueprint 变更需走完整 CR 流程（§2）：

- 新增/删除一级章节
- 新增/删除 Capability ID
- 改变能力分类体系
- 将某能力标记为废弃
- 修改核心设计决策解释
- 修改外部审查标准
- 修改 Document Boundary 定义
- 与 SKILL.md / skill.json 出现能力口径不一致

### 17.3 普通更新走轻量流程

以下 Blueprint 变更只需 CHANGELOG 记录：

- 版本号更新
- Roadmap 补充
- Known Limitations 补充
- 状态从已规划改为部分落地 / 已落地
- 审查指南措辞优化

### 17.4 Blueprint 层级归属

Blueprint 属于**文档层（Documentation Layer）**，不属于核心契约层。

- 普通更新：无需 CR，记录 CHANGELOG
- 结构性变更：需走 CR
- 发布前必检：VERSION / skill.json / CHANGELOG / Blueprint 版本一致性

### 17.5 CHANGELOG 标注要求

每次版本发布时，CHANGELOG 中必须标注 Blueprint 影响：

```markdown
Blueprint Impact: [full / metadata-only / none]
```

- `full`：正文内容有实质性更新（能力矩阵、架构决策、数据流等）
- `metadata-only`：仅更新版本号和日期
- `none`：本次变更不影响 Blueprint 内容

## 18. 根目录白名单

Skill 根目录只允许以下文件和一级子目录存在。白名单之外的文件或目录一律视为非标准产物，不得在升级过程中创建。

**作用域**：本白名单约束范围限定为 Skill 根目录。子目录（`governance/`、`references/`、`scripts/`、`tests/`、`assets/`）的标准文件集由各自目录的规则文件管理，不在本白名单范围内。

**维护机制**：白名单由每次 CR 的 **AP-4 修改范围清单**驱动更新。当 AP-4 中包含 `new_file` 类型且文件位于根目录时，发布检查清单中需确认白名单已同步新增该文件。

| 条目 | 类型 | 性质 |
|---|---|---|
| `SKILL.md` | 文件 | 核心契约（Skill 主提示词） |
| `skill.json` | 文件 | Skill 元数据 |
| `VERSION` | 文件 | 版本号 |
| `CHANGELOG.md` | 文件 | 变更历史 |
| `README.md` | 文件 | 中文说明 |
| `README.en.md` | 文件 | 英文说明 |
| `SKILL_BLUEPRINT.md` | 文件 | 能力蓝图 |
| `.gitignore` | 文件 | Git 忽略规则 |
| `.git/` | 目录 | VCS 系统目录（版本控制元数据，不纳入清洁度检查） |
| `assets/` | 目录 | 模板、资源文件 |
| `governance/` | 目录 | 治理归档（CR、IA、RR、基线等） |
| `references/` | 目录 | 规则声明文件 |
| `scripts/` | 目录 | 自动化脚本 |
| `tests/` | 目录 | 回归测试套件 |

## 19. 交付物类型控制

Agent 在升级过程中只能创建治理流程明确定义的交付物类型：

- **CR**（变更工单）
- **AP**（升级方案审查文档）
- **IA**（影响分析）
- **RR**（回归报告）
- **基线快照**

未列举的交付物类型不得创建。如需新类型的交付物，必须先修改本治理规则本身。

**AP 生命周期**：设计阶段只改 AP。用户准许执行后**第一步**写 CR + upgrade-to + IA 接住思路。删除门=该版本已有 CR、upgrade-to 不再引用 upgrade-plan 路径、CHANGELOG 有该版本段、baselines/{v}/ 存在，且检查清单已提示。顺序：改引用 → 写/核对 CR 与 upgrade-to → 提醒检查 → 删 AP → audit。已有基线仍留该版 AP = 发布失败。

**作用域**：本条款约束范围为 `governance/` 目录下的所有归档文件（包括 `change-requests/`、`impact-analysis/`、`regression-reports/`、`baselines/` 等子目录）。

---

## 20. 引用完整性约束

任何治理归档文件（CR、IA、RR、基线 README、CHANGELOG、**migration**）中引用的文件路径，必须指向实际存在的文件。如果引用的文件属于工作过程中的临时产物（如 Agent 工作草稿），不得在正式归档文档中引用。

**正式归档文档不得引用 upgrade-plan 草稿路径**（如 `governance/upgrade-plan-v*.md`）。违规实例：存量 `upgrade-to-2.1.0.md` 曾引用 `upgrade-plan-v2.1.md` 草稿路径。正确写法：CR 编号标「—（未走独立 CR）」并指向本 migration + 基线 + CHANGELOG。

发布前验证（§2 第 11 步）必须包含幽灵引用扫描：检查所有治理归档文档中的文件引用是否指向实际存在的标准产物。

---

## 21. AP 草稿文件强制约束

AP（升级方案审查文档）草稿在生成时必须遵守：

### 21.1 数量

每个升级周期只允许 **1 个** AP 草稿。禁止因篇幅或按需求拆成多个文件。过长则对话内分块，不拆文件。

### 21.2 命名

必须为 `upgrade-plan-v{目标版本号}.md`。禁止附加 `-requirements`、`-review` 等后缀，禁止用 CR 号当文件名。

### 21.3 存放位置

必须放在 `governance-shared/planning/`。禁止 `output/`、仓库根或其他目录。新周期开始前如有遗留草稿须先确认清理。

## 22. examples 示例生成标准约束

本约束从 **新写的示例** 生效，**不追溯** 3.15.0 重编号前的存量对话正文。

### 22.1 场景背景

新示例开头须有：假项目名、项目经理/组员、业务背景、前置条件。禁止只有「你」「助手」空对话。

### 22.2 完整流程

新示例须含 mermaid 全过程、至少一轮完整对话、关键决策点解释。

### 22.3 可独立阅读

引用其他示例必须给链接。

### 22.4 与实际能力一致

不得演示未实现功能。
