# 更新触发规则

本规则用于提升 ChronoPM Skill 对用户更新意图的识别能力。AI 不应只在用户明确指定目标文件时才更新，而应主动识别用户输入、上传文件或粘贴内容中可能产生的项目管理更新事项。

---

## 1. 核心原则

当用户输入中出现更新意图或强管理信号时，AI 必须主动进入更新触发流程，而不是仅做解释性回答。

**AI 应主动但谨慎：**
- 对低风险过程记录，可主动生成更新内容。
- 对高风险事实源变更，必须请求用户确认。
- 对项目归属、事项类型、审批状态不明确的信息，必须追问。
- 不得将未经确认的推测写为事实。

---

## 1b. 语义信号触发前的术语归一化

在识别"记录一下""更新一下""同步到看板"等触发信号前，执行术语归一化：

1. 读取本项目 `context/domain-glossary.md`（如存在）
2. `confirmed` 术语先映射为标准名，再进行信号检测
3. `pending` 术语仅作为候选理解，不得触发确定性事实源更新
4. `conflict`/低置信度术语触发追问，不自动写入事实源
5. 归一化记录保留原文片段

示例：

用户："记录一下，农专注销接口对接完了"
→ "农专"在词库中为 confirmed，映射为"农民专业合作社"
→ 信号"记录一下"触发更新
→ 更新事实源时使用标准名"农民专业合作社注销接口"
→ 归一化记录中保留原文"农专"

用户："更新一下，清算组报备字段对齐了"
→ "清算组报备"不在词库，低置信度
→ 触发追问："清算组报备"可能是"清算组备案"，请确认
→ 事实源更新标注"不确定"，等待用户确认

## 2. 四级触发机制

### Level 1：显式更新指令 — 直接触发

当用户输入包含以下表达时，必须进入更新流程：

| 触发词 | 说明 |
|---|---|
| 记录一下 / 记一下 | 通用入库指令 |
| 更新一下 / 同步一下 | 更新事实源 |
| 登记一下 | 新增记录 |
| 归档一下 / 入库 | 文件归档 |
| 写进去 / 写到管理库 | 写入指定文件 |
| 放到项目里 / 纳入项目管理 | 纳入管理范围 |
| 加到周报 / 加到日报 / 加到风险 / 加到问题 / 加到任务 / 加到需求 | 指定目标文件更新 |
| 整理成会议纪要 / 生成会议记录 / 生成评审记录 | 生成过程记录 |
| 更新看板 / 更新P&L / 更新里程碑 / 更新资源 | 指定事实源更新 |

**处理流程：** 直接进入更新解析，不需询问是否更新，但高风险项仍需确认后写入。

### Level 2：文件类型触发 — 主动询问是否更新

当用户上传、粘贴或提到以下材料时，AI 应自动判断文件类型，并主动询问是否需要按 ChronoPM 规则解析并生成更新建议：

| 用户表述 | 文件类型 | 默认处理动作 |
|---|---|---|
| 日报 / 今日进展 / 个人日报 / 项目日报 | daily_report | 提取进展、任务、风险、问题、资源变化 |
| 周报 / 本周总结 | weekly_report | 汇总/归档/生成周报 |
| 会议记录 / 会议纪要 / 会议内容 | meeting_minutes | 提取行动项、决策、风险、问题、需求变更 |
| 需求评审 / 需求确认 / 需求讨论 | requirement_review | 提取需求、变更、评审结论、待确认事项 |
| 设计评审 / 技术评审 / 方案评审 | design_review | 提取设计决策、技术风险、行动项、问题 |
| 技术方案 / 技术设计 | technical_design | 提取设计决策、风险、依赖、任务 |
| 接口文档 / API文档 | api_doc | 提取接口依赖和风险，建议引用不直接复制 |
| 测试报告 / 缺陷清单 / 测试问题 | test_report | 提取缺陷、质量风险、验收阻塞 |
| 验收意见 / 验收反馈 / 客户验收 | acceptance_feedback | 提取验收问题、需求差异、决策事项 |
| 客户反馈 / 客户意见 | customer_feedback | 判断是需求、问题、变更还是风险 |
| 上线方案 / 部署方案 / 发布计划 | release_plan | 提取上线任务、风险、回滚方案、决策 |
| 评审 / 评审材料 / 评审文件 | review_general | 根据内容判断是需求评审/设计评审/技术评审，触发对应流程 |

**询问格式：**

```markdown
我识别到这是【文件类型】材料。
是否需要我按 ChronoPM 规则解析并生成以下更新建议？

可能涉及：
1. [目标文件1]；
2. [目标文件2]；
3. [目标文件3]。
```

如果用户之前已经说了"更新""记录""入库"等显式指令，则跳过询问，直接进入更新建议流程。

### Level 3：语义信号触发 — 主动提示候选更新

即使用户没说"更新"，只要内容中出现以下强管理信号，AI 也应主动提示可能需要更新：

#### 需求信号
新增、调整、变更、取消、范围变化、客户要求、评审通过、待确认、验收标准、需求冻结、需求评审

→ 触发：`requirements/requirement-register.md`、`requirements/change-log.md`、`decisions/decision-log.md`

#### 任务信号
安排、负责、跟进、完成、延期、阻塞、下周处理、今天处理、交付、联调、测试、修复、上线

→ 触发：`todos/{date}/{owner}.md` 待办文件

#### 倒排计划信号
倒排、根据X月X日、截止日前完成、围绕某日期排、反向排期、到某日必须完成

→ 触发：按 `00-pm-main-rules.md` §9 WF-7 倒排计划编排执行（写 `wps/WP-*.md` + `_index.md` + PLAN §3 引用简表 + 待办文件）。

> **倒排草案查询提示（v1.21.0）**：PM 查询倒排相关内容时，若待办文件中倒排范围内的待办自上次生成草案后发生过变更，AI 应在输出中附带提示：“待办文件自上次生成草案后有 N 条变更，建议刷新倒排矩阵”。不新增独立触发类型，仅在现有查询流程中附带提示。

#### 待办归属信号
加个待办、加个任务、排一下、安排到计划、归到某工作包、属于哪个计划/WP（旧说法"安排到迭代/属于哪个迭代"同样命中）

→ 触发：按 `00-pm-main-rules.md` §9 WF-8 归属判定执行（新任务创建统一前置规则）。

#### WP 文件信号
新建工作包、建个 WP、拆工作包、WP-NNN 进度/详情

→ 触发：写/读 `wps/WP-*.md` + `wps/_index.md`；创建走 WF-8 溯源（00 号 §8b.5）。计划文件只改 §3 引用简表。

#### 源文档拆解信号
拆解合同、拆招标文件、入库源文档、提取需求条款、源文档台账

→ 触发：`07-requirement-rules.md` §8.6/§8.11。产物落 `requirements/sources/{编号}/`；先读 `_index.md`。存量 `{type}-source/` 未迁完则截止并输出迁移清单。

#### 风险/问题信号
风险、问题、阻塞、依赖未到位、环境未准备、延期、无法推进、没人处理、客户未确认、数据缺失、接口不通、上线受影响

→ 触发：`risks/risk-register.md`、`issues/issue-register.md`

#### 决策信号
决定、确认、拍板、同意、不做、延期、裁剪、优先做、暂缓、取消、方案选型、领导要求、客户确认

→ 触发：`decisions/decision-log.md`

#### 待办信号
明天做、下周做、安排、计划做、待办、todo、跟进、推动、确认、推进、督促、提醒、记得

→ 触发：本项目 `todos/{date}/` 待办文件 + 绑定文件 `todos/{date}/_index.md`。跨项目待办查询/结转请到 ChronoPM-Portfolio 对话。
→ 触发后：待办**创建**统一路由 `00-pm-main-rules.md` WF-8 归属判定（正式任务强制落待办文件）；待办**状态更新**执行状态级联检查。

#### 资源信号
请假、抽调、借调、支援、离场、进场、换人、顶替、B角、没人、共享、投入比例、暂停投入、转去、回到

→ 触发：最新合法日 `_index.md` **§1 花名册**；有待办者同时追加个人 **§0.5**。跨项目共享人员时提示用 ChronoPM-Portfolio 包维护集层索引；本包不写 `portfolio/`。若变动同时构成风险 → 本项目 `risks/risk-register.md`。禁止再写 `resource-register` / `transfer-log`。

#### 工时表 / 日志量 / 能耗投喂信号
工时表、填写量、日志量、能耗、人日、人时、成本损耗、能效、投喂工时

→ 触发：`01-daily-report-rules.md` **§1.6**（写入该人待办 **§0.6**）。**禁止改走 `plans/budget.md`**。单位取 project-context；表头对不上就问；AI 禁止凭空编数。

#### 待办/计划生成信号
生成 PM 待办、生成周计划、处理日报实际完成

→ 触发：`todos/{date}/` 待办文件（待办清单 + 工作日志段；v2.0.0 起无前向快照体系，待办文件本身即历史）

#### 评审信号
需求评审、设计评审、技术评审、方案评审、接口评审、数据库评审、上线评审、验收评审

→ 触发：`meetings/` 或 `reviews/`、`decisions/decision-log.md`、`pending-changes.md`（未排期待办区块）、`risks/risk-register.md`、`issues/issue-register.md`、`requirements/change-log.md`

**提示格式：**

```markdown
我在内容中识别到【信号类型】信号。
建议更新以下文件：
1. [目标文件] — [原因]
是否需要我生成更新建议？
```

### Level 4：纯查询 — 不触发更新

如果用户只是查询（如"现在有哪些风险？""本周项目怎么样？""谁在做什么？"），AI 只查询不输出更新清单。

但若查询中发现明显数据缺口，可提示：

```markdown
查询中发现以下数据缺口：
- [缺口1]

如需我根据本次查询结果更新对应文件，请回复"更新"。
```

## 3. 项目归属判断

### 3.1 首读 project-brief.md

AI 在处理任何用户输入前，必须先读取本项目 `context/project-brief.md`，以此判断输入内容与当前项目的关联度。

### 3.2 归属判断规则

| 判断条件 | 归属 | 目标路径 |
|---|---|---|
| 内容明确属于本项目 | 本项目 | 本项目 `ai/` 下对应事实源 |
| 内容提到他项目名称 / 疑似非本项目 | 他项目 | **不写入**本项目；提示到对应项目对话写入 |
| 内容中提到"整体""所有项目""全局""项目集" | 跨项目 | 提示用 ChronoPM-Portfolio 包（本包不写 `portfolio/`） |
| 内容中提到人员姓名，可在本项目 `_index` §1 花名册中匹配 | 本项目 | 本项目 `todos/`（花名册 + 个人待办） |
| 内容中提到需求编号（REQ-XXX-NNN）且可在本项目登记册匹配 | 本项目 | 本项目 `requirements/` |
| 内容中提到待办编号（TD-xxx）且可在本项目待办匹配 | 本项目 | 本项目 `todos/` |
| 关联度低或无法判断 | 不确定 | 追问用户 |

### 3.3 关联度不匹配时

如果输入内容与 `project-brief.md` 中的项目信息关联度低，AI 应提示：

```markdown
该内容似乎与当前项目不匹配。
当前项目为【项目名称】。
请确认：1. 属于本项目，写入当前 ai/；2. 属于他项目，请到对应项目对话写入；3. 跨项目查询/汇总，请使用 ChronoPM-Portfolio。
```

## 4. 更新权限分级

默认采用 `proactive` 模式。项目可在 `project-rules.md` 中修改权限级别。

### 4.1 权限级别选项

| 级别 | 说明 |
|---|---|
| `passive` | AI 只输出建议更新清单，不直接更新文件 |
| `proactive` | AI 可写入低/中风险事实源并标记 `Confirmed By: 待确认`、登记 `pending-changes.md`，高风险文件必须确认（默认） |
| `progressive` | AI 可自动处理多数文件，关键事实源变更必须确认 |

> 注：`confirm_before_write` 已移除，存量配置自动映射到 `proactive` 处理。

### 4.2 低风险更新（可主动生成或直接更新）

- 日报归档
- 会议纪要草稿归档
- 评审纪要归档
- 周报草稿生成
- 花名册 / §0.5 人员变动候选
- AI 操作日志更新
- 未排期待办候选新增（登记 `pending-changes.md`）
- 风险/问题候选 → 经识别判定卡 SUGGEST，不得低风险直写登记册

### 4.3 高风险更新（必须确认后才能更新）

- 需求状态从已提议改为已确认
- 需求状态改为已取消
- 需求变更批准（已批准）
- 预算/P&L 金额调整
- 里程碑日期调整
- 任务状态改为已完成
- 风险关闭
- 问题关闭
- 正式决策记录新增为定稿
- 验收结论已验收
- 人员正式离场（已离场）
- 删除、覆盖、重写历史记录

## 6. 最小追问规则

当以下信息不明确时，AI 必须追问。追问应最小化，只问阻断更新的关键信息：

### 不清楚项目归属时

```markdown
我识别到这是一条可入库信息，但不确定是否属于本项目。
请选择：
1. 属于本项目，写入当前 ai/
2. 属于他项目，请到对应项目对话写入
3. 跨项目查询/汇总，请使用 ChronoPM-Portfolio
```

### 不清楚事项类型时

```markdown
这条信息可能是【需求】也可能是【任务】。
请确认：
1. 作为需求登记；
2. 作为未排期待办登记（pending-changes.md）；
3. 同时登记需求并拆出任务。
```

### 不清楚是否为正式决策时

```markdown
我识别到其中包含"决定/确认/同意"等表述，但不确定是否为正式决策。
是否写入 decision-log.md？
```

### 不清楚更新模式时

```markdown
我可以根据当前内容生成更新项。
请确认更新模式：
1. 只输出建议更新清单；
2. 生成可粘贴到目标文件的内容；
3. 直接更新低风险文件，高风险项待确认。
```

## 7. 更新处理流程

当触发更新流程时，AI 按以下步骤处理：

```
1. 判断用户意图：查询 / 更新 / 归档 / 解析 / 生成
2. 读取 project-brief.md，判断作用范围和项目归属
3. 判断材料类型：日报 / 会议 / 需求评审 / 设计评审 / 周报 / 资源变动 / 风险问题
4. 定位目标文件（按路由表）
5. 提取结构化事项
6. 判断是否需要追问（最小追问规则）
7. 判断更新权限（低风险可主动 / 高风险需确认）
7.5 写入低/中风险项时必须标记 `Confirmed By: 待确认` 并在 `pending-changes.md` 登记；高风险项仍须确认
8. **级联传播执行**：对每个变更事项，执行其对应实体的级联传播规则（见各实体规则文件 §级联传播规则）。所有 AUTO 直接执行，所有 CHECK 执行并记录，所有 SUGGEST 汇总到建议清单——不得静默跳过任何级联动作（见 `00-pm-main-rules.md` §8a）
9. 输出更新计划或直接生成内容
10. 输出 Suggested File Updates（必须包含所有级联 SUGGEST 项）
11. **级联完成验证**（`00-pm-main-rules.md` §8a.2）：输出"级联完整性"结论
```

## 8. 更新后关联字段完整性检查

在日常更新、查询、生成报告、分析风险、推导计划等操作完成后，AI 应根据 `19-info-completeness-rules.md` 执行关联字段完整性检查。

### 8.1 检查时机

| 操作类型 | 是否检查 | 检查范围 |
|---|---|---|
| 日常更新（日报/会议/需求/任务/资源） | 是 | 更新涉及的文件及其关联文件 |
| 查询类 | 弱触发 | 仅检查与查询直接相关的字段 |
| 生成报告（周报/状态报告） | 强触发 | 报告涉及的所有管理域 |
| 分析风险/成本/进度 | 强触发 | 分析涉及的所有管理域 |
| 导出 Excel/Word/PDF | 强触发 | 导出涉及的所有管理域 |

### 8.2 检查与提醒

- 检查结果按 P0-P3 分级（详见 `19-info-completeness-rules.md` §4）。
- P0/P1 缺失项主动提醒用户，说明影响和建议。
- P2/P3 缺失项在回答后简短提示或仅在巡检报告中列出。
- 用户可通过指令控制提醒行为（"本次不要提醒""进入静默模式"等）。

### 8.3 与 14-self-check 的协作

- `14-self-check-rules.md` 负责文档处理后的即时质检（索引一致性、字段完整性、关联完整性）。
- `19-info-completeness-rules.md` 负责日常操作时的持续巡检（全事实源文件字段缺失/过期/冲突）。
- 两者互补：14 是"事后质检"，19 是"事前/过程中巡检"。
- 两者不合并，各自独立执行。
