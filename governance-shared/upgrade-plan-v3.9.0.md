## 1. 原始需求照抄

### 需求点 1（可观测日志）

可观测日志：每一步执行留日志：调用的模型、消耗 token、抽取耗时、字段错误记录，方便排查幻觉、漏条款问题；日志过多可能要考虑归档查询，日志的字段设计也要符合 ai 生成 md 的文档限制，单表格不超 7 个字段；还要考虑如果等什么都处理完了再写日志，会导致整个调用链路的增加；是不是可以考虑多代理协同；这个里面的运转机制要参考异步线程的代码写法，执行的时候才能避免遗漏。

### 需求点 2（任务分片、异步处理）

支持任务分片、异步处理：百万级大文档不会一次性全量送入模型，支持分批处理；又或者是，人员分批提供日报；现在必须等前一个 agent 处理完了，后一个 agent 才能继续处理，要不然比如处理掉共用的 index 索引位置的时候容易出错，一次完整的日报汇总需要十分钟，太浪费时间了；这里面要提效。

### 需求点 2 附带（Portfolio 读侧）

ChronoPM-Portfolio 是否要改得合理的去思考规划。之前定义 ChronoPM-Project 做写、ChronoPM-Portfolio 做读。优化了日志功能以及归档功能线路后，肯定要支持项目集的查看，调用也会涉及。

### 需求点 3（升级残留垃圾）

方案可落 `governance-shared`。该路径下还有残留的之前升级的垃圾 3.8.0 的方案。要先排查那个垃圾为什么会在那儿。之前版本升级中有优化升级规范检查路径，升级完同步要处理开发路径下非必要存在、升级过程中的垃圾文件，不知道为什么还在那里。当做此次方案中的一个需求点继续优化。

### 需求点 4（打包歧义）

之前让其他 AI 执行 skill 打发布包时，很多 skill 还会产生歧义。此次方案要包含处理这个问题。参考：某 agent 说 Project zip 缺 `tests/regression-suite.md`、`SKILL_BLUEPRINT.md`、`source-split-skill/SKILL.md`（zip 里只有 `source-split-skill/references/`）。另一 agent 核实：这三项是 pack.ps1 刻意排除；但 `source-split-skill` 在包里成孤儿，且排除逻辑缺自动化守门。

### 需求点 5（对外说人话覆盖处理汇报）

实际使用中 AI 回复使用了 skill 框架内的术语词或占位符，用户看不懂。之前版本明确要求要用大白话问用户待确认处理决策项，这不单单体现在最终，推导过程也要显得够人性化。示例：处理日报时打印「原文进当天 §2，进度映射进 §3」。§2/§3 用户不理解。根因分析（用户提供，纳入需求）：说人话只覆盖确认提问不覆盖处理汇报；「必须打印路径+章节」和「禁止内部术语」冲突；没有对外词典；回归只挡了「建议更新清单」。

### 需求点 6（工程质量与测试自动化，评审意见）

## 4. 用户交互流程（人话）

**处理一批日报（验证仓口径的人话例子，不写验证仓）**

以全链通那种「一天三十多份个人待办」为例：张三、李四可以同时丢给两个助手，不必互等总表。两个助手都丢「王国政」的两段原文时，谁都不覆盖对方正在整理的那份，先各自记下，再按时间合进王国政当天那一份（契约：一天一份，只追加不覆盖）。

1. 不同的人：各记各的，不必互等总表。
2. 同一个人：后到的不覆盖先到的，按时间合进去。
3. 一批结束后，按磁盘上已有的个人文件重列当天名单。
4. 对项目经理说人话：原文收好了没有、进度改到待办没有、明天打算做什么还在今天原文里。
5. 人问「改了哪些文件」再给路径。

**拆大文档**

1. 按章节/块分批，不一次塞进模型。
2. 每批抽完立刻记：用了什么模型、token（有则记，无则「未知」）、耗时、哪条字段抽歪了。
3. 漏条款从字段错误表查，不靠聊天回忆。

**集经理查日志**

1. 换 Portfolio 对话。
2. 只看各项目已经写下的过程日志，不改成员项目。

## 5. 输入输出规范

### 5.1 过程日志（防膨胀，懒建，不升 schema）

不是事实源。查询先读 **`ai/logs/ops/_index.md`**（无则尚未发生过过程日志）。路径单一事实源：一律 `logs/ops/_index.md`，禁止再写 `ops-index.md`。

验证仓量级（只举例）：全链通单日约三十余人；若每人 5 步 ≈ 150 行/天。大文档若 200 片 ≈ 200 行/次。因此 **禁止默认按月单文件** 无限追加。

**落盘（活跃区按日）**

| 文件 | 内容 | 上限 | 超限 |
|---|---|---|---|
| `logs/ops/_index.md` | 日期指针（表 C） | 自身 ≤100 行 | 旧月指针进 archive 索引 |
| `logs/ops/YYYY-MM-DD.md` | 表 A 步骤流水 | **300 行** | 拆 `YYYY-MM-DD-p2.md`，index 加一行 |
| `logs/ops/YYYY-MM-DD-errors.md` | 表 B 字段错误（无错误则不建） | **300 行** | 同样 -p2 |
| `logs/ops/runs/{run_id}/{隔离键}.md` | 运行中工人私有，逐步 flush | 单文件 ≤100 行 | 工人不得改别人的 run 文件 |
| `logs/archive/YYYYMM-ops.md` | **跨月**整包（不是超 300 行的去处） | — | 活历史，index 受控可读 |

Phase C 必须把 `runs/{run_id}/` **合并进当天文件后删除该 run 目录**。禁止把分片当长期存储（这是膨胀的第一来源）。

**表 A 步骤流水（`YYYY-MM-DD.md`，7 列）**

| 时刻 | 场景 | 对象 | 模型 | token | 耗时秒 | 结果 |
|---|---|---|---|---|---|---|
| HH:MM:SS | 日报/拆解/收尾 | 人名或 SRC-NNN/片号 | 实得模型名；宿主不给则「未知」 | 输入+输出合计；无则「未知」 | 整数秒；无则「未知」 | 成功 / 失败 / 入队 |

禁止编造模型、token、耗时。token 是用量，不是 API Key。

**表 B 字段错误（`YYYY-MM-DD-errors.md`，7 列；无错误不建文件）**

| 时刻 | 对象 | 字段 | 类型 | 摘录 | 处置 | 步骤 |
|---|---|---|---|---|---|---|
| HH:MM:SS | 人名或 SRC-NNN | 抽歪的字段名 | 空 / 幻觉 / 漏条款 / 越界 | **≤80 字** | 待确认 / 忽略 / 已改 | 对应表 A 时刻 |

禁止把日报原文或合同条款整段贴进「摘录」。

**表 C ops 索引（`logs/ops/_index.md`，7 列）**

| 日期 | 场景摘要 | 行数 | 错误数 | 分片数 | 状态 | 更新 |
|---|---|---|---|---|---|---|
| YYYY-MM-DD | ≤200 字 | 表 A 行数 | 表 B 行数 | 当天 -pN 个数 | 进行中 / 已收尾 / 已归档 | HH:MM |

parse-log 模板（拆解血缘，不是 ops；本次改 ≤7 列，K9）：

| 轮次 | 日期 | 触发 | 源版本与指纹 | ATOM 增/替/废 | REQ 影响 | 执行者 |
|---|---|---|---|---|---|---|
| 1 | YYYY-MM-DD | 首次/重拆/对账 | v?→v1.0 / 指纹变\|未变 | +n / 替 n / 废 n | 无 / SUGGEST | AI / 姓名 |

拆解过程中的字段错误进 ops 表 B，不把 parse-log 撑回 8 列。存量 parse-log 8 列行不回填；下一轮按 7 列写。

Portfolio：`portfolio/logs/ops/_index.md` + 当日文件只记集层动作；成员日志只读各项目 `ai/logs/ops/_index.md` 的行，不遍历 runs/、不写成员。

**禁止**

- 等整批结束再补写当天日志。
- 编造 token/模型/耗时。
- 日志里写 API Key / 密码。
- 把日志当进度事实源。
- 按月单文件堆到上千行。
- 超 300 行不拆 -p2、误去月归档。
- 收尾后仍留 `runs/` 碎片。

### 5.2 分片与临界区（跨人并行 + 同人入队）

跨人：像线程本地。同人：像队列，不是再等整队 10 分钟。

**V0.3 否决共享 `_lease.md`。** 那张表自己就是新的共享竞争点（B1 P1-1）。Markdown 没有跨会话文件锁。唯一不会互相覆盖的写入，是 **文件名互不相同的新文件**。

**硬规则：工人永不写 `{owner}.md`。** 哪怕本对话只有一个人、只有一份日报，也先写 inbox，再由本 run 的收尾合并。规则只有一条，模型不容易走错「快路径」。

```
# 临界区 A：短，串行（本 run 的协调者；不写业务文件）
列出本次对象（人 / 文档片）
分配 run_id（本 run 私有）与隔离键
写 logs/ops/runs/{run_id}/assign.md（只给本 run 工人读）
写 ops「本 run 开始」

# 线程本地 B：不同人可并行；同人也不碰 {owner}.md
for person in people:          # 张三、李四可以同时
    try:
        append 自己的 run 日志「开始」
        只写 todos/{date}/inbox/{owner}-{HHmmss}-{agent}.md
        不得打开、创建、改写 {owner}.md
        不得写 _index.md / pending / 他人 inbox / 他人 claim
        append run 日志「结束+用量+错误」
    except:
        append run 日志「失败」

# 按人合并 C'：每次只合并一个人
# 扫描范围（P1-C）：当日 todos/{date}/inbox/ 里全部 owner（含上批遗留），
# 不是「本批对象」。收尾再扫最近一个合法日（date≤今天且该日目录存在）的 inbox。
# 稿合进「稿所在日期」的 {owner}.md，禁止把昨天的稿写进今天。
for owner in 该日 inbox 全部 owner:
    写唯一文件 inbox/.claim-{owner}-{yyyyMMddHHmmss}-{run_id}.md
      YAML: owner / date / run_id / agent / started / expires(=started+20min)
    立刻再列 inbox/.claim-{owner}-*
      忽略已过期 claim
      按文件名排序
    再列一次（双检）
    若自己不是未过期中的第一名:          # 分支③ P1-7
        删除自己刚建的 claim
        不碰 {owner}.md、不碰他人 claim、不碰 inbox 稿
        结束该人
    若自己是第一名:
        实读清单 L = 当前 inbox/{owner}-*.md 的具体文件名
          （不含 .claim-* / 点文件）          # P1-D
        若 L 为空:                            # 分支② P1-6
            删除自己的 claim
            不创建、不改写 {owner}.md
            结束该人
        合并恒可执行（P1-G）：按 01 §1.3 把 L 追加进
          todos/{该日}/{owner}.md（无则创建）
        遇他人有效 claim：退避重列，最多 3 次
        3 次仍冲突：稿原地保留；ops 表 B 记失败（对象=稿文件名）；
          删自己的 claim；禁止 pending、禁止 ASK、禁止静默删
        成功则：哈希相同跳过；只删 L 里那些文件名；删自己的 claim
        过期的他人 claim 可删

# 临界区 C：短，串行（派生 + 临时文件归零断言）
扫当日目录重建 _index §3（排除 _index.md / inbox/ / 点文件）
把 runs/{run_id}/ 并入当天 ops 后删除 run 目录
更新 logs/ops/_index.md
归零断言（不满足不得宣布当天完成；处置全自动，不等人）：
  1. 当日 inbox/ 无 {owner}-*.md 稿
     非空 → 回 C' 接管（冲突则 3 次重试）
     仍非空 → 稿保留 + ops 表 B 记失败，本断言本轮放过该稿，
               由下轮 C' 与 19 号 AUTO 接走
  2. 当日 inbox/ 无 .claim-* （直接删剩余 claim）
  3. 本 run 的 logs/ops/runs/{run_id}/ 已不存在
  4. 当日每人至多一份 {owner}.md
  5. 最近合法日 inbox 非空 → 对那一日跑 C'（同上，不等人）
```

**claim 不是事实源、不是 7 列表。** 一个文件锁一个人。过期默认 20 分钟。无 OS 锁。

**inbox 格式**：YAML `owner/date/time/agent` + 原文块 + 已解析的工作记录草稿。不是第二份事实源；合并后删除。§3 派生扫描 **必须排除** 整个 `inbox/`（含 claim）。

**共享文件（工人禁写）**：`_index.md`、**任何** `{owner}.md`（含自己的）、`pm-decisions.md` 主体、各 register、`wps/_index`、`sources/_index`、他人 ops、他人 inbox、他人 claim。

`pm-decisions.md` **只协调者写**。多源（T-N1 缺负责人、22 号空闲、14/19 巡检、未绑定 WP、关联缺处理方式、块 8 写入确认）不得各写各的文件、不得整文件覆盖成只剩本源那一块：读整文件 → 按「分块 + 对象编号 + 事项键」查重 → 命中则合并说明/时间，未命中则在对应块追加一行 → 写回。两协调者撞车：后写者再读再合，禁止抹掉别人的块。

**线程本地（工人可写）**：`inbox/{自己}-{HHmmss}-{agent}.md`；`atoms/part-NN-*.md`；`logs/ops/runs/{run_id}/{自己}.md`。

**协调者可写（持有该人 claim 且再列第一）**：该人 `{owner}.md`；收尾时的 `_index` 当日参与、pm-decisions（按块追加）、ops index。

契约第 10 条不变：一天一份 `{owner}.md`。inbox 是排队，不是第二份日报。

举例（验证仓口径、不写验证仓）：助手甲、助手乙同时拿到「王国政」两段原文——两人都只写 `todos/2026-08-21/inbox/王国政-HHMMSS-甲.md` / `…-乙.md`，不必互等，也不改 `王国政.md`。谁先跑 C' 谁建 claim；再列第一者按时间把两段追加进 `王国政.md`。另一人发现自己不是第一就停，不覆盖。

**为何不选 B 的 ① / ② 原文**

| 选项 | 为何不够 |

| ① 协调者在临界区 A 写 `_lease.md` | 两个独立对话各自当协调者时，仍抢同一张表（读改写丢行） |

#### 需求清单

权威：`requirements/_index.md`（检索）+ `requirements/requirement-register.md`（或按模块分片）。不再把 25 列宽表当默认读取面。

索引列（≤7）：`Req ID | 标题 | 确认状态 | 生命周期 | 工作包 | 来源指针 | 优先级`

确认状态：`未确认` / `已确认` / `已否决`。未确认必须能标缺口（可多项）：做不做 / 效果未对齐 / 方案未对齐。三项没齐不得标已确认。

生命周期不再用「已确认」占位：`已提议`（刚入库）/ `进行中` / `已交付` / `已验收` / `已变更` / `已取消`。已提议且确认状态=未确认 = 还在等 PM。

工作包列：`WP-001, WP-014` 或 `—`。空值合法但必须进决策文件「需求未绑定工作包」。

来源指针：`sources/SRC-NNN` + 章节/条款 + 页码。能回到原件。ATOM 已有 `source_ref` 的，入库需求时上提，不让页码只活在证据层。

变更：需求变更仍走 08 号独立 change-log；登记册底部操作 Change Log 保留。决策「确认/否决这条需求」另外写入 PM 决策记录，不拿对话日志充数。

膨胀：沿 06 号——索引保持瘦；正文超 50 条按模块分片 + `_index`；Change Log 50 行/30 天按月归档。查询先读索引再打开命中分片，禁止默认通读整册。

未确认需求可以继续留在清单里（后续文件还会拆出更多条），**不得**拿去组已规划工作包、不得拆待办。

#### 工作包

状态：`待确认` → `已规划` → `进行中` → `已完成`。头状态允许「待确认」（推翻现行「三态不得写待评审」里把待确认也禁掉的理解；「待评审」仍是评审门派生结论，不进头状态）。

- 新建 WP 必须至少绑一条需求编号。搜不到需求 → 禁止建包，进决策文件「工作包无需求」。PM 坚持要这块活 → 先在需求清单补需求（可仍是未确认），再绑，并记疑似蔓延。
- 新建后默认 `待确认`。PM 在工作包确认块认可切法与绑定 → `已规划`，才允许拆待办、才允许进计划时间盒。
- 小需求合成一个大包、大需求拆多个小包，都合法。AI **禁止**代切颗粒度。
- WP 关联需求段只保留编号（及可选来源文件路径指针）。禁止把功能描述、验收标准抄进 WP。功能点行只关联待办编号，不混写需求。
- 下辖待办仍实时聚合、不落盘。

工作包确认清单不是第二份事实源：开放项在 PM 决策文件「工作包待确认」块；状态以 WP 文件头 + `wps/_index.md` 为准。

## 7.5 AP 什么时候删（需求 3，V0.2 重写）

用户要的是 **开发仓最终干净** 和 **思路不丢**，不是卡某个钟点删 3.8.0。

**删除门（同时满足才允许删该版本 AP）**

1. 该版本已有 CR（状态 completed 或 in-progress 且正文含决策）。
2. 该版本已有 `upgrade-to-{v}.md`，且正文 **不再引用** `upgrade-plan-v*.md` 路径。
3. CHANGELOG 有该版本段；`baselines/{v}/` 存在。
4. 执行文件已经用固定话术提醒过升级人检查清单（见 Step Y）。
5. 升级人回复确认，**或** 检查清单项已在 upgrade-to 里全部勾上。

顺序必须是：**改引用 → 写/核对 CR 与 upgrade-to → 提醒检查 → 删 AP → audit**。先删文件后改引用会留下幽灵路径。

## 8. 数据、索引、分块与扩展性

涉及运行时数据：过程日志。

**为何「合不了」在机械上几乎不存在**：稿的 YAML 与文件名自带 owner/date（`inbox/{owner}-{HHmmss}-{agent}.md` 又位于 `todos/{date}/inbox/`），合并=按 01 §1.3 追加文本 + 哈希查重——只要能读写文件就合得进。因此协议应写死为「合并恒可执行」，把「合不了 → 问人」从协议里彻底删除：

4. **19 号巡检残留稿由 SUGGEST 升为 AUTO 接管**：巡检发现最近合法日 inbox 非空 → 直接按稿所在日期跑 C' 合并（巡检场景无并发批次，恰是最安全的合并时机）；claim 直接删；仅把「本次巡检自动合并了哪些残留稿」作为巡检报告事实行输出（告知，不是待办）。L722、L85、SH-007 期望同步改。
