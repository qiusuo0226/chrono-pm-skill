## Change Goal

> 可验证目标：

1. 需求登记册（REQ 层）支持"实现视图"与"原型/文档链接"两个可选字段，开发日报处理（WF-2）时 AI 能同时输出业务上下文（REQ 功能描述）与实现上下文（实现视图/原型链接）。
2. 开发侧文档（PRD/设计文档/接口说明/原型描述）可通过 07 号 §8.6 触发 D 提取为 technical 类 ATOM，并归并到既有 Canonical 证据链。
3. technical 类 ATOM 不参与 scope_scope 范围判定聚合（硬约束，DV-001 红线用例守护）。
4. 存量工作区零迁移：新字段均可选，schema 保持 0.8.0，旧登记册/旧日报不受影响。

## Problem Statement

当前问题：

1. **业务 ⇄ 开发需求语义断层**：合同/招标/立项来源的需求偏业务表述，开发日报偏实现语言（模块名/接口名），AI 处理开发日报时无法对照业务上下文，"每天日报到底说的是什么"理解不完整。
2. **开发文档无摄入通道**：RI 现有 source_type 体系未覆盖开发侧文档（PRD/设计文档/接口说明），原型图无处登记。
3. **大规模需求文档场景**：用户项目需求文档达几万页、数百万至千万字，需要渐进导入与指针式存储策略的明确规则。

## 升级方案审查文档（AP）

### AP-1. 变更概述

引入**需求双视图机制**解决"合同需求（业务视角）⇄ 开发需求（实现视角）"语义断层：

- **view_business（业务视图）**：不新增字段，为 business 类（contractual/procurement/approval/compliance/operational）ATOM 的 norm_text 派生聚合，查时现算，挂 Canonical 经 evidence 派生。
- **view_dev（实现视图）**：新增字段，挂 **REQ 层**（登记册"实现视图"列，摘要级 ≤100 字，与 Task→REQ 日报链路对齐）。
- **原型/文档链接**：新增字段，挂 REQ 层，指针式存储（原文档不入库）。
- **technical 隔离红线**：technical 类 ATOM（dev_prd/design_doc/api_spec/prototype/ui_spec）不参与 scope_scope 聚合，仅填充 REQ 实现视图/原型链接。
- **WF-2 需求上下文**：Task 带 Requirement Ref 时按链路加载（单次 ≤10 条 REQ，降级不阻塞）。

版本定位：Minor（capability_change），1.19.1 → 1.20.0；schema 保持 0.8.0，无迁移；全量回归。

### AP-3. 变更策略与设计思路

1. **为什么选择这个方案**：用户核心痛点是"业务需求文档（给甲方）与开发需求文档（给开发）的断层"，AI 处理开发日报时缺少业务对照。双视图以最小改动（2 个可选列 + 1 个派生视图）打通 Task→REQ 链路。
2. **设计思路**：view_business 派生不加字段（避免 Canonical 层冗余存储）；view_dev 挂 REQ 层（日报链路是 Task→REQ 而非 Task→Canonical，粒度对齐）；原型只存指针（避免工作区体积膨胀）。
3. **关键决策点**（四轮审核锁定）：
   - D1 双视图挂 REQ 层而非 Canonical 层（B2 二轮纠正粒度失配）；
   - D2 view_business 为派生视图不新增字段（B2 二轮补齐存储语义）；
   - D3 technical 类 ATOM 硬约束排除出 scope_scope（B1 二轮架构风险）；
   - D4 19 号巡检收敛为存在性校验，不变相强制可选字段（B1 三轮 R-F2）；
   - D5 词库类别为自由文本，仅补充分类标签示例而非枚举扩展（B1 三轮 R-F1）；
   - D6 12 号扩展列方案 α：追加 U/V 与 O-T 连续（B1 四轮拍板，不打乱行号引用）；
   - D7 05 号"需求详情路由"与既有"范围判定路由"显式区分描述，避免实施混淆（B1 四轮修正 1）；
   - D8 回归统计表同步维护（B1 四轮修正 2，audit 断言守门）。
4. **与现有规则的交互关系**：07 号 RI 三层模型（ATOM→Canonical→REQ）不变；05 号三级索引与 P1 语义兜底复用；17 号状态机与 §12.2 拆分复用；03 号 Requirement Ref 可选语义不变。
5. **替代方案对比**：
   - 否决方案一（V0.1）：新建 source-doc-register 登记册 + WF-9 导入流程——与 contract-register/source-type-registry/§8.6 重叠建设，B 一轮否决；
   - 否决方案二：view_dev 挂 Canonical 层——粒度失配（日报链路是 Task→REQ），B2 二轮否决；
   - 否决方案三：12 号扩展列方案 β（插入与 Markdown 列序一致位置）——打乱既有行号引用、改动更大，B1 四轮否决。
