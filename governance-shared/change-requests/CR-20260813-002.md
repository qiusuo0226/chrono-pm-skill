## Change Goal

在 v1.15.0 已发布的跨源需求归集（RI）能力之上，补齐"合同与子项目**多对多映射**"架构缺口：新增项目集级 `portfolio/requirements/` RI 存储、`contract-register.md` 合同登记册事实源、按合同 scope_level 的 ATOM/Canonical 存储归属（supplement 跟随父合同）、带合同维度的 scope 判定（contract_refs）、四步检索路由、成套文档簇关联与合同变更三级联动。同时以最小补丁方式修复 CR-20260813-001 遗留的脚本层缺口（项目集模式 RI 骨架缺失、SKILL.md §4 事实源表缺 RI 文件、0.7.0 迁移无子项目遍历）。可验证目标：1) 项目集模式下可登记多合同与多对多映射并建 `portfolio/requirements/` RI 骨架；2) 用户问"X 在不在合同 N 范围"可正确路由到对应层级 canonical 并返回带合同维度的 scope 结论；3) supplement 的 ATOM/Canonical 存储与检索跟随父合同 scope_level；4) 空登记册触发补录引导，不臆造结论；5) workspace schema 0.7.0→0.8.0 structure-only 迁移补齐项目集与子项目 RI 目录。

## Problem Statement

当前问题：当前 RI 方案把 ATOM/Canonical/索引全部放在子项目级 `projects/{子项目}/requirements/` 下，隐含"合同与子项目 1:1"假设。但现实中合同与子项目是**多对多**关系（联合体合同、跨项目运维合同、按子项目拆分的主合同+补充协议、同一子项目被多份合同覆盖等 8 类场景）。存在 4 个盲区：1) 合同跨子项目时 ATOM 无处安放；2) 合同覆盖整个项目集时缺 `portfolio/requirements/` 目录；3) 子项目被多合同覆盖时 scope 判定混乱；4) 用户以合同为视角提问时 AI 不知去哪个子项目搜。此外 CR-001 遗留脚本缺口：项目集模式初始化/迁移不建子项目级 RI 骨架与 source-type-registry，SKILL.md §4 事实源表漏列 RI 文件。

## Non-goals

本次明确不做：
- 向量数据库检索工程部署（P2，仅预留）。
- 独立合同管理模块（台账/履约/付款）——合同仅作 RI 检索锚点与存储分界，不改变合同管理基本盘。
- 修改 08 号概念域 B 枚举（不加 `contract_scope`）；合同范围变更复用既有 `scope`/`cost`/`requirement` 类型。
- 修改 scope_scope 既有 5 值枚举（新增伴随字段 contract_refs，不改枚举）。
- 项目集模式下将登记册复制到子项目（唯一登记册在 portfolio/requirements/）。

## Acceptance Criteria

1. 项目集模式下可新建 `portfolio/requirements/`（canonical/atoms/source-type-registry + contract-register），子项目级 RI 骨架与 source-type-registry 在初始化/迁移中补齐。
2. 用户指定合同查询时，按 contract-register 的 scope_level 路由到 portfolio 级或对应子项目 canonical，返回 `scope_scope(result)` + `contract_refs` + 证据链；多合同覆盖逐合同列结论。
3. supplement（补充协议）的 ATOM/Canonical 存储与检索经 `parent_contract_id` 回溯跟随父合同 scope_level。
4. contract-register 为空时，RI 查询触发补录引导（最小字段：ID/名称/scope_level/覆盖/status），不返回臆造结论。
5. schema 0.8.0 迁移：新建 portfolio/requirements + sub_project_dirs/sub_project_files（含 D10 守卫，仅对含 requirements/ 的子项目补齐），不动既有事实源数据。
6. 合同范围变更（拆分/扩大/缩小）走 08 号既有类型升级记录，contract-register 维护 status/superseded_by 血缘，ATOM 相关条目熵 stale 判定，Canonical 触发 scope 重判。

### AP-3. 变更策略与设计思路

1. 为什么选择这个方案：扩展现有 07/05/06/09/18 规则并复用 RI 三层模型，而非另起"合同管理模块"；contract-register 做 RI 的检索锚点与存储分界，最小侵入。
2. 设计思路：契约层 D1(scope_scope 5 值枚举+伴随字段 contract_refs)、D2(Canonical storage_level 跨层归 portfolio)、D3(单项目多合同复用 requirements/contract-register+coverage 列)、D4(项目集登记册唯一在 portfolio/requirements/)、D5(空登记册补录引导)、D7(supplement 跟随父合同 scope_level，parent_contract_id 回溯)、D8(合同变更不改 08 号，复用 scope/cost/requirement)、D9(迁移前向修复)、D10(子项目遍历守卫仅对含 requirements/ 的子项目)。
3. 关键决策点：不改 08 号概念域 B（A 裁决）；supplement 跟随父合同（回到用户原始设计）；sub_project_files 机制解决迁移文件缺口（E 裁决）。
4. 与现有规则的交互关系：00 号意图、05 号查询、06 号文件、07 号 §8a、08 号（零侵入仅被引用）、09 号层级职责、14 号自查、18 号向导、16/20 号治理与迁移。
5. 替代方案对比（被否决）：(a) 独立合同管理模块——与 RI 数据割裂、膨胀风险高，否决；(b) 修改 08 号概念域 B 新增 contract_scope——与 `scope` 语义重叠且破坏封闭枚举，否决。
