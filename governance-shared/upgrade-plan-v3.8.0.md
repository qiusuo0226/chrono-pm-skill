## 2. 原始需求照抄

> （1）以下两份能力，应该还是项目集skill的聚合能力吧，应该不是在project单项目skill中的能力
> Skill 里唯一的跨项目引用模式是：
> 合同去重（V-8）：用簇固定号 + fingerprint 去重，同一份源文档的拆解产物存在 requirements/sources/{簇ID}/，各项目 contract-register 通过簇 ID 关联。但这是合同/源文档专用的。
> 共享人力（V-3）：shared-resource-index 只存姓名 + 参与项目指针，不存内容。
>
> （2）按照我的拆分设计，首先项目集经理或者项目组合经理或者公司，用的是ChronoPM-Portfolio-Skill，而每个项目的项目经理用的是ChronoPM-Project-Skill，项目经理才是直接操作数据源的人，项目集经理只会归档检索。整体调控进度。所以按照我现在的skill架构设计思路，在遇到这种项目集模式的时候，首先ai想到的就是当前操作这个文件夹的人是项目集经理，然后要问这个文件拆了以后放哪儿，是各个项目都放一份（只拆一次，其他拷贝，拷贝的时候要注意文件索引可能要进行增加，因为三个项目可能存在文件相同或不相同的情况，文件索引是可能不一样的），各放一份作为默认推荐（这很重要重点设计）。不主动说用指针关联。
>
> （3）看一下你现在skill设计的术语，词库这些都指向一个文件吗，是怎么设计的，如果文档更新术语可能再拆一遍，用了不同的ai，拆解能力不同。你是怎么考虑的

| 对内留痕 | 助手自己 / 以后查账 | 路径、内部编号、检查项 | **不要**。人问「改了哪些文件」再给 |

#### 3.5a.2 什么可以问人，什么不准问人

**可以问（业务拍板）**：这份东西算哪个项目的？跟合同哪一块对应？这条风险能不能关？

**不准问（助手自己定）**：内部编号叫什么、文件放哪、要不要写索引、用户已用白话说清的事再翻译成内部术语反问一遍

#### 3.5a.3 「请你确认」只有两种意思

| 对外怎么说 | 实际含义 | 人要做什么 |
|---|---|---|
| **我已经记下了，请你认不认** | 低/中风险：助手先写了，等点头才算数 | 回「认」或「不认，改成…」 |
| **我还没动，请你准不准我做** | 高风险 / 下一步动作 | 回「做」或「先不做」 |

禁止再用「建议更新清单」当标题面对用户。对外可用标题：
- 「请你拍板」——需要选项的
- 「我记下了这些，请你认一下」——已经写了等点头的

#### 3.5a.4 每一问的形状（人不用翻上文就能回）

```
N. [一句话背景，用项目里的词]
   我建议：……
   你回这个编号即可：
   A. ……（选了之后我会……）
   B. ……（选了之后我会……）
   C. 先放着，这题以后再说
```

硬规则：
1. 同一轮问完，不拆多轮 captcha
2. 每题 2～4 个选项；必须写清选了助手会做什么
3. 末尾给回复模板：`1A；2B；3C`
4. 用户已经拍过的板，不得再问
5. 编号系统、路径、内部工序名出现在对外提问里 = 本条失败

#### 3.5a.5 实施落点（确认需求后再改）

| 文件 | 改什么 |
|---|---|
| `00-pm-main-rules.md` §5.3/§5.4/§8a.2/§8b.3 | 「建议更新清单」改为对内；对外改「请你拍板」；级联完整性不对用户展示 |

#### 3.5a.6 验收标准

找一个没读过规则的人看对外回复，必须能：
1. 说出自己要做的事：回编号，不用改文件
2. 区分「已经记下了请点头」和「还没做请准许」
3. 不遇到：簇、ATOM、Canonical、六件套、D24、级联、Target File、source_type、指纹、首拆
4. 用 `1A；2B` 能一次答完；漏答的题保持未决，助手不得猜

### 7.4 关键设计决策

#### 7.4.1 "各放一份" vs "指针关联"

**决策**：默认推荐"各放一份"。

**理由**：
1. 符合 ChronoPM 核心理念——每个项目是独立自足的管理单元
2. PM 是直接操作数据源的人，不应依赖外部指针
3. 各项目索引天然独立，各放一份后索引更新互不干扰
4. 后续各项目可能演化出差异，独立副本更灵活

**不推荐指针的原因**：
1. Portfolio 对成员项目只读，指针需 Project 侧配合
2. 当前无通用"跨项目文件引用"机制
3. 指针增加 PM 认知负担

#### 7.4.2 索引差异处理

拆分时 AI 检查各项目目标索引，为每个项目生成**该项目专属的索引更新建议**：

- 项目 A 的 requirement-register 已有 REQ-A001~A010 → 新增 REQ-A011~A015
- 项目 B 的 requirement-register 已有 REQ-B001~B05 → 新增 REQ-B006~B010
- 项目 C 尚未建 register → 需先创建

#### 7.4.3 与只读契约的关系

V-11 不突破只读契约。Portfolio 只输出 V-9 建议更新清单，不直接写入成员项目。

用户明确要求“直接写入”时（B3-6：删除「坚持可写」分支）：
1. 提醒：Portfolio 设计为只读，请切换到对应项目的 Project 对话执行
2. Portfolio 不代写：最多输出对内 V-9 清单供 PM 在 Project 侧执行；用户坚持也不写成员项目（只读契约写死不改，见 §6.3）
3. 联邦根目录加载的是 Project 技能时（市监仓即此结构）：一份文件要进多个成员项目 → 提示换 Portfolio 对话拆分，禁止本包当集经理代写完成（落点：Project SKILL.md，见 §9）

### 7.5 需求五详细设计：人员文件整合

#### 7.5.1 花名册=索引同文件拆段（V0.12 用户追问收口：不是新源）

**用户原话要的东西**：个人待办 md + **索引文件**就能替代 register；「如果 index 里有完整清单，就不会漏扫」。

**花名册不是此次新发明的第三份文件。** 它就是现行 `todos/{date}/_index.md` 里多出来的一节。现行 `_index.md` §1 只列「今天实际有文件的人」，所以结转会漏掉在组但不干活的人——修法是把**同一份 index**拆成两节，不是再维护一份名单。

| | 落点 | 写还是派生 | 权威？ |
|---|---|---|---|
| 在组名单（口语「花名册」） | 最新合法日 `_index.md` **§1** | **唯一写入点**（进组/出组/空闲/同时参与只改这里） | 是。全员名录只此一份 |
| 当日参与 | 同文件 **§3**（**现行 §1 改名并后移**，不与现行 §3 撞号） | **派生**：当天有哪些人的 md 就有哪些行。丢了可以扫目录重建 | 否 |
| 个人 §0 | `todos/{date}/{姓名}.md` | **只留联系方式、负责模块**（T+1 拷贝）。岗位 / 首次进组 / 在组状态 **不在此段**，一律读 §1（N-41） | 否 |
| TD 缩写 | 同份 `_index.md` 的 §TD 缩写映射 | 唯一写入点 | 是 |

**禁止**：另建 `花名册.md` / 继续用 register 当平行源 / 把 §0 的岗位或在组状态当可编辑权威。统一用词「岗位」，花名册与 §0 都不得写「角色」。

**如何避免同步失败**：不是「两份名单对敲」，是「一份名单 + 若干派生」。

1. **最新合法 index** = `todos/` 下 `date≤今天` 且存在 `_index.md` 的最大日期（未来目录不算，见 §7.5.5）。
2. 新建「今天」的 `_index.md` 时：§1 从上一合法日 **整表拷贝**，再按当天进出组改几行；§3 按当天实际生成的个人文件列出。
3. 历史日的 §1 是当天快照，**禁止回头改**（改在组状态只写今天的 §1）。
4. 个人文件可以没有（销售/QA 空窗）——他们只出现在 §1，不出现在 §3，这是正常子集，不是不一致。
5. 自查断言：新 §3 的每个人必须能在 §1 找到；新 §3 的 File Ref 必须磁盘上存在；§1 有、§3 无 = 今天没派活，合法。

**§1 列（7 列满额）**：姓名 | 缩写 | **岗位** | 状态（在岗/空闲/请假/借出/待进场/已出组） | 首次进组 | 分配方式 | 备注（同时参与/B角/离场日原因/不派活编制）。岗位是全员主表，无待办的人也有岗位。

**完整新节序（B6-1，对照现行模板，禁止撞号）**：

| 新节 | 来源 | 写/派生 |
|---|---|---|
| §1 在组名单 | **新增** | 写（唯一全员名录，含岗位） |
| §2 结转追溯标记 | 现行 §2，不动 | 写（结转状态机） |
| §3 当日参与 | **现行 §1 整表后移** | 派生（当天个人文件） |
| §4 当日待办概览 | **现行 §3 后移** | 派生（当天待办行） |
| §5 共享人力提示 | **现行 §4 后移** | 派生/提示 |
| **§6 TD 缩写映射** | **新增**。位置钉死：§5 之后、Revision Log 之前，禁止放别处 | 写 |

现行模板 §1 注释「缩写必须抄自 resource-register…不一致以 register 为准」**翻转为**：缩写抄自本文件 §TD 映射，冲突 ASK。

**§3 列**：维持现行七列（Owner/缩写/File Ref/Todo Count/来源/Generated At/备注）。

#### 7.5.3 人员空闲检测 + 提醒台账机制（Q-B1 拍板，重写）

**用户拍板逻辑**：
- 原本有待办没做完 → 结转（现有机制，不变）
- 没待办（之前结转的都已完结且没安排新工作）且无日报 → **不直接标出组**，标「空闲」状态 + 提醒 PM：派任务还是标离组
- 出组是终态，必须 PM 点头才写（符合「离场须确认」现行分级）

**检测流程（Step 0.8，嵌入结转）**：
0. **检测对象范围（B4-4 收窄）**：仅扫「曾被派过活」的在岗人员——即曾有过待办文件、或曾出现在某日 §3 当日参与表的人。**从未派活的编制**（如销售/QA 只在 register 在岗、从无待办）保持在岗（可备注「不派活编制」），不进空闲台账——Q-B1 管的是「原来有活、突然没活」，不是从未有活的人
1. 扫描 §1 在组花名册中状态=“在岗”且命中上述范围的人员
2. 分三种情况：
   - 有未办结待办 → 正常结转（不管有无日报）
   - 有时间线内待办但无日报 → 催缴提醒（仅输出，不写文件，B 审核已确认此项）
   - 无任何时间线内待办且无日报 → 标「空闲」 + 登记提醒台账
3. 标空闲动作：更新 §1 花名册该人状态=“空闲”（非终态，随时可回“在岗”）
4. 登记提醒：写入 pending-changes（类型=人员状态提醒），内容含姓名/空闲起始日/二选一选项
5. 输出白话提醒（需求六格式）：「{姓名} 手头没有任务也没写日报，已标为空闲。A. 给他派活；B. 他已离组，记一笔；C. 先放着」

**提醒及时性专项设计（用户：之前强化几轮效果不明显，重新想方案）**：

**根因分析（为什么之前提醒没效果）**：
1. 提醒只是一次性对话文本，会话结束即丢失，无法跨会话追踪
2. 提醒未落入任何持久化结构，新会话看不到历史提醒，不会追问
3. 提醒混在大量其他输出中（如「存在 N 项待确认」横幅），容易被淹没
4. 没有升级机制：提醒没人理也不会变响

**新机制：持久台账 + 入口强制呈现 + 闭环消除 + 逐级升级**：

| 环节 | 设计 |
|---|---|
| 落点 | 复用 pending-changes.md（已有持久事实源 + 每轮开头强制呈现机制），新增类型=「人员状态提醒」；不新建台账文件（符合「减少同步更新点」原则） |
| 呈现 | 每轮对话入口（任何触发）检查未处理的提醒 → 白话置顶输出（N-24 横幅改造后不再被淹没）；与今天事项分开呈现 |
| 闭环 | PM 回复 A（派活）→ 落待办 + 状态回“在岗” + 提醒消账；回复 B（离组）→ 有待办文件的人写个人 §0.5 出组记录（无此段则补上），无待办文件的人只记花名册（状态=已出组 + 备注离场日/原因），再提醒消账（B4-1）；回复 C（放着）→ 保留台账，次日再提 |
| 升级 | 同一提醒连续 3 天未处理 → 提示升级：在周报中单列「人员待安排」段；连续 7 天 → 建议登记风险（人力的浪费/遗忘安排风险） |
| 防误伤 | 进组第一天、节假日/周末不触发（读 project-context 工作日历）；「空闲」只是提醒信号，不影响任何已有数据 |

> **为什么这次会有效**：之前提醒失败的核心是「说了就忘」；本机制把提醒变成 pending-changes 台账条目，每轮入口强制检查、不处理不消账，与「待确认变更」共享同一条强制呈现通道。这是把「提醒」从建议升级为带状态的待办。

#### 7.5.4 归档/备份双概念详细设计（V0.11 用户新建概念，取代 V0.10 全禁口径）

#### 7.5.5 禁止提前建未来日待办 + 休息日/最新 index（V0.12，用户截图实证）

**实证（全链通，2026-08-22）**：用户在日报里写「明日都是指周末也就是 8-23」，本意是解释「明日」二字。AI 把 8-21 日报入档后，**新建了 `todos/2026-08-23/`**（何敏/王涛/燕彤三人 + 残缺 `_index`，`carryover_done_for_today=部分`）。`todos/2026-08-22/` 不存在。根因：现行 01 号 §5.6 + 00 WF-8「明日计划必须落待办文件」——AI 把落库日期理解成了「明日」那天。

**这会弄坏「最新 index」**：结转/花名册都依赖最新 `_index.md`。未来目录一旦存在且人不全，扫描名单会缩成那几个人，休息日有人上班时 22 号 index 与 23 号也对不上。

**硬规则（写入 01/00/22/14）**：

1. **禁止创建 `date > 今天` 的 `todos/{date}/`**（今天=工作日历的当天；PM 说「现在开始记某日当天的待办」且该日≤今天才可建）。
2. 日报只写入**当天**个人文件：§2 存档原文（含「明日」段）+ 按「今日完成/进度」改**当天**核心表状态。明日计划**不**在今天新建待办、**不**建未来目录。
3. 改 01 §5.6 / WF-8：明日计划/本周计划 → 只留在今日 §2。次日第一次写待办时 Step 0 全员结转，再用 §6.2「昨日明日计划 vs 今日完成」拉齐；那时才允许把昨日明日计划里的新任务建成**次日**待办。
4. **最新 index** = `{date | date≤今天 且存在 _index.md}` 的最大值。`date>今天` 的目录视为非法，不参与最新判定、不进结转扫描名单。
5. **休息日**：
   - 工作日历休息且无人提交日报/待办 → **不建该日目录**（现行「无 _index 则跳过该日历日」）。
   - 休息日有人上班 → 只为实际上班的人建个人 md；当天 `_index` §1 从上一合法日拷贝**全员**，§3 只有上班者。下一天仍用这份全员 §1 扫描，不会因为「只有部分人有文件」丢掉其他人。
6. **存量未来目录**（如此次 8-23）：自查列出。PM 确认后删除。从旧编号结转过去的行丢弃（真结转应在那天做）。仅存在于未来日的新 TD（如 `TD-王涛-20260823-001`）先回写到最新合法日该人 §2「明日计划」再删目录。禁止把残缺未来 index 补成「全量结转」来将错就错。

#### 7.5.6 个人待办创建契机（N-43，if-else；用户强调只定契机）

这是把现行 22 号「时机 0」写成硬入口，堵住「只给日报点到的三个人建当天目录」：

```
IF 本次操作触及 todos/{今天}/{任何人}.md  或  今天的 _index.md：
    IF 今天不是工作日历的「今天」（date>今天）：
        拒绝创建/写入该日期目录（N-37）
        把内容落到合法当天文件（日报「明日」进当天 §2）
    ELSE IF 今天 _index.md 不存在
         OR carryover_done_for_today 不是 true（含缺省、false、「部分」等非法值）：
        先做 Step 0（全员，读上一合法日 §1）
            该起链的人：有未办结待办 / 当日有日报或能耗投喂 / 当天被点名操作
                → 建或补个人 md + 写入新 §3
            不起链的人：从未派活编制、已出组、空闲且无未办结
                → 只留在 §1，不建空文件
        写 carryover_done_for_today=true（成功或「失败留待明日」都算本次 Step 0 做完）
        再检查：index 在、标记是 true
        THEN 才改点名的那个人
    ELSE：
        今天结转已完成 → 直接改点名的那个人（可追加到已有文件）
ELSE：
    没操作个人待办类文件 → 不触发（查进度、出周报等不因此建目录）
```

「都创建」= 花名册里**该起链的人都建**，不是给销售/已出组建空壳。结转怎么搬行仍按 22 号，这里只钉**何时必须先全员建**。8-23 那种 `carryover_done_for_today=部分` 视为没完成，下次一碰当天待办就要补全 Step 0（若该日已是「今天」）；若该日仍是未来，则按 N-37 当非法目录处理。

#### 7.5.7 兼容人工成本台账（N-44；用户（23）（24））

**兼容原则（硬，施工不得破）**

2. 单位只读该项目 `project-context`「人工计量单位」。未登记标「待登记」并持续提醒，禁止猜测（沿用 R14）。
3. ChronoPM **内部唯一事实源** = 该人最新待办文件 §0.6。外部工时表 / 日志系统 / 粘贴表格 = 投喂源，投完不保留为平行权威。同一自然日再投喂 = **覆盖该日**（幂等），累计按明细重算。
4. §0.6 = 填报消耗（成本台账）；§1.2 = 待办预估/实际工时。两套概念 **禁止合并、禁止互推**。能效用 §0.6 作成本、§1/§3 作工作。
5. **A 拍板（数字来源护栏）**：① 已填成本核算方式 → 按该单位/默认规则/可选公式记账。② 未填 → PM 对话里提到人工成本/能耗/填报量就记入 §0.6，来源写「PM 口述」或「对话检出」，记 PM 用的口径，单位可标「待登记」。③ 人工改已有行必须改「来源」列。④ AI 禁止凭空编造数字。⑤ 与公司工时系统对账由 PM 负责，AI 不对接、不对账。
6. **B 拍板（不建历史）**：新待办从该人最新文件 **整表拷贝 §0.6 再追加**当日行。历史日个人 md **不回写**。禁止为回填建历史空目录。PM 投喂含过去日期 → 只在**当前最新文件**的日表追加日期行。升级执行不灌任何一家历史表。

**结构：一层必有，一层按需，金额不落表**

必有（所有公司，4 列，不扩列）：

```
累计总能耗：N [能耗单位]（截至 YYYY-MM-DD）

| 日期 | 当日能耗 | 来源 | 备注 |
```

T+1：明细整段复制；当天还没有行则追加；累计按日表重算。查询统计 **只读该人最新文件**。

按需（**禁止空表占位**）：仅当本次投喂「同一人同一自然日 >1 行」，或时间粒度细于日期，才出现「分次明细」小节（5 列，H-7 内）：

```
| 日期 | 填报时间 | 当次量 | 外部任务/内容 | 关联 TD |
```

- 当日能耗 = 该日各次 SUM（用户「同一天加起来」的通用化）。
- 只有日合计的公司：**永不出现**此小节。
- 填报时间：有时刻留时刻，只有日期就写日期。
- 关联 TD 默认 `—`。PM 指定、或当日唯一待办且 PM 确认，才写 TD 号；对不上标「待归属」。**禁止 AI 猜绑。**
- 「外部任务/内容」抄投喂表，**不覆盖** §1 待办标题。

金额：§0.6 **永不加金额列**（兼容无单价/涉密单价的公司）。查询时若 project-context 已有成本单价，才临时算「能耗 × 单价」并标注公式；单价空则只出能耗单位。

**能效：默认按日并置，不强迫分摊到任务**

问「某人成本 / 能耗 / 损耗 / 能效 / 做了什么花了多少」：

1. 读该人最新文件 §0.6（累计 + 日表 + 若有分次）。
2. 按日期并置同一天 §1 待办 + §3 工作日志。

## 8. 需求三分析：词库跨项目一致性（用户要求详细描述，已展开）

### 8.0 这个词库是干什么的（白话解释）

**词库 = 项目自己的「黑话翻译本」**。每个项目里都有一些业务专有名词（比如「全链通」「信用监管」「两法衔接」），还有同一东西的不同叫法（比如有人写「企信码」有人写「企业码」，指的是同一个东西）。

AI 处理文件时靠这本「翻译本」统一叫法：
- 看到「企业码」→ 自动归一为词库里确认的标准名「企信码」
- 遇到没见过的新词 → 登记为「候选」，等你确认它是什么意思、标准名叫什么
- 你确认后 → 以后所有文件都自动用标准名，不会再各叫各的

**需求三要解决的问题**：你现在三个项目各有一本独立的翻译本，互相不通气。V-11 把一份共享文件拆到三个项目后，三个项目的 AI 各拿各的翻译本处理，可能出现：同一个词在项目 A 归一成 X，在项目 B 归一成 Y——同一个东西在三个项目里叫法不一致。

### 8.1 现状

| 维度 | 当前设计 |
|------|----------|
| 存储 | 每项目独立 `ai/context/domain-glossary.md` |
| Portfolio 层 | 无词库 |
| 跨项目共享 | 无机制 |

### 8.2 问题

共享文件拆分到三个项目后：
1. 不同 AI 做拆解 → 术语归一化结果可能不一致
2. 词库独立演化 → 项目 A 确认了某术语，项目 B 可能还没发现
3. 拆解能力差异 → 不同 AI 拆解粒度不同

### 8.3 已有缓解机制（为什么之前判定可以先不做）

- 17 号 §1.4 拆解术语节流：证据留 facts.md，词库只收候选指针
- pending→confirmed 状态机：PM 可跨项目统一确认（你在项目 A 确认过的词，到项目 B 再确认一遍即可对齐）
- confirmed 静默替换：一旦确认，后续自动归一

### 8.4 跨项目机制设计（V0.5 重写：用户纠正主场景为自下而上归集）

**用户纠正的主场景**：一个项目经理 = 一个项目 = 一个业务 ai 库；后续 PM 把 ai 目录打包发给项目集经理，集经理放到自己 projects/ 下；**Portfolio skill 要自己识别新项目 ai 库里的术语，补充项目集层面的术语索引指针**。不是默认集经理在集层拆文件往下发种子。

**主推方案 B′：Portfolio 层术语指针索引（自下而上，与 V-3 人员聚合同构）**：

| 环节 | 设计 |
|---|---|
| 触发 | 新项目挂载（V-1 登记）时自动扫描；或集经理说「刷新术语索引」按需重建 |
| 动作 | Portfolio 只读成员项目 `context/domain-glossary.md` → 抽取 confirmed 条目（pending 不收录，避免把未确认的词带上集层） |
| 落点 | Portfolio 层新增术语指针索引文件（如 `portfolio/context/glossary-index.md`）：术语 | 标准词 | 出现项目 | 各项目条目编号（G-号）指针。≤7 列 |
| 边界 | **只存指针不存全文**；不写任何成员项目词库（只读契约）；索引是加速器，事实以各项目词库为准 |
| 漂移提示 | 同一原词在 A 项目确认成 X、B 项目确认成 Y → 输出对齐建议（SUGGEST），不代改（同 V-3 漂移处理模式） |
| 查询 | 集层查词：读索引 → 返回各项目的标准词与确认状态；查不到再按指针去项目词库取证 |
| 刷新 | 项目词库更新后索引可能滞后：查询命中指针后校验目标条目仍存在；不存在则标 stale 并提示刷新（懒刷新，不定时扫描） |
