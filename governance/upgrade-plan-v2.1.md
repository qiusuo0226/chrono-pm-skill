## 1. 需求总览

### 需求一：内置 PM 管理习惯

在 PM Profile 模板中预填内置默认 PM 管理习惯，作为 AI 出厂行为基线。
- 内置编号体系与 PM 自定义编号体系完全隔离
- 去除 PF003（日报核对联动提醒）和 PF004（日报梳理主动提问）不作为内置默认
- 最终 6 条内置默认

### 需求二：个人待办文件增加人员身份信息 + resource-register 保留并简化

- 6 个字段（岗位、姓名、联系方式、负责模块、进组日期、离组日期）加在 `personal-daily-todo-template.md` §0
- §0 与 resource-register 是**不同维度**，互补而非替代：
  - §0 = 该人今天的身份快照（随待办 T+1，每人每日文件携带）
  - resource-register = 项目集层人员资源全景（参与项目/分配方式/B角/状态/风险等级），PM 跨项目看人唯一入口
- resource-register 保留，不删除
- 审查并清理冗余结构

### 需求三：目录结构简化

- `outputs/` 移入 `ai/` 下，保证工作区根目录只留一个 `ai/` 顶层目录
- `continuity/` 目录合并入 `context/`（4 个文件：carryover-register/import-log/legacy-sources/project-lineage）
- 不新建月报模板（月报 = 周报整合，不需要独立模板）
- 注意：子项目下无 `resources/` 目录（仅 portfolio 层有），无需处理子项目 resources/ 消除

### 需求四：v1 残留清理

v2.0.0 升级后工作区存在大量 v1 遗留文件/目录，新老结构混杂。全面扫描并清理：

### 需求五：AI 行为约束强化——日报落点强制规则 + 执行前自检机制

**问题背景**：v2.0.0 升级后，规则文件（01-daily-report-rules.md §1.2）已明确"不再创建独立个人日报文件，汇报写入待办文件工作日志段"，但 AI 实际行为仍在往旧路径 `reports/daily/personal/` 写文件（**案例来源**：2026-08-18 用户日报记录操作，AI 在 `reports/daily/personal/2026/08/` 下创建了 08-17 文件，而非 `todos/2026-08-17/`；该案例发生在用户实际工作环境中，方案制定时基于用户描述），导致新老路径并存、数据分散。

> **注**：Agent B V0.7 审查指出当前工作区实测无 08-17 新文件，可能发生在 uploads 副本或其他环境。三层防护设计本身合理（即使案例无法在此工作区复现，禁止旧路径的规则仍有价值），故保留需求五，案例依据标注来源。

**错误根因分析（2026-08-18 实际案例反思）**：

| 层级 | 根因 | 说明 |
|---|---|---|
| **直接原因** | 看到历史文件就误判 | `reports/daily/personal/2026/08/` 下有 08-03 到 08-14 的历史日报，AI 直接照着创建了 08-17 的文件 |
| **根本原因 1** | 未先读取 Skill 规则 | 用户明确要求"每次工作前必须先读取 Skill 技能文件"，但 AI 跳过了，没有读取 v2.0.0 的日报规范 |
| **根本原因 2** | 把 v1 遗留当参考 | `reports/daily/personal/` 下的文件本身就是 v1 旧体系遗留（应该被清理），AI 却把它们当作"正确格式"来参考 |
| **根本原因 3** | 未主动检查新结构 | v2.0.0 的 `todos/{date}/` 目录是空的，AI 应该意识到"这说明还没开始用新体系"，而不是退回旧模式 |
| **错误模式** | 按历史模式执行，未确认当前规则 | 典型"路径依赖"错误：看到旧文件→模仿旧格式→忽略版本升级 |

**正确做法应该是**：
1. 先读取 Skill 规则，确认 v2.0.0 日报记录到 `todos/{date}/{姓名}.md`
2. 发现 `todos/2026-08-17/` 不存在 → 主动创建
3. 按新格式生成待办文件，而不是旧日报格式

**解决方案（三层防护）**：

**第一层：禁止规则（01-daily-report-rules.md §1.2a）**
- 明确禁止写入 `reports/daily/personal/` 目录
- 明确日报必须写入 `todos/{date}/{owner}.md`（V0.38 N-a 同步：两步落点——§2 日报存档段存原文 + §3 工作日志段存加工，见需求十三）
- 若待办文件不存在，AI 必须主动创建（基于 `personal-daily-todo-template.md`）
- 违反禁止规则视为严重错误，输出中必须标注

**第二层：执行前自检规则（00-pm-main-rules.md 新增 §4a）**
- AI 在执行任何写入操作前，必须先读取并确认当前版本规则
- 自检清单：①当前 Skill 版本？②目标路径是否在允许列表中？③是否存在历史遗留文件干扰判断？
- 若检测到目标路径下存在历史文件，必须警觉"这可能是 v1 遗留，需先确认规则"

**第三层：路径校验规则（06-file-rules.md）**
- 在文件路径表中明确标注 `reports/daily/personal/` 为"已废弃，禁止写入"
- 增加路径校验规则：AI 写入前必须检查目标路径是否在允许列表中
- 增加"历史遗留文件识别"规则：若路径下存在大量按日期排列的历史文件，AI 应怀疑这是旧体系遗留

**工作区清理配合**：
- 需求四的归档操作完成后，旧路径下不再有活跃文件
- 归档目录加 `.archived` 后缀或 README 说明，避免 AI 误读

**规则原文（01-daily-report-rules.md §1.2a 新增）**：

```markdown
### 1.2a 禁止写入旧路径（v2.0.0 强制约束）

**禁止行为**：AI 不得在任何情况下将个人工作汇报写入以下旧路径：
- `reports/daily/personal/`（任何子目录层级）
- `summaries/{name}-progress.md`

**强制落点（V0.38 N-a 改写：对齐需求十三两步流程）**：个人工作汇报必须写入 `todos/{date}/{owner}.md`，两步落点：① 日报原文逐字存档到 **§2 日报存档段**（先存档，禁止只存加工摘要）；② 解析加工结果写入 **§3 工作日志段**（段结构见 `assets/templates/personal-daily-todo-template.md`），进度/问题描述按映射规则落待办字段（见 01 号需求十三两步流程与 13.1）。

**文件不存在时的处理**：若当日待办文件不存在，AI 必须：
1. 基于 `assets/templates/personal-daily-todo-template.md` 创建 `todos/{date}/{owner}.md`
2. 填写 §0 人员信息段（若已知）
3. 将日报原文存档到 §2 日报存档段，解析加工结果写入 §3 工作日志段
4. 同步更新 `todos/{date}/_index.md` 绑定文件

**违规处理**：若 AI 检测到自身即将写入旧路径，必须立即中止并输出警告：「⚠️ 违反 v2.0.0 日报落点规则，已中止写入。正确路径：todos/{date}/{owner}.md」。
```

### 需求七：计划↔待办绑定强制规则（强约束）

**问题背景**：v2.0.0 核心架构要求“个人待办任务为最小可执行单位”，但 AI 实际行为中，修改计划文件（如 dev-freeze-plan.md）时只更新了计划本身，未同步创建/更新对应的个人待办文件（`todos/{date}/{owner}.md`），导致计划任务完全脱离待办体系。

**实际案例**：PM 指示“全链通设立 安排赵东洋测试外商投资企业分支+农专分支 两个市场主体 4天 9.11-9.15”，AI 只更新了倒排计划文件，未创建/更新赵东洋的待办文件。

**根因分析**：

| 层级 | 根因 | 说明 |
|---|---|---|
| **直接原因** | 计划修改后未触发待办创建 | AI 把计划文件当作独立文档，未意识到计划中的每一项排期必须落地为待办 |
| **根本原因 1** | WF-7/WF-8 未被执行 | WF-7 落库步骤已明确“PLAN 文件 + 待办文件”，但 AI 跳过了待办文件写入 |
| **根本原因 2** | 计划模板无强制待办绑定字段 | dev-freeze-plan 等非标准计划格式没有待办 ID 列，AI 无法感知需要绑定 |
| **根本原因 3** | 缺少“计划变更→待办同步”强制规则 | 规则中 WF-7 提到写待办，但没有“修改计划时 MANDATORY 检查待办是否存在”的强制约束 |
| **错误模式** | 计划是计划、待办是待办，两套体系并行 | 典型“双轨并行”错误：计划文件成为独立于待办体系之外的“影子系统” |

**解决方案（四层强制绑定）**：

**第一层：计划模板强化（plan-template.md）**
- WP 清单表已有“下辖待办”列（TD-xxx），但需增加**强制校验规则**：
  - WP 表中每一行“下辖待办”列不得为空（若该 WP 已分配执行人）
  - 若待办尚未创建，标注“待创建”并在变更日志中记录

**第二层：非标准计划格式适配（dev-freeze-plan 等）**
- 非标准计划（如倒排计划、模块测试排期）虽不按 WP 表组织，但每个涉及具体人员+时间的排期行必须标注待办 ID
- 在文件头部增加强制声明：“本文件中所有涉及人员+时间的排期，必须同步创建/更新对应人员的待办文件”

**第三层：00 号规则新增 §4b 计划变更待办同步规则**
- AI 修改任何计划文件时，必须执行以下检查：
  1. 扫描本次变更涉及的每个人员+时间排期
  2. 检查对应人员的 `todos/{date}/{owner}.md` 是否存在
  3. 若不存在 → 创建待办文件，写入对应待办项（带 WP Ref / 计划 Ref）
  4. 若已存在 → 检查待办内容是否与计划一致（时间/范围/人员），不一致则更新
  5. 输出“计划↔待办同步报告”：列出本次新建/更新/跳过的待办数量

**第四层：WF-7/WF-8 强化**
- WF-7 落库步骤增加 MANDATORY 验证：“待办文件是否已写入”
- WF-8 增加触发入口：“计划变更产生的排期调整”（第⑥入口）

**规则原文（00-pm-main-rules.md §4b 新增）**：

```markdown
### 4b 计划变更待办同步规则（强制）

**触发条件**：AI 修改任何计划文件（plans/*.md）时，必须执行本规则。

**强制流程**：
1. 扫描本次变更涉及的所有人员+时间排期项
2. 对每个排期项，检查 `todos/{date}/{owner}.md` 是否存在
3. 不存在 → 基于模板创建，写入对应待办项（带计划 Ref）
4. 已存在 → 检查待办内容是否与计划一致，不一致则更新
5. 输出“计划↔待办同步报告”

**违规处理**：若 AI 修改了计划但未同步待办，必须在输出中明确标注「⚠️ 计划已更新，但以下人员的待办未同步：[列表]」。
```

### 需求八：待办模板表格拆分优化（解决多列 Markdown 渲染失败）

### 需求九：待办结转强制检查机制（强约束）

**问题背景**：AI 在创建某日待办文件时，只处理了 PM 指示中提到的人员（如赵东洋、胡康利），没有先读取前一天的 `_index.md` 查找所有有待办的人员，也没有检查这些人是否有未办结的待办需要结转到新一天。这导致其他人员的未办结待办“丢失”，无法被追踪。

**实际案例**：2026-08-18 AI 为赵东洋和胡康利创建待办文件时，只建了这两个人的文件。但 08/17 的 `_index.md` 中还有其他人员（如赵彧、孙竞雨、王柏森等），他们可能有未办结的待办需要结转到 08/18，AI 完全跳过了这一步。

**根因分析**：

| 层级 | 根因 | 说明 |
|---|---|---|
| **直接原因** | 创建待办时未读取前一天 `_index.md` | AI 只处理了 PM 提到的人，没有扫描前一天全员 |
| **根本原因 1** | WF-8 缺少“前置结转检查”步骤 | WF-8 的归属判定流程中没有“先查前一天 index”的强制步骤 |
| **根本原因 2** | 结转机制只有模板定义，无规则强制 | 模板有“是否结转”字段，但没有规则要求 AI 在创建新日文件时必须先执行结转 |
| **根本原因 3** | 缺少“全员扫描”概念 | AI 不知道需要扫描前一天 index 中的所有人员 |
| **错误模式** | “谁被提到就处理谁”，忽略其他人 | 典型的“被动响应”错误：只处理显式指令，不主动检查上下文 |

**解决方案（强制三步检查）**：

**第一层：WF-8 新增 Step 0（前置结转检查 + 追溯机制，HARD BLOCK）**

在 WF-8 归属判定之前，必须先执行以下步骤：

```
Step 0：前置结转检查（HARD BLOCK，任何待办创建前必须执行，未完成前禁止写入任何待办文件）

【设计目标】
- 覆盖周末/假日（昨天无 `_index.md`）
- 覆盖 AI 漏建某人文件（某人昨天无待办文件）
- 覆盖连续多天未交互
- 效率可控：通过追溯标记避免重复扫描
- 严谨性：标记更新必须满足所有条件
- **日级去重：今天第一次创建待办时执行 Step 0，后续创建直接跳过**

【追溯标记机制】

**双层设计**：全局快速路径 + 每人独立确认

1. **全局追溯标记**（`carryover_traced_until`）：
   - 含义：截至该日期，**所有人员**的结转都已确认完成
   - 作用：若此标记 = `date-1`，则今天无需执行 Step 0（快速跳过）
   - 更新条件：只有当扫描范围内**所有人员都成功结转**后才更新为 `date-1`
   - 若有任何人员结转失败，**不更新此标记**（保留旧值）

2. **每人独立结转状态表**（`carryover_status`）：
   - 每人一行：`姓名 | 最后确认日期 | 状态 | 备注`
   - 状态：`已确认` / `待处理` / `失败`
   - 作用：下次执行 Step 0 时，对每个人只扫描其"最后确认日期"+1 到昨天
   - 更新规则：每人独立更新，不受其他人影响
     - 若某人结转成功 → 更新其"最后确认日期" = `date-1`，状态 = `已确认`
     - 若某人结转失败 → 状态 = `失败`，记录警告，**不影响其他人的标记**

【增强算法】

0. **日级完成检查（最关键，AI 每次创建/更新待办文件时首先执行）**：
   - 检查今天 `todos/{date}/_index.md` 是否存在
   - 若存在且 `carryover_done_for_today` = `true` → **今天的结转已完成，跳过 Step 0**，直接执行 PM 指示
   - 若不存在或 `carryover_done_for_today` = `false` → 继续执行 Step 0

1. 读取前一天 `todos/{date-1}/_index.md`

2. 快速路径检查（历史）：
   - 若昨天 `_index.md` 的 `carryover_traced_until` = `date-1` → 所有人历史已确认，只需扫描昨天一天
   - 否则 → 按每人独立状态确定扫描范围

3. 确定每个人的扫描范围（每人独立）：
   - 读取昨天 `_index.md` 的"每人独立结转状态表"
   - 对每个人：
     a. 若状态 = `已确认`，最后确认日期 = D → 该人扫描范围 = D+1 到 `date-1`
     b. 若状态 = `待处理` 或 `失败` → 该人扫描范围 = `date-7` 到 `date-1`（回溯 7 天）
     c. 若该人不在状态表中（首次出现）→ 该人扫描范围 = `date-7` 到 `date-1`
   - 若昨天 `_index.md` 不存在：
     - 从 `date-1` 向前查找最近存在的 `_index.md`（最多找 7 天）
     - 若找到：读取其状态表，按上述规则确定每人扫描范围
     - 若找不到：所有人扫描范围 = `date-7` 到 `date-1`，输出提示「⚠️ 最近 7 天无待办记录，无法执行结转检查，本次仅创建新待办」→ 然后才能继续

4. 对扫描范围内的每一天（从早到晚），对每个需要扫描的人：
   a. 若该天 `_index.md` 存在且该人在参与人员列表中：
      i. 若该人员当天有待办文件 `todos/{day}/{姓名}.md`：
         - 扫描所有待办项，筛选状态 ≠ 已完成/已取消/已转出 的待办
         - 若有未办结待办 → 在 `todos/{date}/{姓名}.md` 中创建结转条目
      ii. 若该人员当天**无**待办文件（AI 漏建/请假）：
         - 从该天向前追溯最多 7 天，找到该人员最近的待办文件
         - 若找到：扫描未办结待办 → 结转到今天
         - 若找不到：记录该人状态 = `失败`，备注「7 天内无待办文件」
   b. 若该天 `_index.md` 不存在（周末/假日）：
      - 跳过该天（无参与人员列表，无法检查）

5. 结转条目格式：
   - **待办编号不变（硬约束，编号中的日期 = 原始安排日期，序号不变）**
   - 示例：`TD-朱宇杰-20260817-002` 结转到 08/18 后，编号仍然是 `TD-朱宇杰-20260817-002`
   - **禁止行为**：禁止将结转待办重新编号为今天的日期（如 `TD-朱宇杰-20260818-003`）
   - 开始时间 = 当天日期
   - 结束时间 = 原结束时间（若已超期则标注超期）
   - 备注区标注"结转自 {原始日期}"
   - **场景对比（AI 必须区分）**：

| 场景 | 操作 | 编号规则 | 示例 |
|---|---|---|---|
| **结转（跨天）** | 同一人，任务从昨天延续到今天 | **编号不变** | `TD-朱宇杰-20260817-002` → 今天仍为 `TD-朱宇杰-20260817-002` |
| **换人（转交）** | 任务从张三转给李四 | **生成新编号 + 溯源链** | `TD-张三 -20260817-001` → `TD-李四 -20260818-001`，溯源：`TD-张三 -20260817-001 → TD-李四 -20260818-001` |
| **新建** | 全新任务 | **新编号** | `TD-朱宇杰-20260818-001` |

> **编号硬约束适用范围（N-4 修复）**：
> “编号中的日期 = 原始安排日期”仅适用于**同人结转**场景。
> **换人（转交）是例外**：新编号中的日期 = 转交日期（如 `TD-李四 -20260818-001`），溯源链记录原始编号。

6. 更新追溯标记（每人独立）：
   - 对每个人独立更新：
     - 若该人结转成功 → 更新其"最后确认日期" = `date-1`，状态 = `已确认`
     - 若该人结转失败 → 状态 = `失败`，记录警告
   - 全局标记更新：
     - 只有当**所有人员**状态都为 `已确认` 时，才更新 `carryover_traced_until` = `date-1`
     - 若有任何人员状态为 `失败` 或 `待处理`，**不更新全局标记**

7. 输出"结转报告"：
   - 列出每个人的扫描范围
   - 列出结转了哪些人的哪些待办
   - 列出任何失败/警告（某人 7 天内无文件等）
   - 列出更新后的每人状态表

8. **写入日级完成标记（最关键）**：
   - 在 `todos/{date}/_index.md` 中设置 `carryover_done_for_today` = `true`
   - 此标记确保今天后续创建/更新任何人的待办文件时，AI 直接跳过 Step 0

> **语义澄清（N-3 修复）**：
> `carryover_done_for_today=true` 表示“今天的 Step 0 已执行完毕”，**不等于“所有人都成功结转”**。
> 若某人状态为“失败/待处理”，日级标记仍为 `true`（今天不再重试），失败留待**明日 Step 0 再处理**。
> 这是预期行为：状态机中“失败→已确认”是跨天转换，AI 不得因日级标记=true 而误判为全员成功。

> **硬阻断：Step 0 未完成前，禁止创建/写入任何待办文件。若 AI 跳过 Step 0 直接创建待办，视为严重违规。**

【AI 执行规则：状态表查找与更新时机（极其严谨）】

**1. 状态表查找时机（AI 必须按以下顺序执行，不可跳过任何步骤）**

```
时机 0（日级完成检查，每次创建/更新待办文件时首先执行）：
  → 检查今天 `todos/{date}/_index.md` 是否存在
  → 若存在且 `carryover_done_for_today` = `true` → **今天的结转已完成，跳过 Step 0**
  → 若不存在或 `carryover_done_for_today` = `false` → 继续执行时机 1

时机 1：AI 开始为日期 D 创建/更新任何待办文件时（时机 0 未跳过）
  → 必须立即读取 `todos/{D-1}/_index.md`
  → 必须定位到 §2.3 "每人独立结转状态表"
  → 若找不到 §2.3 → 视为"状态表缺失"，按错误处理规则 E1 执行
  → 若找到 §2.3 → 逐行解析，输出"状态表读取确认"：
    "已读取 {D-1} 状态表：赵东洋=已确认(08/17), 胡康利=失败(08/15), ..."
  → 必须等待 PM 确认或自动继续（若 PM 未设置确认要求）

时机 2：AI 完成所有人的结转操作后、写入任何新待办前
  → 必须再次读取 `todos/{D-1}/_index.md` 的 §2.3
  → 对比时机 1 读取的状态表，确认无并发修改
  → 若状态表被修改 → 重新从时机 1 开始
  → 若状态表未变 → 继续执行标记更新
```

**2. 状态变更规则（完整状态机）**

```
每人独立状态只有 3 种：待处理 → 已确认 / 待处理 → 失败 / 失败 → 待处理

状态转换触发条件：

┌─────────────┬─────────────────────────────────────────────┬──────────────┐
│ 当前状态    │ 触发条件                                    │ 新状态       │
─────────────┼─────────────────────────────────────────────┼──────────────┤
│ 待处理      │ 该人结转成功（找到文件+扫描未办结+写入结转） │ 已确认       │
│ 待处理      │ 该人追溯失败（7 天内无文件）                │ 失败         │
│ 已确认      │ 该人今天不在参与人员列表中                  │ 保持已确认   │
│ 已确认      │ 该人今天有待办文件但无未办结项              │ 已确认       │
│ 失败        │ PM 手动修复（补充了缺失的文件）             │ 待处理       │
│ 失败        │ AI 重新追溯成功（找到之前缺失的文件）       │ 已确认       │
└─────────────┴─────────────────────────────────────────────┴──────────────┘

全局标记转换：
- carryover_traced_until = "无" → 所有人状态都为"已确认" → 更新为 date-1
- carryover_traced_until = D → 所有人状态都为"已确认" → 更新为 date-1
- 若有任何人状态为"失败"或"待处理" → 不更新全局标记
```

**3. 标记更新时机（AI 必须在以下精确时机更新，不可提前或延后）**

```
更新时机：Step 0 的第 6 步（结转条目全部写入后、新待办创建前）

更新顺序：
1. 先更新每人独立状态表（§2.3）
2. 再检查是否所有人都是"已确认"
3. 若全是"已确认" → 更新全局标记（§2.2）
4. 写入日级完成标记：`carryover_done_for_today` = `true`（§2.1）
5. 输出"标记更新确认"：
   "已更新状态表：赵东洋→已确认(08/18), 胡康利→失败(7天内无文件)"
   "全局标记：未更新（胡康利状态为失败）"
   "日级完成标记：已设置 carryover_done_for_today = true"

禁止行为：
- 禁止在结转操作完成前更新标记
- 禁止只更新部分人的标记（必须所有人一起更新）
- 禁止在写入新待办后才更新标记（必须在写入前更新）
```

**4. 错误处理规则（AI 必须按以下规则处理异常）**

```
E1. 状态表缺失（§2.3 不存在）：
  → 输出「⚠️ {D-1} 状态表缺失，视为所有人状态=待处理，扫描范围=date-7 到 date-1」
  → 继续执行 Step 0
  → 在当天 _index.md 中创建完整的状态表（所有人初始状态=待处理）

E2. 状态表格式错误（列数不匹配/状态值非法）：
  → 输出「⚠️ {D-1} 状态表格式错误，视为所有人状态=待处理」
  → 继续执行 Step 0
  → 在当天 _index.md 中重建状态表

E3. 状态表中某人缺失（该人在 §1 参与人员表中但不在 §2.3 中）：
  → 输出「⚠️ {姓名} 不在状态表中，视为状态=待处理」
  → 为该人执行结转
  → 在状态表中新增该人行

E4. 状态表中某人多出（该人在 §2.3 中但不在 §1 参与人员表中）：
  → 输出「⚠️ {姓名} 在状态表中但不在参与人员表中，保留其状态，不执行结转」
  → 该人状态保持不变

E5. 结转操作中途失败（如文件写入错误）：
  → 输出「⚠️ {姓名} 结转操作失败，状态保持=待处理」
  → 不更新该人标记
  → 继续处理其他人
  → 在结转报告中记录失败原因
```

### 需求十三：日报存档 + 待办字段自动映射 + 进度字段（V0.36 新增）

**问题背景**（实测案例：赵维芳 2026-08-17 待办文件）：收集到的日报目前直接写入工作日志段，存在两个缺失：① 日报原文无独立存档章节，与加工后的日志混在一起；② 日报中的进度描述（如“个人独资分支机构待修复 21/今日新增 21”“总进度 80%”）不会自动映射到对应待办的字段，进度信息只能混写在备注列（实测 TD-ZWF-20260817-002 备注=“10%”）。另实测确认：当前待办表无独立进度字段。

**两步流程（先存档后映射）**：
1. **第一步：日报存档**：收集到的日报必须先在 `todos/{date}/{owner}.md` 的**独立章节（§2 日报存档）**逐字留存原文（含收集时间/来源标注），不得只存加工摘要
2. **第二步：字段映射**：从存档的日报内容中提取进度/问题描述，按标题/关键词匹配当天待办清单条目，映射到对应字段：进度百分比→“进度”列；bug 数/回归项等问题描述→备注区对应待办行；无法匹配任何待办的进展→在映射结果中标记“待归属”，由 PM 确认是否新建待办（联动安全底线 2，禁止查询/日报触发自动新建待办）

**进度字段落位（用户关注：AI 生成表格列数上限）**：进度列加入**核心执行表**（7 列 → 8 列，正好压在设计原则“核心表 ≤ 8 列”的稳定上限内）：① 进度是每日高频查看字段，属核心表定位；② 若下沉备注区会重蹈“10% 混存备注”覆辙；③ 8 列为硬上限，后续新增字段一律下沉（列预算约束已写入需求八）

**历史迁移文件标记（N-2 回应）**：§7.3.2b 迁移创建的历史待办文件（仅 §0 + 工作日志）必须带文件级标记（frontmatter `migration-source` + 标题标注“迁移归档文件，无活跃待办”），结转 Step 0 与查询路由不将其视为活跃待办来源（§1 空表本身不产生待办，标记用于降低扫描量与语义稀释）

**影响文件**（详见 §6 清单）：`personal-daily-todo-template.md`（核心表加进度列 + 新增日报存档章节）、01 号规则（日报两步流程）、05 号规则（进度查询读取路由）

### 需求十：待办查询路由强化（直接读取 + 缺失时触发结转）

**问题背景**：当用户问“查一下朱嵩的待办”时，AI 没有直接读取朱嵩今天的待办文件（`todos/2026-08-18/朱嵩.md`），而是手动扫描了 08-17、08-16 等多天的历史文件，最后才得出结论“朱嵩今日待办文件尚未创建”。这违反了 v2.0.0 的设计：查询某人待办时，应直接读取当天文件，若文件不存在则触发结转逻辑自动生成，而不是逐日扫描历史。

**AI 实际行为（错误）**：
1. 查 08-18 绑定文件 → 发现没有朱嵩
2. 查 08-17 朱嵩.md → 读取内容
3. 查 08-16 朱嵩.md → 发现是空壳
4. 综合得出结论

**正确行为应该是**：
1. 直接读取 `todos/2026-08-18/朱嵩.md`
2. 文件不存在 → 触发 Step 0 结转检查（需求九）：读 08-17 `_index.md` → 扫描朱嵩未办结待办 → 生成 08-18 朱嵩.md
3. 输出朱嵩今日待办

**根因分析**：

| 层级 | 根因 | 说明 |
|---|---|---|
| **直接原因** | 查询路由未明确“直接读取 + 缺失时触发结转” | AI 把“查某人待办”理解为“搜索该人的历史记录” |
| **根本原因 1** | Quick Query 路由表“某人的任务”行描述模糊 | 只说“按 Owner 筛选”，没说“先读今天，缺失时触发结转” |
| **根本原因 2** | 查询与结转逻辑脱节 | 需求九的 Step 0 是创建待办时触发，但查询时也应触发（查询即服务） |
| **根本原因 3** | AI 默认“查询=只读”，不知道“查询可触发写入” | AI 认为查询不应修改文件，但 v2.0.0 设计是“查询缺失时自动补全” |
| **错误模式** | “搜索历史”而非“读取今天 + 自动生成” | 典型的“被动查询”错误：只读已有数据，不主动补全缺失 |

**解决方案（查询即服务）**：

**第一层：Quick Query 路由表“某人的任务”行重写**

当前：
```
| 某人的任务 | `projects/*/todos/{date}/{owner}.md` 待办文件（按 Owner） | 绑定文件 `_index.md` 定位参与日期 | 逐日扫描该人日报 |
```

改为：
```
| 某人的任务 | **直接读取** `todos/{today}/{owner}.md`；若文件不存在 → **触发 Step 0 结转检查**（读前一天 `_index.md` → 扫描未办结待办 → 生成今天文件）→ 读取生成后的文件 | 绑定文件 `_index.md`（仅用于确认当天有哪些人） | 逐日扫描该人历史待办（除非用户明确问“历史”） |
```

**第二层：05 号规则新增 §2.5a 待办查询即服务规则**

```markdown
### 2.5a 待办查询即服务规则（MANDATORY）

**触发条件**：用户查询某人的待办（如“查一下朱嵩的待办”“张三今天在做什么”）。

**强制流程**：
1. **直接读取** `todos/{today}/{owner}.md`（今天 = 当前日期）
2. 若文件存在 → 直接输出待办内容
3. 若文件不存在 → **触发 Step 0 结转检查**（需求九 §4c）：
   a. 读前一天 `todos/{date-1}/_index.md`
   b. 扫描该人前一天的未办结待办
   c. 生成 `todos/{today}/{owner}.md`（写入结转待办）
   d. 输出“已自动生成今日待办文件（结转自 {date-1}）” + 待办内容
4. **禁止**：逐日扫描该人的历史待办文件（除非用户明确问“朱嵩上周的待办”“朱嵩历史任务”）

**违规处理**：若 AI 逐日扫描历史文件而非直接读取今天文件，必须在输出中标注「⚠️ 查询路径错误：应直接读取今天文件，而非扫描历史」。

**安全底线 2 约束（V0.35 补充）**：查询触发的结转生成属于“查询触发的事实源写入”，必须满足：
1. 生成的文件头部标注 `[来源: 查询触发结转（自动生成），结转自 {date-1}]`
2. 查询输出中明确告知“今日文件不存在，已自动生成结转”，并提示 PM 确认
3. PM 明确否认（如“此人今日休假/已离组”）→ 删除生成的文件，并在 `_index.md` 记录否认原因
```

**第三层：05 号规则 §6.3 快捷查询文件映射更新**

当前：
```
| 待办查询 | `todos/{date}/` 待办文件；可辅读绑定文件 `_index.md` | 不读 SKILL.md、不读 01-daily-report-rules |
```

改为：
```
| 待办查询 | **直接读取** `todos/{today}/{owner}.md`；若不存在 → **触发结转生成**（见 §2.5a） | 不读 SKILL.md、不读 01-daily-report-rules、**不扫描历史待办** |
```

**影响文件**：
| 文件 | 操作 | 内容 |
|---|---|---|
| `references/05-query-rules.md` | 修改 | Quick Query 路由表“某人的任务”行重写；新增 §2.5a 待办查询即服务规则；§6.3 快捷查询文件映射更新 |

### 需求十一明细：升级执行文件机制（拆分 + 信息源收拢）（⚠️ V0.37 P1-M 更名：与总览段需求十一去重）

**问题背景**：Skill 版本/升级/迁移信息当前散落在至少 12 处，存在三处各自描述“每版本改了什么”但只覆盖一个维度的问题。

**当前版本信息散落位置全景**：

| # | 文件 | 内容 | 当前角色 | 问题 |
|---|---|---|---|---|
| 1 | `VERSION` | 当前版本号 | 派生触点 | 无问题（sync_version.py 同步） |
| 2 | `skill.json` → `version` | 当前版本号 | 派生触点 | 无问题 |
| 3 | `skill.json` → `schemaVersion` | Schema 版本 | 派生触点 | 无问题 |
| 4 | `skill.json` → `versionHistory[]` | 每版本摘要（40+ 条目） | 信息源 | **与 #7、#9 重复描述** |
| 5 | `skill.json` → `migrations[]` | Schema 迁移描述 | 信息源 | 只描述 schema 级迁移 |
| 6 | `scripts/_version.py` | SKILL_VERSION + SCHEMA_VERSION | 脚本单一源 | 无问题 |
| 7 | `scripts/migrate_workspace.py` → `VERSION_CAPABILITIES` | 每版本新增目录/文件 | 信息源 | **只记录新增，不记录删除/修改/规则变更** |
| 8 | `scripts/migrate_workspace.py` → `template_map` | 文件→模板映射 | 运行时数据 | 与升级无关 |
| 9 | `CHANGELOG.md` | 每版本详细变更 | 信息源 | **与 #4、#7 重复描述** |
| 10 | `SKILL.md` → frontmatter | version + schema_version | 派生触点 | 无问题 |
| 11 | `references/20-workspace-version-rules.md` | 版本检测规则 | 规则 | 规则本身无问题 |
| 12 | `governance/review-checklists/release-checklist.md` | 发布检查 | 流程 | 缺升级步骤检查 |

**核心问题**：
- **#4 versionHistory + #7 VERSION_CAPABILITIES + #9 CHANGELOG.md** 三处都在描述“每个版本改了什么”，但各自只覆盖一个维度（摘要/新增目录/详细变更）
- 升级步骤分散在 `migrate_workspace.py` 代码中，不可被 AI 直接读取执行
- 版本链有断点（VERSION_CAPABILITIES 缺漏 **29 个**；早期口径“5 个断点版本”已过时，完整清单见 §6 清单 migrate_workspace.py 行；V0.38 N-b 更正）
- 如果再加一个 migration-playbook.md 单文件，又会变成第 13 个维护点

**根因分析**：

| 层级 | 根因 | 说明 |
|---|---|---|
| **直接原因** | 无统一的“每版本升级步骤”权威源 | 三个文件各自描述但都不完整 |
| **根本原因 1** | 信息散落无收拢 | 没有明确“谁是谁的权威源”，导致多处重复维护 |
| **根本原因 2** | 代码即文档的陷阱 | VERSION_CAPABILITIES 既是运行时逻辑又是升级描述，但只覆盖一个维度 |
| **根本原因 3** | 发布流程无强制检查 | 没有检查项确保每次版本升级都附带迁移步骤 |
| **错误模式** | 每加一个能力就加一处描述 | 典型的“多处维护”错误：同一信息在 N 个地方更新，漏一个就出错 |

**解决方案（拆分 + 收拢）**：

**第一层：目录拆分——每版本独立升级文件**

将升级步骤拆分为 `governance/migrations/` 目录下每版本独立文件：

├── upgrade-to-0.4.0.md                # 0.3.0 → 0.4.0 升级步骤
├── upgrade-to-0.5.0.md                # ...
├── ...
├── upgrade-to-1.11.0.md
├── upgrade-to-1.12.0.md
├── ...
├── upgrade-to-2.0.0.md                # 1.21.0 → 2.0.0 升级步骤
└── upgrade-to-2.1.0.md                # 2.0.0 → 2.1.0 升级步骤
```

**每个升级文件的统一格式**（`upgrade-template.md`）：

```markdown
# 升级到 {version}

> 从 {prev_version} 升级到 {version}

```

**第二层：信息源收拢 + 版本触点精简**

**版本触点现状分析**（从文件结构设计角度排查）：

当前版本号（如 `2.0.0`）散落在 **12 处 / 9 个文件**，其中仅 3 处由 sync_version.py 自动同步，其余 6 处人工维护：

| # | 文件 | 版本号位置 | 分发包 | 同步方式 | 一致性风险 |
|---|---|---|---|---|---|
| 1 | `scripts/_version.py` | `SKILL_VERSION` | ✅ | **唯一源头** | — |
| 2 | `VERSION` | 文件内容 | ✅ | sync_version.py | ✅ 低 |
| 3 | `skill.json` | `"version"` | ✅ | sync_version.py | ✅ 低 |
| 4 | `SKILL.md` | frontmatter `version:` | ✅ | sync_version.py | ✅ 低 |
| 5 | `README.md` | 标题 `v2.0.0` | ✅ | **❌ 人工** | ⚠️ 高 |
| 6 | `README.md` | 版本表 `Skill 版本` | ✅ | **❌ 人工** | ⚠️ 高 |
| 7 | `README.en.md` | 标题 `v2.0.0` | ✅ | **❌ 人工** | ⚠️ 高 |
| 8 | `README.en.md` | 版本表 `Skill version` | ✅ | **❌ 人工** | ⚠️ 高 |
| 9 | `SKILL.md` | 版本控制表 `当前 X.X.X` | ✅ | **❌ 人工** | ⚠️ 高 |
| 10 | `SKILL_BLUEPRINT.md` | §1 `当前版本` | ❌ | **❌ 人工** | ⚠️ 中 |
| 11 | `skill.json` | `blueprint.lastVersion` | ✅ | **❌ 人工** | ⚠️ 高 |
| 12 | `CHANGELOG.md` | 每版本标题 `## X.X.X` | ✅ | **❌ 人工** | ⚠️ 中 |
| 13 | `skill.json` | `versionHistory[].summary` | ✅ | **❌ 人工**（sync 只插 version+date，不生成 summary） | ⚠️ 中 |

**核心问题**：1 个源头，9+ 个派生位置，但 sync_version.py 只覆盖 3 个（#2~#4），剩余 7 个（#5~#13）全靠人工维护——这就是不一致风险的根源。

**文件结构设计决策**（哪些文件必须有版本号、能否用指针替代）：

| 文件 | 必须有版本号？ | 理由 |
|---|---|---|
| `VERSION` | **必须** | Skill 根目录结构规范（VERSION 必须在第一层），pack.py 首先读取此文件 |
| `skill.json` version | **必须** | JSON 元数据消费者（平台/AI）需要 version 字段 |
| `SKILL.md` frontmatter | **必须** | Qoder 平台读取 SKILL.md 时需要 frontmatter version |
| `README.md/en.md` 标题 | **必须** | 人类可读性（GitHub/分发场景），分发包内含 |
| `README.md/en.md` 版本表 | 可消除 | 但人类快速查看有用 → 保留但由 sync 自动同步 |
| `SKILL.md` 版本控制表 | 可消除 | 导航有用 → 保留但由 sync 自动同步 |
| `SKILL_BLUEPRINT.md` §1 | 可消除→指针 | 开发侧文件（不进分发包），可改为"详见 `scripts/_version.py`"→但 sync 自动同步更实用 |
| `skill.json` blueprint.lastVersion | **必须** | 平台/蓝图审查需要 |
| `CHANGELOG.md` 标题 | **必须** | 变更历史本质属性（每版本标题天然含版本号） |
| `skill.json` versionHistory summary | **必须** | 平台/蓝图审查需要，摘要由人工从升级文件复制 |

**结论**：大部分文件的版本号**不可消除**（结构规范/平台要求/人类可读性）。真正的优化不是"用指针替代数字"，是**确保所有含版本号的文件都被同一个 sync 脚本覆盖**——升级时只改一个文件、运行一个脚本，全部自动同步。

**优化后版本信息架构**：

| 层级 | 设计 |
|---|---|
| **唯一存储** | `scripts/_version.py`（`SKILL_VERSION`）— 唯一改版本号的入口 |
| **全量同步** | `sync_version.py` 扩展覆盖**全部 8 个派生位置**（含 README×4 / SKILL.md 版本表 / BLUEPRINT §1 / skill.json blueprint.lastVersion / CHANGELOG 最新版本标题） |
| **audit 守护** | `audit_release.py` 验证全部触点一致性（11 类断言） |

**优化效果**：

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 人工维护版本号文件数 | 9 个文件 12 处 | **1 个文件 1 处**（`_version.py`） |
| 升级时需手动变更点 | 12+ 处 | **4 步**（改 `_version.py` + 运行 sync + 运行 audit + 写内容） |
| README 版本不一致风险 | ⚠️ 高（人工维护） | ✅ 消除（sync 自动同步） |
| 发布检查项 | 15 项 | **14 项**（sync 处理版本号 + audit 守护一致性） |

**versionHistory 摘要来源定义**（解决 S-C 审查问题）：

`skill.json` versionHistory 的 `summary` 字段来源明确：
- **权威源**：`upgrade-to-{version}.md` 的“变更摘要”段（一句话描述）
- **写入时机**：发布时人工将升级文件“变更摘要”复制到 skill.json versionHistory 对应条目
- **sync_version.py 行为**：仅插入 `version` + `date`，不生成 `summary`（summary 由人工填写）
- **一致性校验**：发布检查清单 D 组 AI 预检会自动对比 versionHistory 摘要与升级文件“变更摘要”是否一致

**同类问题：非版本统计数据的散落**

升级时需更新的不只是版本号，还有多类统计数据散落在多个文件中：

| 数据点 | 当前值 | 散落位置数 | 涉及文件 | 当前同步方式 |
|---|---|---|---|---|

**核心问题**：和版本号一样的模式——多处散落、人工维护、无自动检查（仅回归用例数有 audit 守护）。

**解决思路**：

- 升级时 audit 自动统计，人工只需判断内容，不再手动数数

**AI 升级执行流程**（20 号规则新增）：

```markdown

**触发条件**：AI 启动 Skill 时，或 PM 指示“升级工作区”时。

1. 读取工作区 `.skill-version.json` 中的 `skillVersion`

**设计原则**：
1. **拆分防膨胀**：每版本独立文件，避免单文件过大
2. **收拢减维护**：升级文件是权威源，其他触点从它派生
3. **版本链连续无断点**：每个版本都必须有对应升级文件
4. **发布强制绑定**：每次发布必须创建升级文件，否则不允许发布
5. **AI 可读可执行**：统一格式设计为 AI 可直接解析并执行
6. **一处维护多处派生**：发布时只写一个升级文件，其他信息从中提取
7. **文件结构规范必须遵守**：如 VERSION 必须位于 Skill 第一层目录，这是规范约束，不可精简

## 需求十三明细：日报存档 + 待办字段自动映射 + 进度字段（V0.36 新增）

**来源**：用户在赵维芳 2026-08-17 待办文件实际使用中发现：① 日报收集后应先存档再加工；② 日报进度描述应自动映射到待办字段；③ 待办表缺进度字段。

### 13.1 日报处理两步流程（01 号规则修订）

| 步骤 | 动作 | 规则要求 |
|---|---|---|
| 1. 存档 | 日报原文逐字写入 `todos/{date}/{owner}.md` **§2 日报存档**章节 | 独立章节，含收集时间/来源标注；禁止只存加工摘要；存档是映射的前置步骤（先存档后映射） |
| 2. 映射 | 从存档内容提取进度/问题描述，匹配当天待办清单条目并写入对应字段 | 进度百分比→核心执行表“进度”列；bug 数/回归项→备注区对应待办行；映射结果在日报存档段尾部登记（可溯源） |

**映射匹配规则**：按待办标题/关键词匹配日报中的业务描述（如日报提“外资公司”→匹配标题含“外商投资企业”的待办）；匹配不到任何待办的进展 → 标记“待归属”，由 PM 确认是否新建待办（联动安全底线 2：禁止 AI 自动新建，必须 PM 确认）。

### 13.2 进度字段设计（待办模板修订）

**落位决策（D-24）**：进度列加入**核心执行表**（7 列 → 8 列）：

| 候选方案 | 判定 | 理由 |
|---|---|---|
| 核心执行表加列（8 列） | ✅ 采纳 | 进度是每日高频字段；正好压在“核心表 ≤ 8 列”稳定上限内，不突破 AI 生成能力边界 |
| 备注区列表项 | ❌ 否决 | 重蹈“10% 混存备注”覆辙，无法结构化统计 |
| 工时与变更表加列 | ❌ 否决 | 进度与工时语义不同，且降低查看效率（需跨表） |
| 状态列合并（如“进行中-80%”） | ❌ 否决 | 破坏状态枚举，影响结转/统计的确定性 |

**进度字段规则**：取值 0%~100%（或“—”）；来源：日报映射/PM 手工更新；状态=已完成时进度必须为 100%（一致性检查项）；结转时进度随待办一起结转。

**列预算硬约束**：核心执行表 8 列已达上限，后续任何新增字段一律下沉备注区或其他表（已同步写入需求八设计原则 1）。

### 4.3 T+1 拷贝机制

写入 `00-pm-main-rules.md` 新增规则段：

**触发**：AI 创建当日 `todos/{date}/{姓名}.md` 且文件不存在。

**流程**：
1. 读取前一天同一人的待办文件
2. 拷贝 §0 人员信息段
3. 完整性检查：
   - 岗位/联系方式/负责模块为空 → 标注“⚠️ 待补全”
   - 离组日期已到（≤ 今天）→ 提示“⚠️ {姓名} 离组日期已到，是否更新？”
4. 前一天文件不存在（首次出现）→ 提示 PM 填写
5. PM 要求变更 → 直接修改当日文件 §0

### 4.4 resource-register 保留策略

## 7. 异常场景

| 异常 | 处理 |
|---|---|
| 前一天无该人文件（首次出现） | AI 提示 PM 填写 §0，不阻塞 |
| §0 字段缺失 | AI 标注“⚠️ 待补全”，列出缺失项 |
| 离组日期已到 | AI 提示是否更新 |
| 白天同步与晚间日报有歧义（DF-003） | 编号罗列请 PM 逐条确认 |
| PM 说“再查一下”（DF-004） | 必须实际重读文件，说明与上次差异 |
| 旧工作区 continuity/ 未迁移 | AI 检测到 continuity/ 存在，提示合并入 context/ |
| 旧工作区 outputs/ 在根目录 | AI 检测到根目录 outputs/，提示移入 ai/outputs/ |
| 前一天 `_index.md` 不存在（首次使用） | 跳过结转检查，输出提示「️ 前一天无 `_index.md`，无法执行结转检查」 |
| 查询某人待办时今天文件不存在 | 触发 Step 0 结转检查自动生成，不逐日扫描历史 |

| 版本缺漏（如 0.2.0/1.3.0 无条目） | migrate_workspace.py 补齐 VERSION_CAPABILITIES + 补齐对应升级文件 |

> **核心原则（用户指令，V0.34 固化，V0.35 提升为 §0 升级强制要求）**：全部迁移升级。低版本目录和废弃文件必须删掉，**不留任何“历史缓存”**。目标是降低 AI 调用理解复杂度：迁移完成后工作区只存在一套 v2 标准路径与结构，AI 规则禁止高版本再查低版本目录文件。禁止跳过迁移直接删除（数据安全）；也禁止迁移完成后保留旧路径/归档副本（指向唯一，消除新旧并存的模糊指向——这正是 AI 反复维护低版本目录的根因）。

**三类数据全量迁移策略（V0.34，无窗口限制）**：

| 数据类型 | v1.x 旧路径 | 迁移策略 | 迁移目标（v2 标准结构） | 旧路径处置 |
|---|---|---|---|---|
| 个人日报 | `projects/*/reports/daily/personal/` | **全量内容级迁移**（无窗口限制，按月分批） | 对应日期的 `todos/{date}/{owner}.md` §3 工作日志段（V0.37 章节号标注；待办文件不存在时创建） | **删除** |
| 项目日报 | `projects/*/reports/daily/project/` | **全量文件级规范化迁移**（不解析内容） | `reports/daily/project/YYYYMM/YYYY-MM-DD-[project]-项目日报.md`（YYYYMM 单级目录 + v2 命名，01 号 §4.1 索引同步重建） | 旧结构文件**删除** |
| 周报 | `projects/*/reports/weekly/` | **全量文件级规范化迁移**（不解析内容） | `reports/weekly/YYYY/YYYY-Wxx.md`（01 号 §3.0 标准） | 旧结构文件**删除** |

> **无归档保留（V0.34 推翻 V0.33）**：报告类数据**不进入** `archive/v1-legacy/`——个人日报内容全量融入待办体系，项目日报/周报全量迁入 v2 标准结构；旧路径、旧命名、旧层级文件不保留任何副本。彻底消除“新旧并存”导致 AI 误把低版本目录当活跃路径的情况。

**个人日报内容迁移规则（全量，按月分批）**：
1. 按月份从早到晚分批迁移，每批输出迁移条数与覆盖日期清单，PM 确认进度

3. 对应日期待办文件不存在时，基于 `personal-daily-todo-template.md` 创建（历史文件仅含 §0 人员信息段 + §3 工作日志段，待办清单段留空）。**历史原文保全口径（V0.40 N-f 澄清）**：历史日报原文**逐字**合并进 §3 工作日志段（禁止摘要化/加工压缩），数据安全以“§3 存原文”保障；历史迁移文件以 N-2 `migration-source` 标记区分为**已归档类只读记录**，不适用 §2 日报存档两步流程（§2 两步流程仅适用于升级后的活跃日报）——两处表述（“仅 §0+§3”与“§2 原文留存”）以此口径统一，无矛盾

1. 扫描三类旧路径，统计文件数与日期范围
