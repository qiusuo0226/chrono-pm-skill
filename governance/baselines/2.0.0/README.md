# ChronoPM v2.0.0

**让 AI 帮你管项目，而不是帮你写文档。**

## 这是什么？

ChronoPM 是一个给项目经理用的 AI 技能（Skill）。装上之后，AI 就能理解你的项目，帮你处理日常管理工作——写日报、整理会议纪要、跟踪任务和风险、管理需求变更、生成周报月报。

它不是又一个项目管理软件。它直接在你现有的文件夹里工作，所有项目数据都是 Markdown 文件，不依赖任何数据库或云服务。

**简单来说：它就是一个越用越懂你项目的 AI 助手，把散落的项目信息自动整理成体系化的知识资产。**

## 这些痛点，你遇到过吗？

做项目管理的人，大概对以下场景都不陌生：

**1. 管理标准不统一**
不同项目经理的管理习惯和方法不一致。同一个项目，换一个人来管，成本把控、风险识别、干系人管理的颗粒度完全不一样。这不是能力问题，而是缺乏一套统一的框架来兜底——项目质量过度依赖个人经验。

**2. 日常琐碎导致信息断层**
项目经理即使建立了比较完备的管理机制和文件体系，但因为日常琐碎事务太多，经常出现某项关联文件没有及时同步的情况。看似小事，但信息一旦断链，累积起来就是项目风险。

**3. 项目交接质量不可控**
项目经理是流动的，人员变动时交接往往不到位。以前的做法是甩一份项目文档包，但几十上百个文件，接手的人根本不知道从哪里看起、哪些是关键信息。隐性风险在交接中埋下，等爆发时已经来不及了。

**4. 大量时间花在文档整理上**
周报、日报、会议纪要、风险清单、变更申请……每天花大量时间整理文档，反而挤压了真正应该花在沟通协调上的精力，本末倒置了。

**5. 验收报告缺乏系统性支撑**
最终的项目验收报告，内容来源于日常管理过程中产生的各种材料。但这些材料分散在各个文件、各个系统里，即使想用 AI 来辅助整理，从零开始投喂也耗费大量精力，而且因为没有完整的投喂标准，效果往往不理想。

**6. 通用 AI 工具不理解项目语境**
项目有大量的专属名词、缩写、内部代号。用通用 AI 的话，需要不断重复解释背景，资源消耗巨大还达不到满意效果，最后大家还是觉得不如自己干。

**7. 多项目联动缺乏全局视角**
高级项目管理者同时管多个项目，需要跨项目统筹资源、了解各项目进度之间的关联影响。但目前没有一个工具能把这些分散的信息串联起来，形成全局视图。

## ChronoPM 怎么解决？

ChronoPM 的定位是**项目管理智能知识助手**。靠日常工作中项目经理持续"投喂"项目相关材料——会议纪要、需求文档、风险清单、周报日报、沟通记录等等——它会自动理解项目专属语境，从成本、资源、干系人、风险、问题、进度等多个维度，生成结构化的项目知识索引，最终形成一套**可读取、可传递、可复用的项目知识包**。

## 带来什么价值？

**拉齐管理基线——给每个 PM 配一个"虚拟 PMO"**
不管项目经理经验深浅，工具都从统一的维度框架去补全信息，不会因为个人习惯不同而遗漏关键维度。管理质量有了下限保障。

**交接从"人走茶凉"变成"知识带走"**
项目交接时，只需移交这套结构化索引文件夹。接手人直接让 AI 读取，快速理解项目全貌——成本花了多少、哪些风险还没关闭、干系人诉求是什么、遗留问题清单。不需要再一个个翻文件，交接质量不再依赖个人表达能力。

**日常材料自动沉淀，释放 PM 精力**
周报、日报、会议纪要投喂进去后，工具自动结构化归档。项目经理不用花大量时间整理文档，把精力还给沟通和协调。同时，这些日常沉淀直接为最终验收报告提供系统性支撑——验收不再是"临时拼凑"，而是"水到渠成"。

**理解项目专属语境，越用越准**
通过持续投喂建立项目专属的知识索引，项目名词、内部代号、历史上下文都能被准确理解。不需要每次重复解释背景，彻底解决通用 AI"听不懂项目话"的问题。

**多项目联动，形成全局视图**
高级项目管理者可以通过关联多个项目的知识包，跨项目统筹资源、对比进度、识别资源冲突，辅助决策。

**零额外学习成本**
它不是一个新系统、新平台，不需要改变现有工作习惯。项目经理只需要像平时一样把材料丢给它，它自动完成结构化整理。

## 怎么用？

**第一步：安装 Skill**

把本目录复制到你的 AI 工具（如 Qoder）的 Skill 目录下即可。

**第二步：初始化工作区**

告诉 AI："帮我初始化项目工作区"。AI 会引导你一步步建立项目结构——项目名称、有哪些人、什么阶段、用什么模式。

**第三步：日常使用**

像跟助手说话一样跟 AI 交流：

| 你说 | AI 做 |
|---|---|
| "今天的日报" | 汇总今天所有更新，生成日报，联动更新个人进度 |
| "开个项目启动会，要点如下…" | 整理会议纪要，提取待办事项，分配到责任人 |
| "客户要加一个 XX 需求" | 登记需求，评估影响范围，更新追踪矩阵 |
| "这周进展怎么样" | 从各文件汇总生成本周周报 |
| "项目集整体状态" | 汇总各子项目状态，生成项目集月报 |
| "检查一下项目信息完不完整" | 扫描所有管理文件，列出缺失项并分级提醒 |
| "这个需求在不在合同范围内" | 从合同→招投标→具体需求三层追溯，给出证据链 |

## 待办与任务包：项目执行的核心（v2.0.0）

v2.0.0 把整个执行体系收敛成两层：**待办文件**管每一条具体任务，**任务包（WP）**管分组与里程碑。理解这两个概念，就能理解 ChronoPM 的全部数据流转。

### 待办：每人每日一个文件

每个执行人每天一个待办文件：`todos/{日期}/{执行人}.md`。它是任务执行状态的**唯一事实源**——日报、周报、进度、倒排矩阵全部从它实时汇总，不再维护独立的看板或索引。

- **全局唯一编号**：每条待办有 `TD-{人名缩写}-{日期}-{序号}` 编号，跨天、跨项目可追溯。
- **换人不改事**：任务换人执行时新建编号并保留溯源链，谁干过什么一目了然。
- **自带工作日志**：日报内容不再单独成文件，直接写入待办文件的工作日志段（今日完成/进行中/阻塞/风险/工时）。

### 任务包（WP）：计划的编排单位

计划文件（`plans/PLAN-xxx.md`）里用任务包（Work Package，编号 `WP-NNN`）组织工作：

- **待办强制归属任务包**：正式待办都带 WP 引用，计划调整时能精准级联到每条待办。
- **里程碑 = 里程碑型任务包**：预演、上线等里程碑不再单独建文件，就是标了"是否里程碑"的任务包。
- **进度不另存**：任务包进度 = 下辖待办完成比例实时聚合，永远与实际执行一致，不存在"进度数字过时"。

### 数据流转全景

```
【输入入口】  日报 / 会议纪要 / 口述安排 / 需求拆解 / 变更批准 / 倒排计划
                          │
                          ▼  AI 解析提取，统一归属判定
【唯一事实源】 todos/{日期}/{执行人}.md 待办文件
                          │
          ┌──────────┼───────────────┐
          ▼                    ▼                     ▼
  按 WP 引用聚合         按截止日期切片        工作日志段
          │                    │                     │
          ▼                    ▼                     ▼
【计划视图】            【时间视图】            【汇报视图】
任务包进度/倒排倒计时    "今天做什么"/"本周计划"   日报 → 周报 → 月报
```

要点：**写只写待办文件，其他全是它的派生视图**。日报/周报是输出物不是数据源，不会出现"报表和实际不一致"。

### 五个任务创建入口

不管任务从哪个口进来，都走同一套归属判定，保证任务不丢、不重、不乱：

| 入口 | 场景举例 |
|---|---|
| 口述安排 | "给小王加个待办，周五前出接口文档" |
| 日报提取 | 成员日报里的"明日计划"自动转待办 |
| 会议行动项 | 纪要里的行动项提取后落待办 |
| 需求拆解 | 需求确认后拆成任务包与待办 |
| 变更批准 | 变更批准后新增/调整的配套任务 |

每条新任务三选一：**归入任务包**（高置信匹配）/ **独立待办**（有负责人+截止日+交付物）/ **一次性提醒**（不占待办文件，只提示一次）。拿不准时 AI 会追问，绝不自行拍板。

### 状态体系（全中文）

| 实体 | 状态流转 |
|---|---|
| 待办 | 待处理 → 进行中 → 待评审 → 已完成（可 已阻塞 / 已取消 / 已转出） |
| 任务包 | 已规划 → 进行中 → 已完成 |
| 需求 | 已提议 → 已确认 → 进行中 → 已交付 → 已验收（可 已变更 / 已取消） |
| 风险 | 开放 → 监控中 → 已缓解 → 已关闭（可 转为问题） |
| 问题 | 开放 → 处理中 → 已解决 → 已关闭（可 已阻塞） |
| 变更 | 已提交 → 评估中 → 已批准 / 已驳回 → 已实施（可 已取消） |

**状态更新怎么生效**：你说一句"小王的接口文档写完了"，AI 会找到对应待办、建议改为已完成，并自动级联检查（任务包进度、关联风险/问题、需求状态）。过程性更新先写为"待确认"，终态变更（完成/取消）必须你确认后才真正生效——既不漏更新，也不会自作主张。

## 两种工作模式

- **单项目模式**：一个 `ai/` 文件夹管一个项目，适合独立项目。
- **项目集模式**：一个项目集管多个子项目，信息自下而上汇总、决策自上而下通知。适合管一组相关项目的 PM。

## 核心特点

**Markdown 文件就是数据库**
所有项目信息都存在 `.md` 文件里。不依赖任何软件、数据库或云服务。用文本编辑器就能打开看，十年后还能读。

**AI 先读后写，人工确认才生效**
AI 每次操作前先读取现有文件了解上下文。写入重要信息前会先让你确认，不会自作主张改掉你的数据。

**改了什么一目了然**
需求登记、变更控制、影响分析——每一步都有记录。谁提的、什么时候、影响了哪些文件，全部可追溯。

**项目知识不随人员流动**
所有项目知识都在文件里。新人来了，AI 读完文件就能接手；人走了，项目历史不会丢。

**从日报到月报一条龙**
日报、周报、月报、会议纪要、决策记录、复盘总结——全部有标准模板，AI 自动填充和汇总。

**需求范围可追溯**
从合同到招投标文件到具体需求，三层模型帮你搞清楚"这个需求在不在合同范围内"。

**需求双视图：业务⇄实现对应**
同一个需求，甲方看"要做什么"（业务视图），开发看"怎么做"（实现视图）。把开发侧文档（PRD/设计/接口文档/原型）纳入需求库，登记册为每条需求保留"实现视图"和"原型/文档链接"，AI 处理开发日报时能对照业务上下文，真正读懂日报在说什么。

**推导基线，状态推导更聪明**
内置生命周期推导链，能从"预演通过""评审通过""验收通过"等里程碑终态事件自动推导模块/任务的实际完成状态，并与待办文件交叉校验；配合实体台账与跨源矛盾处理，周报与查询不再凭单一待办文件状态下结论，漏数、误判更少。

## 分发包命名规范

发布产物按 `{BrandName}-Skill-v{version}.zip` 命名（如 `ChronoPM-Skill-v2.0.0.zip`）：

- **BrandName**：取自 `skill.json` 的 `displayName` 品牌前缀（`—` 或 `(` 之前）
- **version**：语义化版本号，加 `v` 前缀

本机打包使用 Python 入口 `tools/pack-skill/scripts/pack.py`（PowerShell 执行策略受限时）；其排除模型实读 `pack.ps1`，以之为**唯一事实源**，`pack.ps1` 作为跨平台参考实现。发布前须通过 `governance/scripts/audit_release.py` 审计（含“命名漂移守门”断言，禁止 `{name}-{version}.zip` 类旧格式产物）。
