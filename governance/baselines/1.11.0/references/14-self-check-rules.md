# 自查与完整性校验规则

本规则用于确保 AI 在处理项目文档时不遗漏关键事项。项目管理必须严谨，AI 必须对每次处理结果进行自查校验，发现遗漏时主动补充。

---

## 1. 核心原则

1. **索引预建，不是边查边建。** 索引在日常更新时自动维护，查询时直接读取，不在查询时临时构建。
2. **处理即校验。** 每次处理日报、会议纪要、评审材料、文件导入后，必须执行自查清单。
3. **遗漏即补充。** 自查发现遗漏时，立即补充，不等用户发现。
4. **不确定即标注。** 无法确认是否遗漏时，明确标注不确定项，不隐瞒。
5. **可追溯。** 每次自查结果记录在 AI 操作日志中。

---

## 2. 索引预建规则

### 2.1 禁止边查边建

AI 查询时**不得**：
- 临时创建脚本扫描目录
- 逐个读取日报文件搜索关键词
- 临时读取 Excel 文件提取信息
- 在查询过程中构建索引

AI 查询时**必须**：
- 先读取对应索引文件
- 索引存在且未过期 → 直接返回结果
- 索引不存在 → 提示用户重建（不自行全量扫描）
- 索引过期（>24h）→ 提示用户「索引可能过期，上次更新 X 小时前，建议重建」

### 2.2 索引自动维护时机

索引在以下场景**自动更新**，不需要用户专门要求：

| 触发场景 | 自动更新内容 |
|---|---|
| 日报处理完成后 | 从"明日计划"提取 TODO → `personal-todo-index.md` + `daily-todo-index.md` |
| 会议纪要处理后 | 从行动项提取 TODO → `personal-todo-index.md` + `daily-todo-index.md` |
| 任务看板更新后 | 同步任务状态到 `personal-todo-index.md` |
| 周报生成后 | 提取本周重点 → `weekly-todo-index.md` |
| 日报索引维护时 | 更新 `YYYYMM/index.md` 月度索引 |
| 个人进度联动时 | 更新 `summaries/{name}-progress.md` |
| 待确认变更新增时（主动写事实源/高风险建请求） | 写入 `pending-changes.md` 条目，`total_pending` 加 1，保持与 Change Log `Confirmed By: 待确认` 条目一一对应 |
| 待确认变更确认后 | 更新 Change Log `Confirmed By` 为 PM 姓名，从 `pending-changes.md` 移除对应条目，`total_pending` 减 1 |
| 待确认变更驳回后 | Change Log 追加 `修改原因: 驳回-恢复原值`（保留驳回轨迹），AI 恢复事实源原值，从 `pending-changes.md` 移除对应条目，`total_pending` 减 1 |

### 2.3 索引一致性检查

AI 在每次更新索引后，必须执行一致性检查：

| 检查项 | 规则 |
|---|---|
| 索引 vs 事实源 | `personal-todo-index.md` 中的 TODO 状态必须与 `tasks/board.md` 中的任务状态一致 |
| 索引 vs 日报 | `daily-todo-index.md` 中的待办必须能在对应日报"明日计划"中找到来源 |
| 月度索引 vs 文件 | `YYYYMM/index.md` 中的记录数必须与 `YYYYMM/` 目录下的日报文件数一致 |
| 个人进度 vs 看板 | `summaries/{name}-progress.md` 中的任务必须与 `board.md` 中该人的任务一致 |

一致性检查补充（D11，pending 一致性）：`pending-changes.md` 中的条目必须与 Change Log 中 `Confirmed By: 待确认` 条目**一一对应**，且 `total_pending` 与待确认条目数一致；发现不一致时，**以 Change Log 为准重建 `pending-changes.md`** 并输出差异清单。

> 注：待确认项为临时"质保"状态，`Confirmed By: 待确认` 记录不计入延期判定与已完成统计（见 `05-query-rules.md` §6.5/§6.6）。

发现不一致时：
1. 以事实源为准。
2. 输出差异清单。
3. 建议修正索引。

## 3. 文档处理自查清单

### 3.1 日报处理自查清单

日报处理完成后，AI 必须逐项检查：

| 序号 | 检查项 | 漏了会怎样 | 检查方法 |
|---|---|---|---|
| D1 | 今日完成事项是否全部提取为任务进展 | 任务进度不更新，看板滞后 | 逐条核对"今日完成"区块 |
| D2 | 进行中事项是否更新到任务看板进度 | 看板进度不反映实际情况 | 逐条核对"进行中"区块 |
| D3 | 明日计划是否全部提取为 TODO | 待办索引遗漏 | 逐条核对"明日计划"区块 |
| D4 | 阻塞事项是否全部识别为问题候选 | 问题遗漏，风险扩大 | 逐条核对"阻塞/问题"区块 |
| D5 | 潜在风险表述是否全部识别为风险候选 | 风险遗漏 | 扫描"可能""担心""如果""担心"等关键词 |
| D6 | 资源变动关键词是否触发资源联动 | 人员变动遗漏 | 扫描"请假""抽调""借调"等关键词 |
| D7 | 投入工时是否更新到个人进度汇总 | 工时统计不准 | 核对"投入工时"区块 |
| D8 | 日报是否更新月度索引 | 索引不完整 | 确认 `YYYYMM/index.md` 已追加记录 |
| D9 | 个人进度汇总是否同步更新 | 个人视图过期 | 确认 `summaries/{name}-progress.md` 已更新 |
| D10 | 同人同天是否检查了合并而非覆盖 | 日报内容丢失 | 确认同一天同一人不存在多份日报文件 |
| D11 | 待确认变更是否已登记 `pending-changes.md` 且与 Change Log `Confirmed By: 待确认` 条目一一对应、`total_pending` 一致 | pending 索引与实际不一致 | 核对本次新增/确认/驳回的待确认项是否已同步更新 pending-changes，不一致则以 Change Log 为准重建 |
| D12 | Change Log 活跃区是否超 50 行或超 30 天未归档 | 活跃区膨胀、追溯困难 | 活跃区超 50 行或超 30 天触发按月归档到 `change-log/archive/YYYYMM-change-log.md` 并更新 `change-log/index.md` |

### 3.2 会议纪要处理自查清单

| 序号 | 检查项 | 漏了会怎样 | 检查方法 |
|---|---|---|---|
| M1 | 所有行动项是否提取为 TODO | 待办遗漏 | 逐条核对会议中的"行动项/安排/负责/跟进" |
| M2 | 所有决策是否记录到 decision-log | 决策遗漏 | 逐条核对"决定/确认/同意/不做/暂缓" |
| M3 | 提到的风险是否识别为风险候选 | 风险遗漏 | 扫描风险关键词 |
| M4 | 提到的问题是否识别为问题候选 | 问题遗漏 | 扫描问题关键词 |
| M5 | 提到的需求变更是否触发变更流程 | 变更遗漏 | 扫描"变更/调整/新增/取消" |
| M6 | 资源变动是否触发资源联动 | 人员变动遗漏 | 扫描资源关键词 |
| M7 | 待办索引是否同步更新 | 索引不完整 | 确认 todos/ 已更新 |

### 3.3 评审材料处理自查清单

| 序号 | 检查项 | 漏了会怎样 | 检查方法 |
|---|---|---|---|
| R1 | 评审结论是否提取为决策 | 决策遗漏 | 核对"通过/不通过/有条件通过/待确认" |
| R2 | 评审中的待确认事项是否提取为问题 | 问题遗漏 | 核对"待确认/待讨论/待补充" |
| R3 | 评审中发现的风险是否识别 | 风险遗漏 | 扫描风险关键词 |
| R4 | 评审中的行动项是否提取为 TODO | 待办遗漏 | 核对"需要/应该/后续/跟进" |
| R5 | 需求变更是否触发变更流程 | 变更遗漏 | 核对需求状态变化 |
| R6 | 评审纪要是否归档 | 过程记录丢失 | 确认 meetings/ 或 reviews/ 已保存 |

### 3.4 风险/问题追溯自查清单

当用户要求"追溯项目风险/问题"时，AI 必须执行多源交叉校验：

| 序号 | 检查项 | 方法 |
|---|---|---|
| T1 | 风险登记册是否覆盖所有来源 | 对比 risks/risk-register.md 与以下来源的差异 |
| T2 | 来源A：日报中的风险关键词 | 扫描所有日报索引，搜索"风险/可能/担心/如果" |
| T3 | 来源B：会议纪要中的风险讨论 | 扫描会议索引，搜索"风险/可能/担心/如果" |
| T4 | 来源C：周报中的风险章节 | 扫描最近周报的风险部分 |
| T5 | 来源D：问题登记册中的关联风险 | 检查 issues/ 中有关联风险编号的记录 |
| T6 | 来源E：任务看板中的延期/阻塞 | 检查 board.md 中状态为 blocked/overdue 的任务 |
| T7 | 差异报告 | 输出"登记册有但来源无"和"来源有但登记册无"两个方向差异 |

**追溯输出格式：**

```markdown
## 风险追溯校验报告

### 校验范围
- 风险登记册：X 条
- 日报扫描范围：YYYY-MM-DD ~ YYYY-MM-DD，共 X 份
- 会议纪要扫描范围：最近 X 次会议
- 周报扫描范围：最近 X 周

### 交叉校验结果

| 风险编号 | 登记册 | 日报 | 会议 | 周报 | 问题关联 | 一致性 |
|---|---|---|---|---|---|---|
| R-001 | ✅ | ✅ | ✅ | ✅ | ✅ | 一致 |
| R-002 | ✅ | ❌ | ✅ | ✅ | - | 日报未提及（正常） |
| - | ❌ | ✅ | ❌ | ❌ | - | ⚠️ 日报提及但未登记，建议补充 |

### 遗漏项

| 来源 | 关键词 | 上下文 | 建议动作 |
|---|---|---|---|
| 日报 2026-08-05 仇索 | "担心接口联调延期" | "...接口还没通，担心下周联调会延期" | 建议新增风险候选 |

### 结论
- 登记册已有风险：X 条
- 发现遗漏候选：Y 条
- 建议确认后补充
```

## 4. 处理后自查输出格式

每次处理完文档后，AI 必须输出自查清单：

```markdown
## 自查清单

| 序号 | 检查项 | 结果 | 说明 |
|---|---|---|---|
| D1 | 今日完成事项提取 | ✅ 3/3 | 全部提取 |
| D2 | 进行中事项更新 | ✅ 2/2 | 全部更新 |
| D3 | 明日计划提取 TODO | ✅ 4/4 | 全部提取 |
| D4 | 阻塞事项识别 | ✅ 1/1 | 已识别为问题候选 |
| D5 | 风险关键词扫描 | ⚠️ 1 项遗漏 | "担心接口延期"未识别为风险候选，已补充 |
| D6 | 资源变动检测 | ✅ 0/0 | 无资源变动 |
| D7 | 工时更新 | ✅ | 已更新 |
| D8 | 月度索引更新 | ✅ | 已追加 |
| D9 | 个人进度同步 | ✅ | 已更新 |
| D10 | 合并检查 | ✅ | 首次创建 |

### 自查发现
- [发现1]：风险关键词"担心接口延期"在初次处理时未识别为风险候选，已补充为 R-YYYYMMDD-NNN 候选
```

### 简洁格式（全部通过时）

```markdown
## 自查清单：✅ 全部通过（10/10）
日报处理完整性校验通过，无遗漏。
```

## 5. 多轮自查规则

### 5.1 首次处理后的自查

首次处理文档后执行完整自查清单。

### 5.2 用户追问时的自查

当用户追问"有没有漏的""是不是全了""再检查一下"时，AI 必须：

1. **重新执行完整自查清单**，不是简单回答"已经检查过了"。
2. **扩大扫描范围**：首次只查了日报，追问时增加会议纪要和周报交叉校验。
3. **输出差异报告**：与首次处理结果的差异。

### 5.3 批量处理时的自查

当一次性处理多份文档时（如全团队日报）：

1. 每份文档单独执行自查。
2. 全部处理完后执行汇总自查（合并去重、交叉校验）。
3. 输出汇总自查清单。

## 6. 遗漏补救规则

### 6.1 发现遗漏时

1. **立即补充**，不等用户确认（低风险项）或立即建议补充（高风险项）。
2. 在自查清单中标注"⚠️ 首次遗漏，已补充"。
3. 在 AI 操作日志中记录遗漏原因和补救动作。

### 6.2 遗漏原因分析

AI 在发现遗漏后，应分析遗漏原因：

| 原因类型 | 说明 | 改进措施 |
|---|---|---|
| 关键词未覆盖 | 用户的表述不在信号词列表中 | 补充信号词 |
| 语义理解偏差 | AI 理解了字面意思但未识别为管理信号 | 标注为经验教训 |
| 处理中断 | 文档过长导致后半部分被忽略 | 分段处理，每段后自查 |
| 格式异常 | 文档格式不规范导致提取失败 | 标注为不确定项，请求用户确认 |

### 6.3 遗漏统计

AI 操作日志中应记录每次处理的遗漏率：

```markdown
## 自查统计
- 处理文档数：5
- 自查项总数：50
- 首次通过：47
- 首次遗漏：3（已全部补充）
- 遗漏率：6%
```

## 7. 索引过期检测

### 7.1 过期判断规则

| 索引文件 | 过期阈值 | 过期处理 |
|---|---|---|
| `personal-todo-index.md` | 24 小时 | 提示「待办索引上次更新 X 小时前，建议重建」 |
| `daily-todo-index.md` | 24 小时 | 同上 |
| `weekly-todo-index.md` | 7 天 | 提示「周度待办索引上次更新 X 天前，建议重建」 |
| `YYYYMM/index.md` | 实时 | 每次日报处理时同步更新 |
| `summaries/{name}-progress.md` | 24 小时 | 提示「个人进度汇总已过期，建议更新」 |
| `pending-changes.md` 待确认项 | 7 天 | 超 7 天未确认进入**日常提醒**（每日催办，合入 `19-info-completeness-rules.md` P0-P3）；超 14 天未确认升级为 **critical**（P0/P1 优先级） |

### 7.2 过期提示格式

```markdown
## 索引状态检测

| 索引文件 | 上次更新 | 状态 | 建议 |
|---|---|---|---|
| personal-todo-index.md | 2026-08-08 10:00 | ⚠️ 过期（25h） | 建议重建 |
| daily-todo-index.md | 2026-08-09 09:00 | ✅ 正常 | - |
| summaries/陈佳菁-progress.md | 2026-08-07 18:00 | ⚠️ 过期（48h） | 建议更新 |

是否现在重建过期索引？
```
