# 自查与完整性校验规则

本规则用于确保 AI 在处理项目文档时不遗漏关键事项。项目管理必须严谨，AI 必须对每次处理结果进行自查校验，发现遗漏时主动补充。

---

## 1. 核心原则

1. **索引预建，不是边查边建。** 索引在日常更新时自动维护，查询时直接读取，不在查询时临时构建。
2. **处理即校验。** 每次处理日报、会议纪要、评审材料、文件导入后，必须执行自查清单。
3. **遗漏即补充。** 自查发现遗漏时，立即补充，不等用户发现。
4. **不确定即标注。** 无法确认是否遗漏时，明确标注不确定项，不隐瞒。
5. **可追溯。** 每次自查结果记录在 AI 操作日志中。

---

## 2. 索引预建规则

### 2.1 禁止边查边建

AI 查询时**不得**：
- 临时创建脚本扫描目录
- 逐个读取日报文件搜索关键词
- 临时读取 Excel 文件提取信息
- 在查询过程中构建索引

AI 查询时**必须**：
- 先读取对应索引文件；有 `context/brain.md` 且 `.state.json` 的 `facts_fingerprint` 一致则先读 brain
- 索引存在且未过期 → 直接返回结果
- 索引不存在 → 提示用户重建（不自行全量扫描）；缺 brain 不致命，读事实原文并声明 as-of
- 索引过期（>24h）→ 提示用户「索引可能过期，上次更新 X 小时前，建议重建」
- 写事实后有 Python 则 P-VIEWS，禁止只改 brain 当纠偏

### 2.2 索引自动维护时机

索引在以下场景**自动更新**，不需要用户专门要求：

| 触发场景 | 自动更新内容 |
|---|---|
| 日报处理完成后 | 原文经 inbox→C' 合入当天 `{owner}.md`；**明日计划只留当天原文，不落成待办行、不建未来日目录**（N-37）。工人**不得**写 `_index.md`。收尾由协调者重建 §3；核对当日 inbox 空（稿先合，claim/runs 删） |
| 会议纪要处理后 | 行动项经 inbox→C' 落待办；缺负责人进 `pm-decisions.md` 块 6。工人不写 `_index.md` |
| 待办状态变更后 | 同步状态到待办文件；绑定文件 `_index.md` 由协调者收尾重建，工人不写 |
| 日报处理完成后（报告侧） | **不再**维护 `YYYYMM/index.md`（v3.4.0 停维）。项目日报/周报/时间线报按 01 号存根范式；判重走 D23 |
| 待裁定事项写入时 | **写入前查重**：键 = **分块 + 对象编号 + 事项键**。命中 → 合并说明/时间，不追加、计数不加。无重复才在 `pm-decisions.md` 对应块追加一行。横幅 N = 八块开放行之和 |
| 待裁定事项确认后 | 从开放块移除，追加「决策记录」。属块 8「已经写了等点头」的同时改事实源 Change Log `Confirmed By` 为 PM 姓名 |
| 待裁定事项驳回后 | 追加决策记录留驳回；属块 8「已经写了等点头」的同时恢复事实源原值 |
| 实体级联完成后 | 确认对应实体规则文件 §级联传播规则 中所有 AUTO 动作已执行、CHECK 结果已输出、SUGGEST 动作已加入建议更新清单 |

### 2.3 索引一致性检查

AI 在每次更新索引后，必须执行一致性检查：

| 检查项 | 规则 |
|---|---|
| 绑定文件 vs 待办文件 | `todos/{date}/_index.md` 中的待办概览状态必须与各人 `todos/{date}/{owner}.md` 待办清单状态一致 |
| 花名册 vs 当日参与 | 同文件 **§3 每人必须出现在 §1**；§3 File Ref 必须指向已存在的个人待办文件；**§3 扫描排除整个 `inbox/`** |
| 非法未来日目录 | 列出 `todos/{date>今天}/` 为非法（不当最新 index，不参与花名册/结转扫描） |
| 待办 vs 来源 | 每条正式待办的来源（日报正式进展 / 纪要行动项 / 已规划 WP 拆待办 / 变更批准等）可追溯。**明日计划不是当天待办来源**（N-37） |
| 日报月度索引（停维） | 存量 `YYYYMM/index.md` 可留不删；**不得**再追加、不得再做记录数一致性校验 |
| RI 登记册 vs 检索路由 | RI 范围判定查询前检查本项目 `requirements/contract-register.md` 非空且格式完整（字段齐全）；登记册中的 active 合同须能在本项目 canonical 索引找到。空登记册 → 触发补录引导，不臆造结论（CR-20260813-002）。跨项目检索请用 ChronoPM-Portfolio |
| 本项目禁写集层 | 本项目 `ai/` 内不得把 `portfolio/` 当事实源落点；发现 `portfolio/` 存储路径 → 不读写，提示跨项目归集请用 ChronoPM-Portfolio |

一致性检查补充（D11，`pm-decisions.md`）：
- **写入前查重（强制）**：键 = **分块 + 对象编号 + 事项键**；命中则合并说明/时间，不追加、计数不加。
- **块 8「已经写了等点头」** 必须与各事实源 Change Log `Confirmed By: 待确认` **一一对应**。不一致 → **以 Change Log 为准重建该块**，输出差异清单。
- **块 1–7 以 `pm-decisions.md` 为权威，禁止用 Change Log 重建。**
- 横幅 N = 八块开放行之和。禁止再用 `total_pending` 单指 Change Log 待确认条数。

> 注：待确认项为临时"质保"状态，`Confirmed By: 待确认` 记录不计入延期判定与已完成统计（见 `05-query-rules.md` §6.5/§6.6）。

### 2.3a `pm-decisions.md` 八块机制（v3.9.0，本文件为唯一完整定义）

路径：本项目 `ai/pm-decisions.md`（懒建）。一个 md，按缺口分块。工人禁写；只协调者写。多源按块追加：读整文件 → 按键查重合并 → 只追加或改命中行 → 写回。禁止写成只剩本源那一块。两协调者冲突：再读再合，禁止互盖。

**开放项八块（各块一张表，列 ≤7）**

1. 需求未确认（含三项缺口：做不做 / 效果 / 方案）
2. 需求未绑定工作包
3. 工作包待确认（绑定草案）
4. 已规划工作包无待办
5. 待办未绑定工作包
6. 待办缺负责人（不落无主待办）
7. 关联待办缺处理方式
8. 其他待裁定：含「已经写了等点头 / 还没写等准许」+ 人员状态提醒（22 号空闲）

**硬规则**

| 动作 | 规则 |
|---|---|
| 写入前查重 | 键 = 分块 + 对象编号 + 事项键。命中 → 合并说明/时间，不追加 |
| 与 Change Log 一一对应 | **只对块 8「已经写了等点头」**。不一致 → 以 Change Log 重建**该块**。块 1–7 以本文件为权威，**禁止**用 Change Log 重建 |
| 横幅 N | 八块开放行之和。白话「有 N 件事等你裁定」 |
| 确认 | 从开放块移除，追加决策记录；属块 8 已经写了等点头的同时改 Change Log `Confirmed By` |
| 驳回 | 决策记录留驳回；属块 8 已经写了等点头的同时恢复事实源原值 |
| 7/14 天催办 | 八块开放行都算，合入 19 号 P0–P3 |
| D21 / D22 | 写入对应块（块 5 / 块 2 或块 3），禁止只在对话里说一声 |

决策记录（已裁定，只追加）：`时间 | 类型 | 对象编号 | 问句摘要 | 裁定 | 影响`。不是聊天原文。活跃区 50 行/30 天 → `ai/pm-decisions-archive/YYYYMM.md`。会议上的拍板仍在 `decisions/decision-log.md`，不与本文件混表。

发现不一致时：
1. 以事实源为准。
2. 输出差异清单。
3. 建议修正索引。

### 2.4 索引派生分级

索引按其能否从事实源重建，分三类管理：

**完全派生索引**（可从事实源全量重建，实体变更时经级联规则 AUTO 触发重建）：
| 索引 | 来源 |
|---|---|
| `todos/{date}/_index.md` §3/§4（绑定派生） | 当日各人待办文件聚合（**排除整个 `inbox/`**）。**§1 花名册不是完全派生**（含无待办者），不得用当日文件重建覆盖。工人禁写 `_index.md` |
| `YYYYMM/index.md`（v3.4.0 停维） | 存量可留；新报告不再维护此派生索引 |

**增量维护索引**（变更时增量更新，非全量重建）：
| 索引 | 维护方式 |
|---|---|
| `change-log/index.md` | 归档时增量追加月份导航条目 |

**独立累积索引**（不可从单一事实源重建，维持现有"过期检测→提示"机制）：
| 索引 | 说明 |
|---|---|
| `outputs/index.md` | 追加式 |
| `pm-decisions.md` | 八块开放项 + 决策记录（独立累积；仅块 8 与 Change Log 待确认对齐） |

规则：
- 完全派生索引在事实源变更时通过级联规则 AUTO 触发重建。
- 增量维护索引不做全量重建，走增量 + 过期检测（§2.3 一致性检查衔接）。
- 独立累积索引不适用自动重建，维持"过期检测 → 提示"机制（§7）。
- 索引级联完整性由各实体规则文件 §级联传播规则 + 本文件 §2.2 末尾"实体级联完成后"行共同保障。

### 2.5 输出前级联验证（强制，仅限写入场景）

当工作流涉及事实源或派生视图的写入/更新动作时，AI 必须在输出前执行级联完成验证，流程见 `00-pm-main-rules.md` §8a.2（唯一权威定义，本文件不重复展开）。

纯查询场景（`10-update-trigger-rules.md` Level 4）不产生写入，不触发此验证。

## 3. 文档处理自查清单

### 3.1 日报处理自查清单

日报处理完成后，AI 必须逐项检查。工人身份**不得**写 `_index.md`（含 `logs/ops/_index.md`）；自查须核对当日 inbox 已空（非空则 AUTO 跑 C'，不得静默删稿、不得向人派单）。

| 序号 | 检查项 | 漏了会怎样 | 检查方法 |
|---|---|---|---|
| D1 | 今日完成事项是否全部提取为任务进展 | 任务进度不更新，待办文件滞后 | 逐条核对"今日完成"区块 |
| D2 | 进行中事项是否更新到待办文件进度 | 待办进度不反映实际情况 | 逐条核对"进行中"区块 |
| D3 | 明日计划是否只留在当天原文（不落待办行、不建未来日） | 违反 N-37：把明日计划落成当天待办或未来目录 | 核对「明日计划」只在当天原文；次日才由结转/T-A3 拉齐正式任务 |
| D4 | 阻塞事项是否全部识别为问题候选 | 问题遗漏，风险扩大 | 逐条核对"阻塞/问题"区块 |
| D5 | 潜在风险表述是否先出识别判定卡 | 见词直登或漏识别 | 检出信号词后须有判定卡；禁止直接写登记册 |
| D6 | 资源变动关键词是否触发资源联动 | 人员变动遗漏 | 扫描"请假""抽调""借调"等关键词 |
| D7 | 投入工时是否更新到待办文件工时列 | 工时统计不准 | 核对"投入工时"区块 |
| D8 | 日报月度索引已停维（v3.4.0） | 继续维护已废索引 | **不要**再追加 `YYYYMM/index.md` / `reports/daily/index.md`。缺 `reports/timeline/` 不报 P0。判重走 D23 |
| D9 | 绑定文件 §3 是否由协调者按当日个人文件重建（工人未写 index） | 工人抢写 index 或 §3 与目录不一致 | 工人禁写 `_index.md`；收尾核目录人名 vs §3（排除整个 `inbox/`） |
| D10 | 同人同天多次汇报是否检查了合并追加 | 工作日志内容丢失 | 确认同人同天汇报合并追加到同一待办文件工作日志段，未覆盖 |
| D11 | 待裁定：写入前按「分块+对象编号+事项键」查重（命中合并不追加）；**仅块 8**与 Change Log `Confirmed By: 待确认` 一一对应；**块 1–7 不以 Change Log 重建** | 重复粘贴，或块 8 与事实源不一致，或误用 Change Log 覆盖块 1–7 | 写入前查重；核对本次新增/确认/驳回；块 8 不一致以 Change Log 重建**该块** |
| D12 | Change Log 活跃区是否超 50 行或超 30 天未归档 | 活跃区膨胀、追溯困难 | 活跃区超 50 行或超 30 天触发按月归档到 `change-log/archive/YYYYMM-change-log.md` 并更新 `change-log/index.md` |
| D13 | 级联传播是否完整执行 | 下游同步遗漏 | 确认对应实体规则文件 §级联传播规则 中所有 AUTO 动作已执行、CHECK 结果已输出、SUGGEST 动作已加入建议更新清单 |
| D14 | WP §3（功能点） 与待办终态一致性 | 实体状态与事实源漂移 | 本轮触碰的 WP §3（功能点） 行 vs 待办终态事件；不一致则 SUGGEST 同步。不查已废 entity-registry |
| D15 | 每条正式待办（有 Owner + Deadline + 交付物）是否 WP Ref 恰好 1 个且非孤儿 | 待办孤儿、多 WP、数据不一致 | **限局部**（本轮触碰）。核对 WP Ref 恰好一个存在的已规划 WP；空/待绑定/none/多值 → 不落完成态，问绑哪个或拆分。禁止全库扫；未触碰历史行只读降级 |
| D16 | 是否存在“只在日报/纪要中呈现而未落待办文件”的半写状态 | 半更新残留 | 检查最近日报/纪要的正式行动项是否按 WF-8 落待办文件（一次性提醒除外）；发现半写 → 补全待办文件并输出差异清单 |
| D17 | 本项目内是否出现集层存储路径 `portfolio/` | 把 `portfolio/` 当本包事实源 | 扫描本项目 `ai/`；发现 `portfolio/` 存储路径 → 不读写，提示跨项目归集请用 ChronoPM-Portfolio |
| D18 | DF 行完整性 | 内置习惯基线丢失、不可审计 | 检查 `context/pm-profile.md` §1：DF-NNN 相对 21 号 §5.1a 基线表编号连续、无缺失、无任何 DF 行被移入 §3 已否决/已废弃段；缺失 → 从模板恢复该行（状态 `disabled` + 备注「检测到缺失已自动恢复」）并提示 PM |

| D19 | 操作类型×已加载规则匹配 | 规则未加载导致漏流程 | 对照 SKILL.md §6 最小规则集：当前操作类型必须已加载对应规则文件；缺失则先加载再继续，不得跳过流程 |

### 3.4 风险/问题追溯自查清单

当用户要求"追溯项目风险/问题"时，AI 必须执行多源交叉校验：

| 序号 | 检查项 | 方法 |
|---|---|---|
| T1 | 风险登记册是否覆盖所有来源 | 对比 risks/risk-register.md 与以下来源的差异 |
| T2 | 来源A：日报中的风险关键词 | 扫描所有日报索引，搜索"风险/可能/担心/如果" |
| T3 | 来源B：会议纪要中的风险讨论 | 扫描会议索引，搜索"风险/可能/担心/如果" |
| T4 | 来源C：周报中的风险章节 | 扫描最近周报的风险部分 |
| T5 | 来源D：问题登记册中的关联风险 | 检查 issues/ 中有关联风险编号的记录 |
| T6 | 来源E：待办文件中的延期/阻塞 | 检查待办文件中状态为已阻塞/已超期的任务 |
| T7 | 差异报告 | 输出"登记册有但来源无"和"来源有但登记册无"两个方向差异 |

**追溯输出格式：**

```markdown
## 风险追溯校验报告

- 风险登记册：X 条
- 日报扫描范围：YYYY-MM-DD ~ YYYY-MM-DD，共 X 份
- 会议纪要扫描范围：最近 X 次会议
- 周报扫描范围：最近 X 周

### 交叉校验结果

| 风险编号 | 登记册 | 日报 | 会议 | 周报 | 问题关联 | 一致性 |
|---|---|---|---|---|---|---|
| R-001 | ✅ | ✅ | ✅ | ✅ | ✅ | 一致 |
| R-002 | ✅ | ❌ | ✅ | ✅ | - | 日报未提及（正常） |
| - | ❌ | ✅ | ❌ | ❌ | - | ⚠️ 日报提及但未登记，建议补充 |

### 遗漏项

| 来源 | 关键词 | 上下文 | 建议动作 |
|---|---|---|---|
| 日报 2026-08-05 仇索 | "担心接口联调延期" | "...接口还没通，担心下周联调会延期" | 建议新增风险候选 |

### 结论
- 登记册已有风险：X 条
- 发现遗漏候选：Y 条
- 建议确认后补充
```

## 5. 多轮自查规则

### 5.1 首次处理后的自查

首次处理文档后执行完整自查清单。

### 5.2 用户追问时的自查

当用户追问"有没有漏的""是不是全了""再检查一下"时，AI 必须：

1. **重新执行完整自查清单**，不是简单回答"已经检查过了"。
2. **扩大扫描范围**：首次只查了日报，追问时增加会议纪要和周报交叉校验。
3. **输出差异报告**：与首次处理结果的差异。

### 5.3 批量处理时的自查

当一次性处理多份文档时（如全团队日报）：

1. 每份文档单独执行自查。
2. 全部处理完后执行汇总自查（合并去重、交叉校验）。
3. 输出汇总自查清单。

## 6. 遗漏补救规则

### 6.1 发现遗漏时

1. **立即补充**，不等用户确认（低风险项）或立即建议补充（高风险项）。
2. 在自查清单中标注"⚠️ 首次遗漏，已补充"。
3. 在 AI 操作日志中记录遗漏原因和补救动作。

### 6.2 遗漏原因分析

AI 在发现遗漏后，应分析遗漏原因：

| 原因类型 | 说明 | 改进措施 |
|---|---|---|
| 关键词未覆盖 | 用户的表述不在信号词列表中 | 补充信号词 |
| 语义理解偏差 | AI 理解了字面意思但未识别为管理信号 | 标注为经验教训 |
| 处理中断 | 文档过长导致后半部分被忽略 | 分段处理，每段后自查 |
| 格式异常 | 文档格式不规范导致提取失败 | 标注为不确定项，请求用户确认 |

### 6.3 遗漏统计

AI 操作日志中应记录每次处理的遗漏率：

```markdown
## 自查统计
- 处理文档数：5
- 自查项总数：50
- 首次通过：47
- 首次遗漏：3（已全部补充）
- 遗漏率：6%
```
